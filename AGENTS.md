# AGENTS.md

Guidance for AI coding agents working on this repository.

## What this repo is

Stream Server is a hard fork of an open-source Rust replacement for Stremio's closed-source `server.js`: a local HTTP torrent-streaming engine with archive streaming (RAR/ZIP/7Z/TAR/NZB) and a deliberately small control API — only what stremio-core's `StreamingServer` model calls (`/settings`, `/network-info`, `/device-info`, `/casting`, `/create`, `/{infoHash}/create`, the `stats.json` routes, `/get-https`) plus `/heartbeat` and `/stats.json`, and a **stub of the `/local-addon`** Stremio's default profile calls (`routes/local_addon.rs`: empty manifest, `{"streams": []}`, `{"metas": []}` for both catalog shapes core builds, `meta` → quiet 404, and its own fallback so anything else under the prefix is a debug-logged 404 rather than an ERROR-level unhandled request — kept so stock profiles show no error group, no failed catalog row and log no ERROR per details page; it serves nothing). Media routes and the local-addon stub are open; every control route requires a per-launch bearer token (`ServerAuth`, `server/src/auth.rs`), and everything a control route does is also a library method on `ServerHandle` so embedders need no HTTP client. The README's API section lists every surviving route with its OPEN/TOKEN status and the removed ones. Serves HTTP on **11470** and HTTPS on **12470** by default. **Source is MIT; default binaries are GPL-3.0-or-later** — see [Licensing](#licensing). Consumed by stremio-native (desktop) and stremio-android (JNI) today, and targeted at a new in-development Flutter + libmpv/media_kit client going forward.

This fork has deliberately dropped Stremio server.js API compatibility for transcoding: there is **no HLS transcoding and no FFmpeg/FFprobe integration** (no `hlsv2` route, no probe/hwaccel endpoints, no embedded-subtitle-track extraction) — that logic, and the `ffmpeg`/`ffprobe` runtime dependency it needed, has been removed. Clients are expected to direct-play and handle codecs/subtitles themselves.

**The entire build is pure Rust, with no opt-in native path at all**: `librqbit` is the sole, unconditional torrent backend, 7z is pure-Rust `sevenz-rust2`, and RAR is pure-Rust `unrar-rs` behind a default-on feature. `cargo build` / `cargo test` — with or without `--no-default-features` — always succeeds on a machine with **no** libclang, no fontconfig/gtk headers, no FFmpeg, and no libtorrent. The C++ `libtorrent` backend and its vcpkg build apparatus (the `libtorrent-sys` binding crate, `triplets/`, `vcpkg-overlays/`, `vcpkg.json`) have been removed entirely from this repo; there is nothing left here that pulls in a C or C++ toolchain for torrenting. The server is headless by design — no tray, no desktop GUI; graphical shells live in wrapper binaries in other repos.

## Licensing

The repo **source** is MIT (the `LICENSE` file is unchanged and must **stay MIT** — it contains no GPL code). But RAR support is **on by default** and uses the `unrar-rs` crate, which is **GPL-3.0-or-later**. That crate is only fetched at build time, yet linking it means a **default-built, distributed binary is GPL-3.0-or-later**. This is intentional: the owner wants RAR on by default and is releasing openly (iOS App Store is not a concern). MIT is GPL-compatible, so the MIT source shipping alongside GPL default binaries is fine. To build an **MIT binary without RAR**, use `--no-default-features` (RAR requests then return 501; the librqbit backend is not a feature, so it's not named here). Do **not** change the `LICENSE` file to GPL; document the situation instead.

Both session maps are `archives::sessions::Sessions`, which sweeps a session `SESSION_IDLE_TIMEOUT` after its last lease — a route keeps the lease inside the response body — and dropping a session releases what it owned: an NZB session's NNTP pool, an archive session's downloaded file and extracted members (`archives::source`, one `ProgressiveCache` per member, shared by every request on it, and its writers give up after `cache::ABANDONED_AFTER` with no reader). | `enginefs/` | Torrent engine abstraction. `src/backend/mod.rs` defines async traits `TorrentBackend`/`TorrentHandle`, `BackendConfig` (whose `listen_port: TorrentListenPort` — `Fixed(range)` tried in order, or `Ephemeral` = port 0 — is the one field librqbit consumes at session start), with a single implementation: `backend/librqbit.rs` (pure Rust, unconditional — there is no other backend to select), with `backend/dht_bootstrap.rs` resolving its DHT bootstrap names to address literals first). Plus `engine.rs`, piece/disk/metadata caches, tracker management/probing, and `traffic.rs` (the window that turns the torrents' peer counters into the client's activity signal -- see the bullet below). Offline downloads: `BackendEngineFS::pin_download` (pin set on the `Engine`, unioned into every want-set plan; exempt from idle removal and the seeding pause; **a retention property and never a location** -- see the bullet below -- so a torrent that was streamed first is pinned where it already is, with the engine every open reader holds; a torrent the pin has to add is added like any other, with a `TorrentPlacement` that is now a want-set and nothing more; refused below `PIN_FREE_SPACE_MARGIN` of free space on the store's volume -- `PinDownloadError::client_message` is the only text of that error a route may put in a response body, like `MagnetAddError::client_message`; a refused pin drops the torrent *its own add* created (`started_here && joiners == 0 && !is_pinned && !torrent_activity_registers(..)` -- never one a stream request joined, whose reader is about to open, and never one anybody is on **now**: `joiners` counts who joined the *pending add* and the engine is published before the preconditions are checked, so a stream that opens across `file_count()`/`stats()`/the free-space probe joins nothing and is invisible to it; the live registers are the only thing that sees it) and takes no byte with it, since the refusal precedes any download and what the store holds was fetched by somebody else; persisted in `<download_dir>/pinned-downloads.json` and restored at startup; pins the restore found no torrent for stay dormant, are listed by `dormant_pinned_downloads`, and come back with the torrent. `unpin_download(hash, idx, delete_files)` forgets the pin and, with `delete_files`, deletes the data too -- the whole torrent through `remove_torrent_and_files` when it was the last pin, otherwise just that file, since librqbit has no per-file delete and the torrent must keep running for its other pins; for a dormant pin, its directory in the piece store, which nothing else would reclaim while the pin protects it -- but only after the session has been asked whether "dormant" is even true (see the placement bullet). It returns an `UnpinOutcome`, whose `deleted_files` is what actually left the disk -- never echo the request flag, and never read "already absent" as "freed".) | `stremio-runtime-stub/` | Zero-dep `stremio-runtime` shim binary: spawns the server with `--no-auth` (legacy clients speak plain HTTP and cannot send the bearer header; `REAL_SERVER_ARGS`), monitors it, waits for port 11470, prints the exact ready line legacy clients expect. |

### Always verify these before committing — the whole build is pure Rust, no system deps for any feature combination

```bash
cargo build                 # debug; add --release for the optimized binary
cargo test
cargo fmt --all             # run before every commit; CI enforces --check
cargo clippy --all-targets -- -D clippy::correctness -D clippy::suspicious -W clippy::all
```

## Conventions

- **Errors**: `anyhow` (`Result` + `.context()`) in application crates; `thiserror` for typed errors in `enginefs`.
- **Logging**: `tracing` macros only (no `println!` for diagnostics). Subscriber setup lives in `server`; HTTP tracing via tower-http `TraceLayer`. The one deliberate `println!` besides the startup lines is the generated auth token: secrets never go through `tracing` (the log files would keep them).
- **Async**: tokio multithreaded; `async-trait` for the backend traits; keep hot-path methods cheap (see `TorrentHandle::is_finished` doc comment — no full stats walks on stream-start). Blocking work (e.g. 7z decompression) goes through `spawn_blocking`.
- **Feature gating**: the only cargo feature left in this workspace is `rar` on `server` (`#[cfg(feature = "rar")]`, default-on, returning 501 when disabled). New *native/C* deps must be optional behind a feature, never in the default set; pure-Rust deps like `unrar-rs` (`crypto-rust`) may ship by default, subject to their license (see [Licensing](#licensing)). There is no backend feature to gate — `librqbit` is a plain unconditional dependency of `enginefs`.
- **Routes**: one file per API area in `server/src/routes/`, registered centrally in `build_router()` in `server/src/lib.rs`, which merges two sub-routers. **A new route goes in `control_router()` — token-protected — unless it serves media bytes to a player** (then `media_router()`, open, because players cannot send headers). The `/local-addon` stub is the one deliberate non-media open route (default profiles, legacy clients included, call it as an addon and it exposes nothing) — do not grow it into a real addon. Never add a token-in-query-string path; the bearer header is the only credential. Preserve exact endpoint paths/response shapes for the surface that remains — it mirrors the subset of Stremio's server.js API (camelCase serde) that stremio-core's `StreamingServer` model calls; do not resurrect removed server.js routes without a consumer (see the README's "Removed routes"). A route landing in `media_router()` is **not** automatically on the LAN media listener: that listener serves `lan_media_routes()` (`server/src/lib.rs`), a separate, explicit allow-list of exactly what a cast receiver needs — the byte-serving halves only (`lan_stream_routes`, `archive_stream_routes`, `nzb_stream_routes`), over torrents and sessions the loopback side already created — so a new media route needs its group added to `lan_media_routes()` by name before the LAN can reach it, and the safe default for one that is not is exclusion. The test of belonging there is that a stranger on the network cannot make this device *do* anything through it: `/proxy` and `/ftp` fetch an arbitrary caller-supplied remote URL (an open proxy for whoever can reach it); the archive and NZB `/create` routes download a caller-named archive or open TCP connections to caller-named news servers; and the loopback `stream_routes` create a torrent, with the caller's `tr=` trackers, on the first request for a hash — so the LAN mounts `routes::stream::{lan_stream_video, lan_head_stream_video}` (`EngineAccess::ExistingOnly`: an unknown hash is a `404`, `tr=` is ignored, no magnet add is started or joined). All of that is fine on loopback (only this host's own stremio-core can reach it), not fine handed to the whole LAN. See `server/src/lan_media.rs` and the README's "LAN media listener" section.
- **Library parity**: whatever a control route does must be reachable as a `ServerHandle` method sharing the same function (`routes::system::{engine_stats, file_stats, update_settings}` are the pattern); the embed test compares the two. Input normalisation belongs *inside* the shared function, not in the HTTP handler — the stats functions normalise their tracker list themselves (`compat::normalize_tracker_sources`) and the handlers hand them the raw `tr=` values, so a library caller cannot see different behaviour. Types crossing that boundary stay `serde`-serializable for FFI.
- **State**: `AppState` (Clone, Arc fields) in `server/src/state.rs`; DashMap for concurrent maps.
- **Platform code**: behind `cfg(target_os = ...)` with no-op stubs. Edition 2024 everywhere.
- **Tests**: inline `#[cfg(test)]` modules beside the code; integration test at `server/tests/embed.rs`, where requests to control routes go through `bearer_client(&handle)` (the default config generates a token). Every embedded server binds ephemeral ports for both HTTP (`http_addr` port 0) and librqbit (`ServerConfig::embedded()` sets `TorrentListenPort::Ephemeral`), so any number of server-spawning tests may run in parallel — still fold related assertions into one server where it reads naturally, but there is no port budget. Bare `cargo test` runs everything — there's no reduced default set to worry about.

  **Five ways a test passes here and fails on a CI runner** — four CI rounds went on these, so check every new test against all five:
  1. *Torrent file order.* `librqbit::create_torrent` walks a fixture directory with `walkdir` and never sorts, so a torrent's file indices are the filesystem's readdir order — on ext4 a per-filesystem name hash, different on every machine. Never hardcode an index that is coupled to a file's name, length or path; look it up with `backend::librqbit::torrent_file_index` (enginefs) or `file_index` (`server/tests/embed.rs`). The same goes for anything the *server* derives from the order, notably torrent-wide `phase`, which describes the guessed stream file — ask `/{infoHash}/{fileIdx}/stats.json` about the file you mean. And size fixture files as whole pieces (multiples of the 16 KiB piece length) unless the test is about a boundary piece, or which files share one depends on the order.
  2. *Path spellings.* `prepare_torrent_data_root` stores and reports the **resolved** `cacheRoot`. An expectation built from a `TempDir` path must go through `stream_server::resolved_path` (the same `plain_path(canonical_prefix(..))` the server uses, exported doc-hidden for exactly this) — on Windows `TempDir` yields the 8.3 short name (`C:\Users\RUNNER~1\…`) and the server the long one, and on macOS `/var` is a symlink to `/private/var`. Reproduce it on Linux by running with `TMPDIR` pointed at a symlink to the real temp dir.
  3. *Sleeping instead of synchronising.* Nothing that waits on a spawned task, the blocking pool or the network may be sequenced with a fixed `sleep`. Use `#[tokio::test(start_paused = true)]` where the clock can be virtual, otherwise a bounded poll on observable state (`wait_until`, a `TEST_WAIT_BOUND` deadline). A bound is only there so a regression fails instead of hanging — keep it generous; a tight one is a timing assertion nobody meant to write.
  4. *`{:?}` on a path in an assertion needle.* `Debug` escapes the separator, so a `must not contain` check built that way is vacuous on Windows. Match the formatting the value under test actually used (see `a_torrent_error_reaches_the_client_without_the_server_paths`), or assert against both spellings.
  5. *Waiting for a peer to actually connect.* A bounded wait on a real peer connection is a bet on the runner's network stack, and the Windows runner lost it: a dozen loopback seeder sessions dialling an embedded server's librqbit listener produced `peers=0` after 120 s, run after run, so the test's own precondition — a swarm bigger than the cap — could not be met there at all. Peer-dependent assertions belong in the enginefs tests, which dial *out* to addresses they were handed (`lean_parks_the_surplus_and_full_re_dials_it`); everything else — a footprint, a cap, bytes served from data already on disk — is provable with no peer, which is what the embed suite does (`set_background_caps_the_torrent_and_still_streams`). A test that cannot make its point without a swarm should be one of the enginefs ones, not a second copy in `embed.rs`.

  Fixtures also get a scratch root of their own (`fake_engine_root` in the enginefs tests), never a fixed path under `std::env::temp_dir()`: the tests run in parallel and a pin rewrites `pinned-downloads.json` in whatever root it was given.
- **Versions**: all crates share one version (bump in lockstep across every Cargo.toml).
- **Commits**: conventional style — `feat(scope):`, `fix(scope):`, `build:`, `ci:`, `docs:`, `chore:`.

### Agent model economy

Use the cheapest model adequate for the task at hand. Small/fast models are fine for mechanical edits, docs updates, renames, and enumeration; reserve strong models for architecture decisions, concurrency-sensitive code, and adversarial review. This is a standing instruction from the repo owner to conserve tokens/quota.

## Gotchas & do-not-touch

- **Do not casually edit**: the `.github/workflows/release.yml` build matrix and artifact/asset names (`scripts/generate_release_notes.py` and the release-notes step depend on the `release/*` filenames it produces); `server/Cargo.toml`'s `[package.metadata.deb]` and `[package.metadata.wix]` blocks (release-critical, and the WiX GUIDs must never be regenerated).
- **Contract strings**: `stremio-runtime-stub` depends on the literal ready line `EngineFS server started at http://127.0.0.1:11470` and port 11470 — changing startup output or default ports breaks legacy clients.
- **Release profile** (`panic = "abort"`, lto, opt-level=z, in the root `Cargo.toml`) means no unwinding in release — don't rely on `catch_unwind`.
- **Single instance**: the server takes a lockfile in the temp dir (`stream-server.lock`); a second desktop instance exits silently.
- **Magnet adds block inside librqbit**: `Session::add_torrent` for a magnet resolves metadata before returning, with no timeout of its own, and no torrent exists until then. enginefs runs every such add detached and bounded by `METADATA_RESOLVE_TIMEOUT` (90 s, const-asserted below `INACTIVE_TORRENT_REMOVE_TIMEOUT`) in a registry keyed by info hash. Routes that must answer promptly (stats/status) go through `EngineFS::get_or_begin_add_magnet` (non-blocking: `EngineLookup::Ready`/`Adding`/`Failed`) and report `EngineStats::resolving_metadata` or `EngineStats::magnet_add_failed`; routes that need the file list use `get_or_add_magnet`/`routes::compat::get_or_create_engine` (waits, joins an existing add, and is the only path that retries a failed one) and map the typed `MagnetAddError` with `compat::engine_creation_failure` (timeout → 504). A supervisor task settles the registry entry however the add ends (success removes it; error/timeout/abort — and a panic in debug builds; under the release profile's `panic = "abort"` a panic kills the process instead — turn it into a `FailedMagnetAdd` record), and the engine eviction loop sweeps entries nobody has looked up for the inactivity window. Never call `EngineFS::add_torrent` for a bare info hash or a magnet link from a route — `/{infoHash}/create` included, and `/create`'s `from`, which sorts a magnet out (`routes::engine::CreateSource`) before the torrent-file case reaches `add_torrent`. Trackers can only be supplied by the request that creates the engine (`LibrqbitHandle::add_trackers` is a documented no-op), so every creation path must pass the request's `tr=` trackers. For a magnet librqbit ignores `AddTorrentOptions::trackers` and reads only the link's own `tr=` params, so `LibrqbitBackend::add_torrent` folds the merged list into the magnet URL (`magnet_with_trackers`) — keep that when touching the add path.
- **The pin set is not optional state.** Any new want-set logic (`plan_only_files`, a new `Reconcile` branch, a smarter eviction policy) must union the engine's `pinned_files` in, and anything that drops or pauses torrents must skip an engine with `is_pinned()` -- the idle sweeper and the seeding-disabled pause already do. A pinned file that stops being wanted is a download that silently stalls, and a swept pinned engine loses the cache cleaner's protection with it. Pins are persisted, so the mistake survives restarts. The delete path is where this bites hardest: `unpin_download(.., delete_files = true)` validates `file_idx` against the file list *before* anything is removed (an index the torrent does not have would clear no pin, look like the last pin going, and take the whole torrent), and it drops the file from the playback bookkeeping before it reconciles, because the plan unions the active file back in and librqbit would keep writing through the handle it holds on an unlinked inode. **The bytes are one record of a file and librqbit's have-set is the other**, so the per-file delete asks `TorrentHandle::drop_file_pieces` (librqbit's `drop_pieces`) before it truncates, holds the returned claim until the unlink is done, and the claim's release re-selects the boundary piece the still-pinned neighbour shares. **`drop_pieces` frees no byte** -- it is have-set bookkeeping and hands the indices back precisely so the caller can delete them -- so the delete takes two things: those pieces out of the store (`piece_store::delete_pieces`), and the whole-file copy at the backend's path if an earlier version left one there. Miss the first and the client is told the disk came back while every piece of the file is still in a directory the pin protects, which nothing would ever reclaim. `deleted_files` is therefore "bytes actually left the disk" and **not** "the path is absent": under this storage the path is always absent, so the old "NotFound counts as deleted" would have made the flag a constant true. Without it librqbit kept reporting the deleted file complete, advertised its pieces, and a re-pin downloaded nothing. But `drop_pieces` needs `piece_reclaim`, and at the pinned librqbit rev `Session::add_torrent` refuses that option on a storage that cannot release a single piece -- so `LibrqbitBackend` sets it only when the session's storage can (`session_can_release_pieces`, decided once when the session opens, and asked of the factory rather than assumed from its type). **The shipped session's default storage is the piece store, one file per piece, and releasing a piece is deleting its file -- so `piece_reclaim` is on for every add**, `drop_file_pieces` works, and the per-file delete's claim really does re-select the boundary piece the still-pinned neighbour shares. It was off for as long as the session ran on librqbit's own whole-file filesystem storage, and the degradation it had then is still the code's fallback for a backend whose storage cannot release: `drop_file_pieces` is refused by name and logged, the bytes still go, and the next restart's fastresume validation -- one hash-checked piece per claimed file -- catches the empty file and re-checks the torrent from disk. `piece_reclaim` is persisted with the torrent, and the price of it being on is paid at every startup: **librqbit restores every torrent paused**, because the piece-level want-set is not in the record, and nothing but the reconciler starts one again -- after `restore_pinned_downloads` has put the want-set back and marked each restored engine settled (`reconcile::Conditions::settled`). A change that skips or reorders that is a restart that comes up downloading and seeding nothing.
- **`/proxy` caches, and the cache is bounded by being ordinary cache.** `server/src/proxy_cache.rs` keeps whole 256 KiB chunks of a proxied response under `<download_dir>/.proxy`, beside the piece store and inside the cache root on purpose: the cleaner already walks that directory, so every cached byte is counted, aged and evicted per volume with **no change to `cache_roots` and nothing of it in `EngineFS::protected_torrents`** -- keep it that way. It is one of the two halves of the root the cleaner still walks itself; only `.pieces` is asked for rather than walked. Two traps sit either side of it. The root may not be named `.cache` or `.metadata`: `cache_cleaner::is_session_artifact` exempts *any* path with either component anywhere in it, and a cache that exempts itself from the cleaner is unbounded disk nobody counts. And nothing here may become protected: protection is a set of torrents the *store* holds, this cache has no torrent to be named by, and a proxied stream nobody is reading is the first thing that should go. (`is_path_protected`, the `starts_with` match that used to shield a whole subtree from one protected ancestor, is gone with the paths it matched.) Eviction is per file, oldest mtime first, so it punches holes into the middle of a cached response -- that is intended, and every chunk is therefore read as independently absent. **Presence has to mean complete here, and unlike the piece store nothing outside the module can make it so** (there is no hash to check a URL's bytes against), so a chunk is held in memory until it is whole, written to a temporary name and renamed into place, and one whose length disagrees with its entity is refused at the read and deleted, never served (`Cached::body` is the one place a chunk's length is checked; the lookup lists bucket directories and goes by name); do not "optimise" that into a direct write. **Identity is the other half of that, and has the same reason.** An entity is filed under `<length>_<content type>_<validator>` and the validator is not optional: length and type say nothing about a URL whose content was replaced by content of the same size, and without it chunks of two generations land in one directory and a cached head is joined to a stranger's tail -- a body the player was told a coherent `Content-Range` about and that nothing anywhere could find out was wrong. So a response the origin will identify by neither `ETag` nor `Last-Modified` is not kept, the narrowed fetch asks `If-Range` under the validator, and the join happens only when the `206` names it again. Do not weaken any of the three into "the lengths match". The launch-time sweep (`proxy_cache::sweep`, called from `run` before the router serves) takes those temporaries and **nothing else** -- unlike the piece store's sweep, nothing claims a cached URL, every committed chunk is cache and surviving a restart is the whole point. The key is the target URL plus `h=` plus the forwarded player headers that are not about a range, computed from `routes::proxy::FORWARDED_REQUEST_HEADERS` rather than from a second list; `r=` and `p=` are deliberately out of it (`r=` never reaches the origin, and `p=` in the key would defeat two players sharing one stream). A credential in `h=` is refused, not keyed -- `/proxy` takes no bearer token, so it reuses `CREDENTIAL_REQUEST_HEADERS` rather than restating the credential rule, which has already failed as a discipline four times. **Every** cache hit is put through the same playlist classification (`routes::proxy::is_a_playlist`) a fetch is -- whole or partial, before it answers *and* before a fetch is narrowed against it -- and a hit whose verdict is "playlist" steps aside whole, leaving the player's own range to go to the origin unnarrowed. That is what keeping `r=` out of the key rests on, and it has been got wrong at both ends: while a full hit answered first the same URL was rewritten on a miss and relayed raw on a hit, and while a partial hit narrowed first it came back as a raw unrewritten `206` of the tail alone. Write "every hit" or write nothing here: the qualified form is what let four documents say two different things about one rule. **The doc says what it does not do -- nothing revalidated, no `Vary`, no coalescing -- and that list must stay honest**; the README repeats it, and three documents in this repo have already overclaimed. The one conditional this cache sends is that `If-Range`, and it is not revalidation: it rides on a fetch the player had asked for regardless.
- **The cache cleaner counts occupancy, never `metadata().len()`** (`cache_cleaner::occupied_bytes`): librqbit's *filesystem* storage pre-allocates every wanted file at its full length, so the cache root is full of sparse files whose apparent size is the whole film. The session runs on the piece store now and writes nothing sparse, but the rule stays: the roots are still full of what earlier versions pre-allocated (nothing migrates), and a cleaner that reads a length as a cost is one bad add away from the same reading. Counting `len()` reported 17 GB on a phone holding 3.85 GB and had the cleaner evicting against a limit the disk had never crossed. Unix uses `st_blocks * 512` (a POSIX unit, not the filesystem's block size); Windows falls back to the apparent length, since `std` exposes no cheap equivalent. The same rule already applies in enginefs to progress. A run yields an `EvictionReport`, and one that ends over the limit warns with the protected byte count rather than reporting a cleanup that did nothing. That warning is driven by `EvictionReport::over_limit` and never by `total` against `limit`: one pass is one report folded from every volume's, and summing both sides lets a roomy volume's slack cancel a full one's shortfall -- the client is told the pass got under the limit while the drive it cannot write to is over its own cap by exactly as much as before. Anything folded across volumes that has to answer "is one of them still stuck?" needs its own per-volume figure carried through the fold, as that field is. The debounced clean is armed by the first filesystem event only — re-arming on every event meant a torrent that keeps writing deferred it for the whole of playback. **The floor is `enginefs::CACHE_FREE_SPACE_FLOOR`, one number with three readers** — the stream route's readiness check, this cleaner's cap, and the engine's reconciler (`EngineFS::start_reconciler`, started by `run()` per engine, every 2 s) — and the third is what makes the other two hold: librqbit writes the file it wants straight to `ENOSPC`, so without it a film larger than the free space ran a television to zero between two passes. The reconciler's free-space arm pauses a writing torrent under the floor (`TorrentHandle::stop_torrent` → `Session::pause`, **pinned torrents included** — the one deliberate exception to "anything that pauses skips a pinned engine", because the alternative is the filesystem stopping it as a fatal error; the cleaner still never evicts a pinned one), rings `EngineFS::out_of_space_signal` so `recover_out_of_space_torrents` runs at once, and starts it again itself (`TorrentHandle::start_torrent`) only 64 MiB over the floor (hysteresis, whose memory is the torrent's own run state). Its readers stay parked while the pass decides — librqbit wakes a parked read only when its piece arrives, so `Engine` keeps its readers' wakers and `refuse_reads_for_space` fails them with `StorageFull`; that is done once the **volume** has been short for 20 s (`STOPPED_READ_STALL_BOUND`, per volume and not per torrent, and applied on the same pass as a later torrent's stop), the bound for a server whose cleaner is off. **The refusal is recomputed too, and lifting it is not tied to the start call**: it stands while the free-space arm is the arm stopping that torrent, and the very next pass whose verdict is anything else lifts it (`let_reads_park_again`), because it is a claim about the device and no other arm makes one. Tied to `start_torrent` instead it could stand for ever with nothing able to clear it -- an idle-paused torrent gets no start when the cleaner frees the volume, and the playback that follows resumes it in `activate_file` before the reconcile is asked, so the `Run` finds it already `Live`. The one verdict that does *not* lift it is `Leave`: `Error` is the cleaner's, whose `restart_from_error` lifts it itself, and a failed `statvfs` is evidence neither that the volume filled nor that it cleared. A recovery pass evicts to `RECOVERY_HEADROOM` under the cap so the restarted torrent has room to run; the ordinary pass evicts to the cap, and `restart_from_error` restarts only what the backend actually killed — a torrent that is merely stopped is started by the next reconcile, from a reading it takes itself. The stream route answers `507` for a request that would write to a volume under the floor and `get_statistics` reports `phase: error` with `STOPPED_FOR_SPACE_MESSAGE` for a torrent stopped on one (`Engine::is_stopped_for_space`, recomputed — see the bullet below). Do not move the floor back into the server crate, and **keep the reconciler's stop and the idle pause separate owners of one librqbit state** while the idle policy still has an owner of its own: both are `Session::pause`, and librqbit records only *that* a torrent is paused, never why. `LibrqbitBackend` therefore keeps an `IdlePauses` set of the hashes its own `pause_torrent` paused, and `resume_torrent` — which the engine layer calls on **every** playback start, over torrents it has no reason to think are paused — lifts exactly those and is a silent no-op for everything else. Without that, a starting stream would unpause a torrent the reconciler had stopped and put it straight back onto a full volume, and every ordinary playback start would log an error for unpausing a torrent that was never paused. `stop_torrent` records nothing, so nothing but `start_torrent` lifts it, and the idle sweep skips an engine that `is_stopped_for_space()` rather than pausing it twice.
- **HTTPS here trusts Mozilla's compiled-in roots, not the device's store.** Every `reqwest` client in this workspace is built by `enginefs::http_client_builder` (`enginefs/src/http_client.rs`), which calls reqwest's `tls_certs_only` over `webpki-root-certs`; librqbit has its own copy of the same policy at the pinned rev, so a tracker announce is covered too. **Do not build a bare `reqwest::Client`**: reqwest 0.13 hands any client that brings no roots of its own to `rustls_platform_verifier::Verifier`, and `add_root_certificate` is not an escape (extra roots take `new_with_extra_roots`, still that verifier). On Android that verifier calls Java's `CertPathValidator` with revocation checking on, so a leaf with no OCSP URL makes Android download and parse the issuer's CRL in Java -- measured at ~400 MB of Java heap per announce on a Chromecast with Google TV, 91% of the app's Java allocation and the GC storm behind an ANR; on Linux it re-reads the system store from disk per client built, and this workspace builds several. The trade is stated in the module doc and is deliberate: a corporate TLS-inspecting proxy's CA no longer verifies our HTTPS, which for a server whose every HTTPS peer is on the open internet is the right way round. `enginefs/tests/tls_roots.rs` proves it by difference (a plain builder cannot `build()` with `SSL_CERT_FILE`/`SSL_CERT_DIR` pointed at nothing; ours can), and a unit test pins that the compiled-in set is a real root program -- with `tls_certs_only` an empty set trusts nothing. Two clients are deliberately outside it and neither reaches the platform verifier: `/proxy`'s unverified retry (`danger_accept_invalid_certs` takes reqwest's `NoVerifier` arm first) and one proxy unit test whose connection is refused before any TLS. `jni::init_android_tls_verifier` still arms the Java verifier, as a fallback for a client somebody forgets to route through the builder -- a handshake that reaches it is the bug, not the design.
- **Stopping an idle torrent is a real pause, and it exists because of the volume.** With `seedingEnabled=false` and nothing playing, the reconciler's idle arm calls `TorrentHandle::stop_torrent`, which for librqbit is `Session::pause`: peers dropped, writes stopped, piece map and files kept, and `Session::unpause` (`start_torrent`) puts it back with no re-check and no progress lost. It was the trait's no-op until the free-space review measured what that cost -- an engine marked `idle_paused`, the free-space watch of the day skipping it *because* it claimed to be paused, and the torrent going 3 MiB to 12 MiB in three seconds straight through the floor. (Both halves of that are gone: there is no flag to claim anything, and the reconciler asks the volume and the run state.) So the trade the old no-op was protecting (a paused torrent loses its swarm and the next episode has to re-acquire it) is taken deliberately: what the stop stops is a torrent fetching a film nobody is watching while we have promised to upload nothing, and that is not worth a television's disk. The cost is bounded by the anti-flap dwell (`RECONCILE_MIN_DWELL`): after the reconciler moves a torrent, its *timer* leaves it stopped for one `INACTIVE_TORRENT_PAUSE_GRACE`, while a stop (a disk fills in seconds) and a playback start (somebody is waiting) are both exempt. `set_upload_throttled` remains on the trait as the gentler lever and has no caller. Two tests pin the stop against a real two-session swarm, both of which failed against the no-op: one that it freezes the fetch and the start keeps the pieces, one over the finding's whole scenario -- seeding off, a stream that starts and ends, the grace, and the bytes stopping.
- **librqbit's `paused` flag is not what the torrent is doing, and across an initial check it is wrong in both directions.** `ManagedTorrent` keeps a persisted `paused` bool *and* a `ManagedTorrentState`, writes them at different moments, and lets them disagree. `Session::unpause` sets `paused = false` (`torrent_state/mod.rs:649`) before `_start` discovers a check is already running and returns success having started nothing (`:548-551`); that check finishes with its own captured `start_paused` and parks the torrent in `Paused` -- stopped, flag says running. The other way, `TorrentStateInitializing::check` passes `pause_requested` to `FileOps::initial_check` and to nothing else (`initializing.rs:279`, read at `file_ops.rs:113`), so a pause landing during a *fastresume* check is dropped, the continuation applies the add-time `start_paused` and the torrent goes `Live` -- downloading, flag says paused. That second one is the measured 3 MiB -> 12 MiB overshoot past the free-space floor. A third shape has no divergence but no settled state either: a pause during a *full* check does bail it, and the `Err` arm returns `Ok` without touching the state (`mod.rs:590-593`), leaving the torrent `Initializing` with no check running, which `wait_until_initialized` (`mod.rs:759`) polls forever. So ask `TorrentHandle::run_state` (`enginefs/src/backend/mod.rs`), which reads the state machine, and never `is_paused()`; and keep `Initializing` a separate answer from `Paused`, because only the latter is a state anything can start again. Three tests in `backend/librqbit.rs` (`run_state_*`) drive a real persisted session into each shape; they need a storage that blocks in `pread_exact` (`gated_storage`) to be inside the window at all, which is why no earlier test in this area could see it. librqbit's own `is_pause_requested` is `pub(crate)` at the pinned rev, so the `pause_requested` these report is the persisted flag -- the same thing to a caller, but it cannot tell you whether the check is still running.
- **Why a torrent is paused is never stored; it is recomputed.** There is one persisted pause bit in librqbit and two policies that pause -- the idle one (nothing playing, seeding off) and the free-space one -- so every earlier round of this code kept an in-memory note of which policy owned a pause (`Engine::idle_paused`, `Engine::stopped_for_space`, `LibrqbitBackend`'s `IdlePauses` set) and asked the note before acting. Those notes start empty in a fresh process while the pause they describe survives it, so after a restart "empty" reads as "nobody paused it" and the call sites that consult them (`pin_download`, `set_seeding_enabled`, `focus_torrent`, all `if idle_paused.swap(false) && ...resume()`) are dead in exactly the case they exist for; a stored "no space" would additionally be a claim about a disk that may have been emptied since. `enginefs/src/reconcile.rs` replaces the lot: `desired()` is a pure function of conditions that are all readable now -- run state, playing, pinned, metadata, finished, free bytes, idle time, and the reason the decision is being taken -- and the set of facts that must survive a restart is empty. This works **here** because both policies really are functions of the present and no route in this server lets a user pause a torrent by hand (grep before assuming that still holds). Two rules hold it up: the hysteresis at the free-space line keeps **no** stored bit -- a running torrent is measured against the floor, a stopped one against floor + `FREE_SPACE_RESUME_MARGIN`, so the Schmitt trigger's memory is its own output, pinned by a thirty-tick flap test -- and the decision is read from `TorrentHandle::run_state`, never `is_paused()` (see the bullet above). The reconciler holds one lock per info hash, never one global one: `IdlePauses` was a single `tokio::Mutex<HashSet>` held across `Session::pause`'s persistence flush, which queued every torrent's pause behind every other torrent's disk write. It **observes** the engine registry -- `peek_engine`, never `get_engine`, or a two-second eye would keep every torrent from ever being idle -- and it leaves alone any handle whose backend manages its own playback lifecycle. **It owns both arms, and every pause and every unpause in the process is its call**: there is no `pause_torrent`, no `resume_torrent`, no `unpause_restored`, no `IdlePauses`, no housekeeping-sweep pause and no per-stream grace-period task left. What the last stream ending changes is a condition (`Engine::last_active_at`), which the ladder reads for itself. Every site that used to hand-roll a resume -- the stream route's `MetadataResolutionGuard`, `pin_download`, `focus_torrent`, `on_stream_start` -- is now an **awaited** `reconcile_hash(.., PlaybackStart)`, taken *after* the activity it belongs to is registered (the ladder reads `playing` from those registers) and awaited because the unpause it may issue is what un-wedges a torrent the last process left stopped, and the reader opens on the next line. One of them registers nothing at all -- `focus_torrent` writes no register and stamps no clock -- so **the idle arm is the `Timer`'s alone and a `PlaybackStart` never takes it**: `playing` is read from registers the asker may still be in the middle of writing, and answering "nothing is playing, stop it" to somebody about to open a reader stops the very torrent they named. It was latent because the one production caller runs `on_stream_start` two lines earlier; the gate is what makes that ordering stop mattering. The alternative -- letting `focus_torrent` stamp `Engine::last_active_at` for itself -- buys the same answer by *inventing* the reading the idle arm then measures its grace from, for a whole `INACTIVE_TORRENT_PAUSE_GRACE`, on any torrent any caller names; the gate costs one tick instead, because the next `Timer` pass stops a torrent nobody turned out to be watching. No other arm is trigger-gated: an unsettled reading, a resolving magnet and a volume under the floor answer the same to both. **Every route that opens a reader on a torrent registers a stream first**, and there are two of them, not one: `routes::stream` and the `torrent:` form of `routes::archive::stream_file`, which serves an archive member straight out of a live torrent and registered nothing at all until `TorrentMemberStream` -- so the timer paused the torrent an archive body was streaming from, and a request landing on an already-stopped one asked the reconciler nothing while `LibrqbitBackend::get_file_reader` handed back a reader that parked for ever. Grep for `get_file_reader` before adding a third. Both halves of that registration are held end to end by `server/tests/embed.rs`: `an_archive_body_keeps_its_torrent_running_while_it_is_open` leaves a member's response body open past the grace with a second torrent nobody reads beside it, so the control being stopped in the same window is what proves the idle arm was firing at all; and `an_archive_member_read_lets_the_torrent_be_stopped_again_when_it_is_done` reads a member to its end and waits for the reconciler to stop that torrent again. The guard therefore has to ride *inside* the body -- dropped with the response it would end the registration while every byte the player has yet to read is still to come -- and its `Drop` has to spawn the `on_stream_end`, or every archive member ever read leaves a stream registered for the life of the process. `set_seeding_enabled` is the exception that proves the trigger's rule: a person moved the switch, but nothing is about to open a reader, so it is a `Timer` decision and keeps its resume margin -- `server::run` applies the persisted setting at startup, over every torrent the last process left stopped, and `PlaybackStart` there restarted them at the floor for nobody. The idle arm's clock is `Engine::last_active_at`, stamped only where `torrent_is_active` actually reads the activity registers true, and it is **not** `Engine::last_accessed`: that one is the registry's idle-eviction clock and counts *lookups*, so every `GET /{infoHash}/stats.json` reset it through `get_engine` and a details page left open in the client kept a torrent nobody was watching downloading all night with seeding off (master's sweep read the registers and never `last_accessed`, so this is a guarantee the ladder has to keep, not a new one). **It has two seeds, because the two kinds of engine can vouch for different things, and a single seed is wrong for half of them.** An engine this process *made* is stamped with its creation instant, which is a real observation -- nothing can have used a torrent in an interval that did not exist -- and seeding it with an absence instead paused a freshly added torrent on its first tick with seeding off, dropping the swarm it had just dialled. An engine built over a torrent a *previous* process left behind is given `NEVER_ACTIVE` (`Engine::forget_last_active`, called by `new_with_backend_and_storage` on every restored handle), because this process has no reading of it at all; stamping `now` there claims "used a moment ago" about a past this process never saw, and renews that claim on every restart, so each restored engine bought itself a whole fresh `INACTIVE_TORRENT_PAUSE_GRACE` merely by appearing and an app that restarts often had an idle arm that could not fire. The absence is therefore carried as an absence: `Engine::quiet_for` answers an `Option`, and the idle arm reads `None` as quiet -- a torrent nobody is watching may be paused whether or not we can say for how long, and after a restart there is no recent stream for the grace to protect. `0` is neither seed nor sentinel: it is an ordinary reading meaning "used inside the first second". Only **three** process records survive, and all three are honest about starting empty: `Conditions::settled` ("this process has re-applied the want-set", false at start, which is *correct* -- a piece-reclaim backend restores every torrent paused and wanting every hole, so nothing may start one before `restore_pinned_downloads` has run) `Engine::last_transition_at` (the anti-flap dwell; `u64::MAX` for "this reconciler has never moved it", never `0`, because `Clock::now_secs` answers `0` for the whole first second of the process and a stop made in it -- which the startup `set_seeding_enabled` makes on any quick boot -- would otherwise read as the sentinel and skip the dwell) and `Engine::last_active_at` (the creation instant for an engine this process added, `NEVER_ACTIVE` -- read back as `None`, an absence -- for one restored over a torrent it never saw). `Engine::is_stopped_for_space` -- what the statistics report and the cache cleaner evicts for -- is recomputed the same way, from the run state and the last reading of the volume, through the same `reconcile::volume_is_short` the ladder calls -- but at `CACHE_FREE_SPACE_FLOOR`, **not** at the ladder's hysteresis line. `volume_is_short` takes the line from its caller for that reason: floor + `FREE_SPACE_RESUME_MARGIN` is the ladder's answer to "may I start this one again?", and handing it to a reader asking "is the device short?" reports a volume the stream route serves from and the cleaner's cap calls fine as out of disk, and drops every torrent that merely happens to be paused inside the band out of `EvictionClasses::protected` into `stopped_for_space`, which the cleaner does not protect; `reconcile::Volumes` holds those readings, and they are an observation at most one tick old rather than a record of anything decided. The `Error` arm is `Leave` only for a **settled** torrent: an unsettled one is not the cleaner's either (it will not restart a torrent whose want-set is not back), so the ladder answers `Stop`, which calls nothing on a torrent that is not running but does let its reads park again -- `Leave` there would hold a `StorageFull` refusal that nothing was ever going to lift. `restart_from_error` is the error transition alone: a torrent that is merely stopped is the reconciler's to start, from a reading it takes itself, and one method serving both is how an earlier defect got in. Every test in this area asserts on `run_state`, never on a flag the code under test wrote -- four consecutive defects shipped past tests that asserted the flag. Four of them run over a **real persisted librqbit session**, one per resume site, because the restart is the only place the bug lived; `stats.json`'s `swarmPaused` now answers from `run_state` (it was the constant `false` for every torrent there had ever been), which is what makes the same property assertable from `server/tests/embed.rs`. And because the reconcile is awaited on the request's own future, a test drops that future mid-reconcile and pins that nothing is left behind -- no half-applied state, no unreleased hash lock, no detached task still deciding.
- **The DHT is a peer source, not a requirement, and a dead one must stay quiet.** librqbit retries DHT bootstrap and UPnP forwarding *forever*, at WARN on every attempt (`crates/dht/src/dht.rs`'s `bootstrap_hostname_with_backoff`, `crates/upnp/src/lib.rs`'s discovery/`manage_port` loops), so a network that drops the DHT's UDP produced hundreds of identical warnings and no conclusion in a real field log. Both targets are therefore pinned to `error` in `DEFAULT_LOG_FILTER` (`server/src/lib.rs`) and the state is reported once instead, by `diagnostics::dht_health`: INFO when it comes up, ONE WARN after a 90 s grace if it has not, INFO if it recovers, everything else at debug. Do not re-raise those directives, and do not add bootstrap hosts to `DEFAULT_DHT_BOOTSTRAP_NODES` to "fix" a bootstrap failure: an earlier commit did exactly that and made things worse -- three of the five names it shipped resolve but answer 0/3 DHT pings, which is retry noise, not resilience. The list is now exactly the two names measured to answer (which is also librqbit's own default); `router.bittorrent.com` was kept a while on reputation and dropped once a re-probe from two networks had it answering nothing there either. A test asserts the list exactly, and **a host may only be added with a measured `ping` behind it**. The real fix for the field log was DNS: `backend/dht_bootstrap.rs` resolves the names itself (system resolver, then DNS over HTTPS, then a `dht-bootstrap.json` cache next to `dht.json`) and hands librqbit address literals, since `lookup_host` accepts them; whatever it cannot resolve stays a name so librqbit can keep trying. Both DHT files -- `dht.json` and `dht-bootstrap.json` -- are `is_session_artifact`s in `cache_cleaner.rs`, so the cache cleaner cannot evict the very state that exists to avoid the network. Both resolvers are injected (`BootstrapResolvers`) -- `BootstrapResolvers::offline()` is the no-DNS set every hermetic caller must use, and no test may hit a real resolver. That fixes the DNS half only; a network that drops the DHT's UDP is unaffected, and the doc comments say so. The observable state is `enginefs::backend::DhtStatus` (`ever_bootstrapped` is sticky on purpose), served as the `dht` key of `/stats.json` and as `ServerHandle::dht_status`; a client shows "DHT unavailable, using trackers only", not an error. Also note the librqbit fork's misleading message: `bootstrap_hostname` returns `v4.or(v6)`, so a v4 failure's error is *discarded* and what gets logged is the v6 branch's `NoSuccessfulLookups { errors: 0 }` for bootstrap hosts that have no `AAAA` record -- "0 errors" is an empty v6 address set, not proof that nothing was attempted.
- **UPnP port forwarding is only for a fixed listen port** (`TorrentListenPort::wants_upnp_forwarding`). `Ephemeral` -- what `ServerConfig::embedded()`, the Android JNI cdylib and every test use -- binds a different port each launch, so a mapping is worthless next time, and on Android SSDP discovery is multicast the app sandbox cannot send at all. The forwarder retries on an interval for the life of the process either way.
- **The piece store is the session's default storage, and that is the only place it can be.** `LibrqbitBackend::session_storage_factory` builds a `PieceStoreFactory` over `piece_store::StoreRoot::in_download_dir(download_dir)` -- `<cacheRoot>/rqbit-downloads/.pieces` -- and `open_session` installs it as `SessionOptions::default_storage_factory`, never on an individual add. The persisted record librqbit replays at startup names an output folder and a file selection and **no storage**, so the storage a restored torrent comes back on is whatever the next session's default is; that is why `StorageFactory::ensure_persistable` (a promise that a restart finds the data again) can only be made from here, and it is made. Two consequences you must not forget. **Torrent data is now one file per piece uniformly, downloads included**: librqbit still reports a file path per file, under an output folder it chooses itself, but no payload byte is ever written there -- the store takes one root and it is the cache root, so `DownloadInfo::path` is a name and not a file. Nothing above the backend reads that name for anything (see the placement bullet below). **Every free-space question is therefore asked of that root, and of nothing else**: `reconcile::Volumes` is built over it and has no per-folder API left to get wrong (`available()`, `short_for(now)`, `data_folder()`), which is what the reconciler's arm, `Engine::is_stopped_for_space`, `held_stopped_for_space` (so `out_of_space_torrents`, so the cleaner), the stream route's per-torrent `507` and `check_pin_preconditions` all read. Asking `TorrentHandle::output_folder()` instead -- which every one of them did until the store went in -- reads a card nothing writes to, and for a pin that used to be the card a settings key of its own named: the ladder left a torrent running onto a full store, and refused a pin that had all the room it needed. `check_pin_preconditions` also asks only for the pinned file's **missing bytes**: the copy sizing it used to do (`same_volume`, `volume_id_probe`, `allocated_bytes`, all now deleted) was about a relocation rewriting whole files at the destination, and there is no relocation left at all. **There is no migration, by decision**: a whole-file download an earlier version wrote is neither converted nor read, the torrent re-downloads as pieces, and the old bytes are ordinary cache for the cleaner -- which only works because an engine protects its *pieces* alone (`EngineFS::eviction_classes`, and see the cache-cleaner bullet). One thing did not have to change: `PIECES_PER_DIRECTORY` was already applied in `piece_store::store::piece_path`, so a 27 GB torrent's ~6,750 piece files land in seven bucket directories and not one, with a test that says so. **That bucketing is the store's alone now** -- see the next bullet: `piece_store::StoreRoot` is the one type that turns an info hash and a piece index into a place, and `root_in`/`PIECE_STORE_DIR` are crate-private behind it, so a caller can name the store but never its shape.
- **A pin is a retention property, and `output_folder` decides nothing.** There is one torrent-data root -- the piece store's, `<cacheRoot>/rqbit-downloads/.pieces` -- and data placement is that root plus the info hash and nothing else. `output_folder` is librqbit's concept and stays inside `backend/librqbit.rs` (the fork must remain upstreamable): it is where a torrent's *name* lives, it is reported to a client as `DownloadInfo::path`, and it is what the per-file delete sweeps a legacy whole-file copy from. Nothing in enginefs or server may key off it for placement, monitoring, protection or accounting, and there is no `TorrentHandle::output_folder` to read it with any more. What went with that rule, and must not come back: `TorrentPlacement::output_folder` (the struct is a want-set now), `TorrentBackend::relocate_torrent` and librqbit's file-moving implementation of it, `EngineFS::{relocate_engine, begin_relocation, end_relocation, replace_engine, download_folder, set_downloads_dir, downloads_dir, engine_paths}`, the `relocations` registry the cleaner consulted, `PendingMagnetAdd::settled_later` and its optional abort handle, and the owned pin guard a move carried. **A pinned torrent does not move**, so none of the machinery that made a move safe is owed: it was all there because a pin used to re-add the torrent under `<downloadsDir>/<infoHash>`. Where a location is genuinely needed, ask the store (`BackendEngineFS::piece_dir`): that is what protection, the dormant-pin delete and the free-space check all do. **The dormant-pin delete must prove it is dormant before it unlinks anything, and the registry is not the proof.** `unpin_download` reaches that path because `get_engine` found nothing, and `remove_engine` drops a registry entry while leaving the torrent running (the TUI's `d`, and the idle sweep between dropping the entry and telling the backend), while a magnet add parks a hash outside both the registry and the backend for as long as metadata takes. Unlinking `<cacheRoot>/rqbit-downloads/.pieces/<infoHash>` in either case is the have-set desync the whole interlock exists to prevent -- the torrent goes on advertising pieces that are gone. So three things gate it: the pin actually removed (`was_dormant` -- with no engine and no pin this layer has no record tying those bytes to a download, and they are the cleaner's), `pending_magnet_add` (a hash being added is left entirely alone), and `TorrentBackend::get_torrent` (a torrent the session holds is deleted *through the backend*, `remove_torrent_and_files`, which drops it before its storage releases the pieces -- the interlock stays in the one place). Only a hash the session has never heard of is deleted by hand. `settings.downloadsDir` did not survive: there is one torrent-data root, `settings.cacheRoot`, and the cleaner walks that one root (read from the engine, not from the setting).
- **In the piece store, a piece is ours at one instant, and presence means complete.** Bytes are written to `<piece>.part` and renamed into place in `TorrentStorage::on_piece_completed`, which librqbit calls after the hash check, and `PieceStore::has_piece` answers from the final name alone. That is not tidiness: the rev we pin builds the startup have-set as the resume bitfield **intersected with `TorrentStorage::has_piece`**, the intersection only clears bits, and the fastresume hash check samples ~65 pieces of a torrent however large -- so a wrong "yes" is not a re-download, it is a have-bit standing over bytes nothing verified, advertised and served. A file created by a piece's first 16 KiB chunk is there for the whole of the download, which is why `is_file()` on the piece name is the wrong answer and had to stop being it. Three rules hang off the staging name and each has a test: **a read prefers the staged copy** (the two coexist only while a dropped piece is being downloaded again over one not yet deleted, and the read that decides whether to keep the new bytes is the hash check itself -- served the old copy it passes over bytes nothing wrote); **`init` deletes a staged copy that shadows a complete one, and only that one** (the pair is explained by chunk bookkeeping that does not survive the process, so what a kill leaves is a stale shadow over a verified piece, while a lone staged piece shadows nothing and a pause is allowed to keep its in-flight work); and **`delete_piece` takes both**. A piece no file owns -- entirely inside BEP-47 padding -- answers *yes* to the trait's `has_piece` and *no* to the store's: nothing will ever write it, and a piece nothing can write is a piece nothing can lose, which is the question the trait asks; answering no would clear a have-bit no download could ever set again. The store also keeps a few open handles (`OPEN_HANDLES`, keyed by piece and by copy) and an in-memory set of the pieces that have a staged copy, so a piece written or streamed end to end is one `open` instead of one per 16 KiB chunk (and two per read, the staging probe first). Neither changes what is on disk or what a read sees: a handle is forgotten before its file is renamed or deleted and a cached complete handle goes the moment a staged copy is begun, the staged set is advisory in one direction only (its "yes" is checked against the filesystem, its "no" is trusted because every staged file is either written by this process or seen at `init`), and a test pins the open counts.
- **The retention policy is arithmetic, and it is not wired to anything yet.** `piece_store::policy` decides what we keep and what we share -- budget covers the file, keep and seed all of it; it does not, halve it into a rolling window (90% ahead, 10% behind) and a committed set that is filled only from pieces we already hold and never churns once full. It takes its budget in bytes from `CacheLimit::effective` and does not recompute it, deliberately: two layers with two readings of "how much room is there" evict against different numbers. **Do not build an availability map** -- rarity-based retention was measured at ≤0.15% over random across four live swarms and 0.00% on three of them, because seeder fractions of 94-100% cap the effect -- and **never fetch outside the playhead**: the committed set takes pieces the window is about to release and nothing else. One blocker stands between it and a running torrent, in the fork and not in this repo. The persistence one is gone twice over: `JsonSessionPersistenceStore::update_db` used to refuse a non-`FilesystemStorageFactory` torrent, at the pinned rev it asks `StorageFactory::ensure_persistable` instead, and `PieceStoreFactory` now makes that promise -- it is the session's default factory, which is the only position from which the promise is keepable. What is left is that **"only advertise what is committed" is not expressible through the fork's API today**: `have` implies announced, through both the `have_broadcast` (`should_transmit_have` → `TorrentStateLive::should_advertise_have`) and the handshake bitfield (`serialize_bitfield_message_to_buf`), and a window piece has to be `have` for the stream to read it. `drop_pieces` gives *not* have, not wanted, not advertised -- there is no have-readable-unannounced third state -- so wiring the policy without one would advertise every window piece and then withdraw it, which is exactly the advertise-then-refuse the policy exists to avoid.
- **The activity light reads the connection, never the disk, and it is judged in one place.** `ServerHandle::background_traffic` answers "this server is using your connection while you are not watching", in two halves -- `downloading`, `uploading` -- with `active` their disjunction, because the client's light is one slot with three glyphs and offers a control per half, so each must be honest alone. There is deliberately no taxonomy of who is at the other end. **The conjunction with "nothing playing" is taken in Rust** (`routes::system::background_traffic`), never handed to the client as two signals: the halves are measured differently, and an app sampling them a moment apart across FFI gets a light that flickers on every disagreement. Four things around it are load-bearing. **One: the counters are librqbit's own per-torrent peer counters** (`TorrentHandle::transfer_totals` → `TransferTotals { fetched, uploaded }`, summed by `BackendEngineFS::transfer_totals` over the torrents that exist), compared against the last reading of the same sum. They are *not* the storage and *not* `EngineStats::downloaded`: the first version wrapped the session's default storage factory to count reads and writes, and lit up at every launch with saved torrents, in a session with no network -- librqbit's initial check reads every restored torrent back off the local disk to hash it. `downloaded` has the same trap in another form: it is `progress_bytes`, have-bytes, which mirrors the hash check's `checked_bytes` while a torrent initializes, so it too grows through a check no peer took part in. `fetched` is the peer-received counter and nothing else feeds it; a test (`the_initial_check_moves_nothing_over_the_connection`) adds a torrent whose data is already on disk to a hermetic session and reads the counters before the check and after it -- the reading before is trivially zero, since an initializing torrent has no live state to count, so what the test pins is that the check leaves both halves at zero while `downloaded` ends at the payload's length; the light staying dark *during* the check was observed in a live restart, not asserted. The counters live on the live state, so a torrent that pauses or is removed takes its bytes out of the sum; a sum that dropped reads as "not grown", which is right. **Two: there is one engine** (`AppState::engine`). There used to be two fields, `engine` and `download_engine`, holding the same `Arc` -- the pairing of a memory-only stream engine with a disk-backed download engine was designed and never built, no memory-only storage exists, and every reader read one instance twice behind an `Arc::ptr_eq` guard. The light sums that one engine's torrents (`BackendEngineFS::transfer_totals`), the same reading `/stats.json` takes; "nothing playing" is its `BackendEngineFS::playback_is_live`. If a genuinely distinct second engine is ever wanted it can be added back honestly -- a field that is a clone of another is not that. **Three: the reading is a peek, not a poll, and it creates nothing.** `Engine::get_statistics` touches `last_accessed`; `transfer_totals` must not, or a light polled every second or two holds every torrent out of the idle sweep for ever and is then lit by the seeding it caused (a test pins the idle clock while it asks). Nothing in the path looks a hash up or adds one -- `stats_target` falls through to `get_or_begin_add_magnet`, and a light that started a torrent in order to report on it would be reporting on itself. `stats()` is not the cheap path either: it builds the file list and takes a tracker-scrape snapshot that may schedule a scrape, so the light reads librqbit's `stats_snapshot()` under the torrent's state lock instead -- a handful of torrent-level counters plus the aggregate peer counters, since `TorrentStateLive::stats` is private at the pinned rev -- and takes `fetched_bytes` and `uploaded_bytes` from it. **Four: "moving" is judged over a window and playback has to be absent over that window too** (`TRAFFIC_WINDOW`, 5 s; `TRAFFIC_WINDOW_STALE_AFTER`, 20 s; `TrafficWindow`, on `AppState`, one per server, with its own clock rather than an engine's). A counter that has not grown since the last reading is the measurement -- a single sample of a total is not a rate -- so nothing can be said until one window has closed, and a window that stretched past the stale bound (a backgrounded app, a suspended phone) is a baseline again rather than a verdict about minutes nobody observed. The bytes a player's own stream pulled in are still in the counters after they stop, so a verdict that asked only "is anything playing *now*" would light the light for one window after every playback; the cost of getting that right is up to two windows of latency the other way, which is the right side to be wrong on. Playback seen inside a window puts both halves out at once, not at the window's close -- the verdict does *not* only change when a window closes, and a test says so. `StreamActivitySnapshot::playback_is_live` is the *definition* of "playing" -- the live fields only (`engine_active_streams`, `active_streams`), and it must never grow to include `active_file` or `active_multifile_selections`, which name the file last chosen, outlive the stream because the want-set is planned from them, and would make a light that comes on with the first playback of the session and never goes out. `BackendEngineFS::playback_is_live` is the same answer without building the snapshot (two read locks, nothing cloned), and a test holds the two together across every state one live field can produce; a change to the definition goes in both.
- **The startup piece sweep claims what the *session records*, not what came up.** `BackendEngineFS::sweep_unadopted_pieces` deletes every directory under `<cacheRoot>/rqbit-downloads/.pieces` that nothing claims, and the claim set is three things: the restored engines, the dormant pins, and whatever librqbit's own persistence still names -- `session.json` plus the per-torrent `<infoHash>.bitv`/`.torrent` files in the persistence folder, read by `piece_store::session_recorded_hashes`. The third is not redundant and must not be dropped: a restore is allowed to fail (an output volume that is not mounted, a `.torrent` that will not parse, an add that errored), the failure says nothing about the data, and a claim set of "engines ∪ dormant pins" deletes that torrent's whole piece directory while `session.json` and its fastresume bitfield still point at it. Both persistence records are read because either can be the only one left: an unparseable `session.json` takes every claim in it with it, and a torrent added seconds before the process died has a session entry and no bitfield yet. Anything unreadable is a warning and no claim -- and that is only safe because the two records back each other up.
- **The cache cleaner covers one root -- walking what it owns and *asking the store* for the rest -- and protection is the only thing keeping a download** (`cache_cleaner::cache_roots` takes it from the engine -- `state.engine.download_dir` -- and never from `settings.cacheRoot`, since a running session cannot be moved onto a root set for the next start). There used to be a second walked root, the configured `downloadsDir`, and before that it was *pruned out* of the walk on the grounds that what is there is an offline download the user asked for; that stopped being right when downloads became piece files like everything else, because an old plain-file download is neither migrated nor read and, unwalked, would be orphaned *and* immortal. The whole of the root is covered to the bottom, in two halves. **The cleaner walks everything but `.pieces` and asks `piece_store::StoreRoot` what is in there** (`WalkInputs::walk_the_rest` prunes the store's subtree with `StoreRoot::holds`; `WalkInputs::ask_the_store` calls `StoreRoot::scan`). It used to walk the piece tree itself and `remove_file` what it found, which put the store's bucketed directory shape in the `server` crate as well as in `enginefs::piece_store` -- two copies of one decision, the second of which would have gone on "working" as a silent accounting error after the first changed. **What a pass reports freed is what left the disk, never what the walk promised** (`reclaim` returns the store's `delete_piece` answer and the two eviction rules count only on `Ok(true)`): nothing serialises passes -- `routes::stream` runs a whole `clean_cache` on the request task for every 507 while the background loop is in one -- so two passes routinely scan the same piece and only one can take it. A loser that books the bytes makes `EvictionReport::made_room()` true for a pass that freed nothing, `DiskFullRecovery` clears its exhausted set on that and restarts the ENOSPC torrents onto a disk that gained nothing, which is the restart loop the guard exists to stop -- and the same inflated total is what `LastEviction` hands the memory sampler as the cache's occupancy. The store's side of that bargain is that it only ever offers a piece a delete can reach: **every level of a piece's address is checked for the spelling the store writes, not for the number it parses to** (`piece_store::store::canonical_index`, taking neither a leading `+` nor leading zeroes, applied to the bucket directory and the file in it; `StoreRoot::scan` applies the same rule to a torrent directory's name, since `torrent_dir` lowercases). `<hash>/00/0`, `<hash>/0/00` and `<hash>/+0/0` all parse as piece 0 and no `delete_piece(hash, 0)` can take any of them, so they are strays -- counted, because they are occupying the volume, and never offered. A torrent's piece is now named to this crate as `Reclaimable::Piece { info_hash, piece }` and by nothing else: the cleaner cannot build its path and unlinks none of the store's files, so a piece and the staged half of a re-download over it go together (one `StoreRoot::delete_piece`, reported as one deletion) and a file the store does not recognise is *counted and left alone* -- it is on the disk, so it must show in the total, and only `piece_store::sweep` may say it is debris. What may not go is decided by `protected_torrents` alone: every live engine and every **dormant** pin, **by info hash rather than by path** (`EngineFS::protected_torrents`, one field of `EvictionClasses`, whose three classes are all `Vec<String>` now). It used to hand the cleaner `<cacheRoot>/rqbit-downloads/.pieces/<infoHash>` and have it match that against paths it had walked itself, which is the same duplication from the other end; a dormant pin used to have a second entry besides, under the removed `downloadsDir`, that never held one of its bytes. **An engine protects its pieces and nothing else**, and the "nothing else" is load-bearing rather than a simplification: it used to name the backend's `file_path` per file, which it had to while the session wrote whole files, and going on naming them now would hold the *superseded* whole-file copy of the engine's own data protected for as long as the torrent is in the session -- orphaned and immortal both, which is the exact failure that made the cleaner walk every root it is given in the first place. Since there is no migration, that copy is on disk on every existing install and the cleaner is the only thing that will ever reclaim it. The store's root is inside the cache root on purpose, so every piece in it is counted. **Deleting a piece behind librqbit's back is still the one thing that must not happen**, and this step did not move the interlock that stops it: it is `BackendEngineFS::delete_download_data`, which takes the `DroppedFilePieces` claim from `TorrentHandle::drop_file_pieces` and holds it across `StoreRoot::delete_pieces`. The cleaner's own reclaim does not hold such a claim yet -- routing it through `piece_store::policy` is the next step, and until then the cleaner must only be pointed at torrents nothing is reading (`protected` covers every live engine). Do not "optimise" the pinned-engine exemption away, and do not add a second walk root -- there is one torrent-data root, and anything that needs walking belongs under it. **Not every engine in the registry protects its files any more** (`EngineFS::eviction_classes`, of which `protected_torrents` is one field): an unpinned torrent in librqbit's error state for a reason *other* than space is `dead` — nothing restarts it, the error would recur — and its files are ordinary cache sorted to the *front* of the size rule; an unpinned torrent stopped *for* space (by the watch, or by `ENOSPC`) is `stopped_for_space`, listed whole and neither protected nor unlinked. The cleaner takes one of those only when a pass could free nothing else (age rule and size rule both empty-handed), and only through `EngineFS::evict_stopped_torrent` — torrent, files and piece map together, because a paused torrent holds its files open (an unlink frees no block) and a piece map that says it has them (a resume would read an empty file as data). Last, not first, on purpose: while anything else can go, evicting that is what lets the stopped torrent resume with its progress, which the recovery then does; once nothing else can, its bytes are what blocks the user's next stream, their retry of the same title included — on the television that prompted this three corpses held 700 MB "protected" and every later stream failed for it. The evicted hash is refused with `MagnetAddError::EvictedForSpace` (routes: `507`) for `EVICTED_FOR_SPACE_RETRY_AFTER`, because a player's reconnect and stremio-core's stats poll both re-add a hash within the second and would refill the disk the pass just emptied. **Both add paths enforce that window**, not just the magnet one: `EngineFS::add_torrent` (the `.torrent`-file path behind `/create`) asks `TorrentBackend::source_info_hash` for the hash *before* the add -- a backend add is already writing files by the time it could be asked what it added -- and returns the typed error inside its `anyhow` so the route can `downcast_ref` it to the same 507. A source whose hash cannot be known without fetching it (a `.torrent` behind an http URL) is added as before. A pinned torrent is protected however it stopped; an unpin is how the user gives the bytes up. **One root means one volume and one cap** (`CacheRoots::limit`): `cacheSize` against that volume's free space, keeping `CACHE_FREE_SPACE_FLOOR` back. What this replaced -- `budgets_by_volume`, `outermost`, `walk_within`/`CacheRoots::boundaries`, `EvictionReport::combined_with` -- existed because `downloadsDir` could put a second root on a second disk: a free-space cap is a statement about *one* volume, so the roots had to be grouped by volume before they were collapsed, each walk had to stop where another budget's root began (`WalkDir` crosses mount points), and the per-volume reports had to be folded into the one answer a client gets. With one root none of that has anything to describe. `remove_empty_parents` still stops at the root itself, which is configuration and not the cleaner's to remove, however empty eviction leaves it -- and it now runs only for the files the cleaner unlinked itself, since the bucket directories inside the store are the store's to prune (`TorrentStorage::remove_directory_if_empty`). `cache_cleaner::usage` reads the *same* `WalkInputs::run` a clean pass decides from, with `max_age: Duration::MAX` so nothing ages out; the separate read-only walk that used to mirror it is gone, and with it the risk of the two disagreeing about what the cache contains.
- **The shipped `btMaxConnections` is 160, which is 40 peers per torrent, and it applies live.** `TorrentSpeedProfile::effective_connection_limits` derives the per-torrent live-peer cap as `btMaxConnections / 4` clamped to 40..=200; the default was 800, which landed on the ceiling of 200. On the device this server is aimed at that is the wrong end: a peer costs ~75 KiB once buffers, task, channel and table entry are counted, so 200 of them are ~15 MB per torrent on a 2 GB television whose low-memory killer fires around 300 MB -- the same measurement that produced `LEAN_PEER_LIMIT` and `Footprint`. Lean already takes the *background* to 8; 40 is what the **foreground** wants, and `DEFAULT_BT_MAX_CONNECTIONS = 160` lands exactly on the floor, deliberately. A user who wants more still has it, up to `MAX_EFFECTIVE_BT_CONNECTIONS`. **The setting is `Live` in `bt_settings_support`, not `NextStart`**: `LibrqbitBackend::set_configured_peer_limit` puts the new cap on every torrent at once through the same `ManagedTorrent::set_peer_limit` the footprint uses, so lowering it hangs up on the surplus now and raising it re-queues the parked peers, with no restart and no progress lost. The footprint and the configured limit are one `Mutex<PeerCaps>` because they are one decision (`PeerCaps::limit()`) and either can change under the other -- under `Lean` a settings change only *stores* the new value, which is then what the return to `Full` restores, and it never prunes the peer table (only a footprint change does). `SessionOptions::peer_limit` is still what the session *opens* with, so never read the live cap off it; `SessionTuning::pending_restart` deliberately omits `btMaxConnections` for the same reason. Note the reach: the first run writes the default into `settings.json`, so an install that has been up since the 800 default keeps 800 -- nothing can tell that from a user who typed it, and rewriting a persisted setting behind their back is worse.
- **Lean mode shrinks, it does not stop -- and it keeps seeding.** `ServerHandle::set_background(true)` puts the torrent session on `enginefs::backend::Footprint::Lean` (`set_background(false)` = `Full`); the app calls it from its hidden/paused and resumed hooks. It exists because a 2 GB TV's low-memory killer took the backgrounded app twice at 311-379 MB RSS, and the measured attribution put the largest *and still growing* share on librqbit's peers: `peer_limit` 200 per torrent, each ~48 KiB of protocol buffers plus a task, a channel and a table entry, and a peer table that had retained 4224 addresses after one download. "Share between films" is a feature, so **what lean keeps is deliberate: every torrent stays live -- seeding goes on, a pinned download goes on -- nothing is paused, nothing on disk is touched, and a stream request that arrives while lean is served like any other (the embed test streams the head of a file while lean), just from fewer peers.** What it drops: the per-torrent live-peer cap goes to `LEAN_PEER_LIMIT` (8 -- a client uploads to four or five unchoked peers at a time and a home uplink saturates before that, so eight is the unchoke set with headroom for churn; the number is argued on the constant) and the surplus is hung up, least useful first (peers still connecting, then peers that have nothing we need and want nothing from us, fewest bytes exchanged first); and the peer table is pruned of every `Dead` and `NotNeeded` entry. **Only the `NotNeeded` half of that pruning is free** -- those are peers we hung up on, and the table kept them to remember not to dial them again -- while a `Dead` entry is the opposite, a peer waiting out a backoff *to be re-dialled*, and forgetting one cancels the reconnect: it comes back only when a tracker, the DHT or PEX names it again, or when it dials us. Both go anyway, because the table is the thing lean is shrinking (4224 addresses after one download, each with counters and backoff state) and a reconnect on a timer is the last thing a backgrounded app wants; the fork offers no state-filtered variant and asking for one would trade the larger half of the saving for reconnects we are trying not to make. The lever is the fork's, at the pinned rev: `ManagedTorrent::set_peer_limit` (runtime cap on the live state's peer semaphore; a lowered cap forgets permits as the parked peers return them, so the cap holds without a second pass; a raised cap re-queues the parked `NotNeeded` peers) and `TorrentStateLive::forget_disconnected_peers`. **The return to `Full` is not instant and the parked peers are not first**: `reconnect_all_not_needed_peers` pushes them onto the *tail* of the same FIFO queue every tracker/DHT/PEX address joins, so in the field they are dialled behind whatever backlog is waiting (in the cap's own tests there is no tracker and no DHT, so the queue is empty and they do come back at once -- which is what made the claim look true). It also re-queues every *other* `NotNeeded` outgoing peer, not only the ones the cap parked. Three things about the order are load-bearing. **Prune before lowering, never after**: the peers the lower cap parks are `NotNeeded` too, and pruned they are gone for good -- `Full` would have nobody to re-dial. **A repeated `Lean` is a no-op at the backend** (`LibrqbitBackend::set_footprint` returns early on the footprint it already has) for the same reason: a second prune would take the parked peers. And **an add reads and applies the footprint under the same mutex a change holds** while it walks the session's torrents, so a torrent added during a change ends with the footprint that won; a torrent that is not yet live takes the cap for when it is (`ManagedTorrentShared::peer_limit`). `PeerDiscovery::known` (additive in `stats.json`'s `peerDiscovery`) is the table's length -- the figure that shows the pruning; `seen`/`unique` is cumulative and never goes down. The Flutter/JNI half (calling this from the lifecycle hooks, pausing mpv, dropping the image cache) is the app's; `src/jni.rs` is untouched by this.
