# AGENTS.md

Guidance for AI coding agents working on this repository.

## What this repo is

Stream Server is a hard fork of an open-source Rust replacement for Stremio's closed-source `server.js`: a local HTTP torrent-streaming engine with archive streaming (RAR/ZIP/7Z/TAR/NZB) and a deliberately small control API — only what stremio-core's `StreamingServer` model calls (`/settings`, `/network-info`, `/device-info`, `/casting`, `/create`, `/{infoHash}/create`, the `stats.json` routes, `/get-https`) plus `/heartbeat` and `/stats.json`, and a **stub of the `/local-addon`** Stremio's default profile calls (`routes/local_addon.rs`: empty manifest, `{"streams": []}`, `{"metas": []}` for both catalog shapes core builds, `meta` → quiet 404, and its own fallback so anything else under the prefix is a debug-logged 404 rather than an ERROR-level unhandled request — kept so stock profiles show no error group, no failed catalog row and log no ERROR per details page; it serves nothing). Media routes and the local-addon stub are open; every control route requires a per-launch bearer token (`ServerAuth`, `server/src/auth.rs`), and everything a control route does is also a library method on `ServerHandle` so embedders need no HTTP client. The README's API section lists every surviving route with its OPEN/TOKEN status and the removed ones. Serves HTTP on **11470** and HTTPS on **12470** by default. **Source is MIT; default binaries are GPL-3.0-or-later** — see [Licensing](#licensing). Consumed by stremio-native (desktop) and stremio-android (JNI) today, and targeted at a new in-development Flutter + libmpv/media_kit client going forward.

This fork has deliberately dropped Stremio server.js API compatibility for transcoding: there is **no HLS transcoding and no FFmpeg/FFprobe integration** (no `hlsv2` route, no probe/hwaccel endpoints, no embedded-subtitle-track extraction) — that logic, and the `ffmpeg`/`ffprobe` runtime dependency it needed, has been removed. Clients are expected to direct-play and handle codecs/subtitles themselves.

**The entire build is pure Rust, with no opt-in native path at all**: `librqbit` is the sole, unconditional torrent backend, 7z is pure-Rust `sevenz-rust2`, and RAR is pure-Rust `unrar-rs` behind a default-on feature. `cargo build` / `cargo test` — with or without `--no-default-features` — always succeeds on a machine with **no** libclang, no fontconfig/gtk headers, no FFmpeg, and no libtorrent. The C++ `libtorrent` backend and its vcpkg build apparatus (the `libtorrent-sys` binding crate, `triplets/`, `vcpkg-overlays/`, `vcpkg.json`) have been removed entirely from this repo; there is nothing left here that pulls in a C or C++ toolchain for torrenting. The server is headless by design — no tray, no desktop GUI; graphical shells live in wrapper binaries in other repos.

## Licensing

The repo **source** is MIT (the `LICENSE` file is unchanged and must **stay MIT** — it contains no GPL code). But RAR support is **on by default** and uses the `unrar-rs` crate, which is **GPL-3.0-or-later**. That crate is only fetched at build time, yet linking it means a **default-built, distributed binary is GPL-3.0-or-later**. This is intentional: the owner wants RAR on by default and is releasing openly (iOS App Store is not a concern). MIT is GPL-compatible, so the MIT source shipping alongside GPL default binaries is fine. To build an **MIT binary without RAR**, use `--no-default-features` (RAR requests then return 501; the librqbit backend is not a feature, so it's not named here). Do **not** change the `LICENSE` file to GPL; document the situation instead.

## Workspace map

| Crate | Role |
|---|---|
| `server/` | axum HTTP API. `src/lib.rs` holds `ServerConfig` (incl. `auth: ServerAuth` and `torrent_listen_port: TorrentListenPort` — `Ephemeral` for `embedded()`, the fixed `42000..42010` range for `binary_default()`), `build_router()` — which merges `media_router()` (open) and `control_router()` (wrapped in the bearer middleware) — `build_lan_media_router()` — the optional LAN media listener's router: `lan_media_routes()` (an explicit allow-list, *not* `media_router()` itself — it excludes `/proxy` and `/ftp`, each an open proxy for an arbitrary caller-supplied remote URL) plus the fallbacks, no control routes at any level (`src/lan_media.rs` holds `LanMedia`, the start/stop control block on `AppState`; `ServerConfig::lan_media_addr` says where it binds, the `lanMediaEnabled` setting is the operator veto, and stopping **aborts the accept loop** -- the port is free at once, but a response already streaming runs to its end, so it is neither a drain nor a kill) — and the embeddable `ServerHandle` with its library API (`settings`, `update_settings`, `dht_status`, `engine_stats`, `file_stats`, `pin_download`, `unpin_download`, `downloads`, `download_path`, `auth_token`, `base_url`, `close_proxy_streams`, `proxy_streams_live`, `set_lan_media`, `lan_media_addr`, `lan_media_running`, `lan_media_requests_served`, `lan_media_base_url`; also a cdylib for Android JNI — see `src/jni.rs`). `src/auth.rs` is `ServerAuth` + the `require_bearer` middleware. `src/main.rs` is the headless daemon binary (`--tui` ratatui mode, `--no-auth` / `--token <t>` / `STREAM_SERVER_TOKEN` parsed by `parse_cli`, single-instance fslock). A generated token is printed to stdout only (`run()` in lib.rs, when `print_startup`) — it must never be passed to a `tracing` macro, since the log files (the append-only archive included) would keep it. `src/jni.rs` builds its config with `jni_config`, which sets `ServerAuth::Disabled`: the JNI call returns only a URL, so the Kotlin side could never receive a token, and the listener is loopback-only. `src/proxy_streams.rs` is the registry of proxied streams a player is reading, keyed by a token the *client* mints and carries in the `/proxy` URL (`p=`), so `POST /proxy-streams/{token}/close` (control) can end that player's read instead of leaving it to a `network-timeout` that is generous on purpose; a close makes the body error rather than end **and retires the token** -- a later `/proxy` request carrying it gets `410 Gone`, because ffmpeg's `reconnect=1` otherwise re-fetches through the same URL and playback carries on. The client's order is quit-then-close (a cancelled demuxer never reaches its reconnect), and it reaches only a wedge that is a blocked read. `src/routes/` has one file per API area (`routes/downloads.rs` holds the offline-download functions shared by `ServerHandle::{pin_download, unpin_download, downloads, download_path}` and the control routes `POST`/`DELETE /{infoHash}/{fileIdx}/download` and `GET /downloads.json`; a refused pin answers `PinDownloadError::client_message` only -- 404 bad index, 507 full disk, 504/502 failed magnet add; `settings.downloadsDir` is validated by `routes::system::prepare_downloads_dir` and pushed to the engines with `set_downloads_dir`). Also: `archives/` (RAR/ZIP/7Z/TAR/NZB sessions — 7z is pure-Rust `sevenz-rust2` in `archives/sevenz.rs`, always on; RAR is pure-Rust `unrar-rs` in `archives/rar.rs`, behind the default-on `rar` feature), `diagnostics/` (logging setup, crash handler, memory sampler, `dht_health` — no HTTP routes), `ssdp.rs`, `state.rs` (`AppState`). |
| `enginefs/` | Torrent engine abstraction. `src/backend/mod.rs` defines async traits `TorrentBackend`/`TorrentHandle`, `BackendConfig` (whose `listen_port: TorrentListenPort` — `Fixed(range)` tried in order, or `Ephemeral` = port 0 — is the one field librqbit consumes at session start), with a single implementation: `backend/librqbit.rs` (pure Rust, unconditional — there is no other backend to select), with `backend/dht_bootstrap.rs` resolving its DHT bootstrap names to address literals first). Plus `engine.rs`, piece/disk/metadata caches, tracker management/probing. Offline downloads: `BackendEngineFS::pin_download` (pin set on the `Engine`, unioned into every want-set plan; exempt from idle removal and the seeding pause; placed in `<downloads_dir>/<info hash>` via `TorrentPlacement`, relocating a torrent managed elsewhere through `TorrentBackend::relocate_torrent` -- for the length of the move the hash is parked in the magnet registry as an in-flight add (`PendingMagnetAdd::settled_later`, no abort handle, never swept) so lookups wait for the new engine instead of finding the dropped torrent; **the move itself runs detached, with a supervisor that settles it however it ends**, for `spawn_magnet_add`'s reason -- `pin_download`'s caller is an awaited axum handler and a cross-device copy is minutes of it, so left in the caller's future a client hanging up stopped the copy halfway, left the hash parked as an `Adding` entry nothing retries, and left `relocations` protecting both ends of the move for the life of the process, which is data the cleaner may never evict and nothing else names. `begin_relocation` is that detached task's own first act and `end_relocation` runs on every outcome of it, its panic included -- the record of what is protected and the removal of that record must stay on the same side of the spawn, or a hangup between them protects both trees forever; the per-hash pin lock goes with the move too (an owned guard handed to the supervisor), so an `unpin_download` issued after the requesting client has gone still queues behind it rather than deleting the tree being copied into; refused below `PIN_FREE_SPACE_MARGIN` of free space -- `PinDownloadError::client_message` is the only text of that error a route may put in a response body, like `MagnetAddError::client_message`; persisted in `<download_dir>/pinned-downloads.json` and restored at startup; pins the restore found no torrent for stay dormant, are listed by `dormant_pinned_downloads`, and come back with the torrent. `unpin_download(hash, idx, delete_files)` forgets the pin and, with `delete_files`, deletes the data too -- the whole torrent through `remove_torrent_and_files` when it was the last pin, otherwise just that file, since librqbit has no per-file delete and the torrent must keep running for its other pins; for a dormant pin, the `<downloads_dir>/<info hash>` folder, which nothing else would ever reclaim. It returns an `UnpinOutcome`, whose `deleted_files` is what actually left the disk -- never echo the request flag.) The librqbit session runs with `fastresume` (per-torrent `.bitv` bitfields in the persistence folder). |
| `stremio-runtime-stub/` | Zero-dep `stremio-runtime` shim binary: spawns the server with `--no-auth` (legacy clients speak plain HTTP and cannot send the bearer header; `REAL_SERVER_ARGS`), monitors it, waits for port 11470, prints the exact ready line legacy clients expect. |

There is no `bindings/` directory of any kind: the vendored 7-Zip and UnRAR C++ bindings were replaced long ago by the pure-Rust `sevenz-rust2` and `unrar-rs` crates (direct `server` dependencies), and the C++ `libtorrent-sys` FFI binding crate — the last native crate in the workspace — has since been removed too, along with the vcpkg overlays/triplets/baseline it needed. RAR is behind the default-on `rar` feature; 7z is always on.

`members` and `default-members` in the root `Cargo.toml` are now identical (`enginefs`, `server`, `stremio-runtime-stub`) — there is no native crate left to exclude from bare cargo invocations, so `--workspace` and the default set build the same thing.

## Build, test, lint

### Always verify these before committing — the whole build is pure Rust, no system deps for any feature combination

```bash
cargo build                 # debug; add --release for the optimized binary
cargo test
cargo fmt --all             # run before every commit; CI enforces --check
cargo clippy --all-targets -- -D clippy::correctness -D clippy::suspicious -W clippy::all
cargo run -p server         # http://localhost:11470
```

RAR is on by default (`unrar-rs`, `crypto-rust`) and is covered by the plain `cargo build`/`cargo test` above — it needs no system deps. Its escape hatch, `cargo build --no-default-features`, drops RAR (and links no GPL code) and must also keep building; RAR requests then return a 501 JSON error. There is no other feature combination to check: `librqbit` is unconditional, not a feature.

None. There is no runtime external-binary dependency at all.

## Conventions

- **Errors**: `anyhow` (`Result` + `.context()`) in application crates; `thiserror` for typed errors in `enginefs`.
- **Logging**: `tracing` macros only (no `println!` for diagnostics). Subscriber setup lives in `server`; HTTP tracing via tower-http `TraceLayer`. The one deliberate `println!` besides the startup lines is the generated auth token: secrets never go through `tracing` (the log files would keep them).
- **Async**: tokio multithreaded; `async-trait` for the backend traits; keep hot-path methods cheap (see `TorrentHandle::is_finished` doc comment — no full stats walks on stream-start). Blocking work (e.g. 7z decompression) goes through `spawn_blocking`.
- **Feature gating**: the only cargo feature left in this workspace is `rar` on `server` (`#[cfg(feature = "rar")]`, default-on, returning 501 when disabled). New *native/C* deps must be optional behind a feature, never in the default set; pure-Rust deps like `unrar-rs` (`crypto-rust`) may ship by default, subject to their license (see [Licensing](#licensing)). There is no backend feature to gate — `librqbit` is a plain unconditional dependency of `enginefs`.
- **Routes**: one file per API area in `server/src/routes/`, registered centrally in `build_router()` in `server/src/lib.rs`, which merges two sub-routers. **A new route goes in `control_router()` — token-protected — unless it serves media bytes to a player** (then `media_router()`, open, because players cannot send headers). The `/local-addon` stub is the one deliberate non-media open route (default profiles, legacy clients included, call it as an addon and it exposes nothing) — do not grow it into a real addon. Never add a token-in-query-string path; the bearer header is the only credential. Preserve exact endpoint paths/response shapes for the surface that remains — it mirrors the subset of Stremio's server.js API (camelCase serde) that stremio-core's `StreamingServer` model calls; do not resurrect removed server.js routes without a consumer (see the README's "Removed routes"). A route landing in `media_router()` is **not** automatically on the LAN media listener: that listener serves `lan_media_routes()` (`server/src/lib.rs`), a separate, explicit allow-list built from the same named route-group functions (`stream_routes`, `archive_routes`, `nzb_routes`, `local_addon_routes`) `media_router()` merges — so a new media route needs its group added to `lan_media_routes()` by name before the LAN can reach it, and the safe default for one that is not is exclusion. `/proxy` and `/ftp` are in `media_router()` (open, because players cannot send headers) but deliberately absent from `lan_media_routes()`: both fetch an arbitrary caller-supplied remote URL rather than serving bytes from this server, which makes either an open proxy for whoever can reach it — fine on loopback (only this host's own stremio-core can reach it), not fine handed to the whole LAN. See `server/src/lan_media.rs` and the README's "LAN media listener" section.
- **Library parity**: whatever a control route does must be reachable as a `ServerHandle` method sharing the same function (`routes::system::{engine_stats, file_stats, update_settings}` are the pattern); the embed test compares the two. Input normalisation belongs *inside* the shared function, not in the HTTP handler — the stats functions normalise their tracker list themselves (`compat::normalize_tracker_sources`) and the handlers hand them the raw `tr=` values, so a library caller cannot see different behaviour. Types crossing that boundary stay `serde`-serializable for FFI.
- **State**: `AppState` (Clone, Arc fields) in `server/src/state.rs`; DashMap for concurrent maps.
- **Platform code**: behind `cfg(target_os = ...)` with no-op stubs. Edition 2024 everywhere.
- **Tests**: inline `#[cfg(test)]` modules beside the code; integration test at `server/tests/embed.rs`, where requests to control routes go through `bearer_client(&handle)` (the default config generates a token). Every embedded server binds ephemeral ports for both HTTP (`http_addr` port 0) and librqbit (`ServerConfig::embedded()` sets `TorrentListenPort::Ephemeral`), so any number of server-spawning tests may run in parallel — still fold related assertions into one server where it reads naturally, but there is no port budget. Bare `cargo test` runs everything — there's no reduced default set to worry about.

  **Four ways a test passes here and fails on a CI runner** — three CI rounds went on these, so check every new test against all four:
  1. *Torrent file order.* `librqbit::create_torrent` walks a fixture directory with `walkdir` and never sorts, so a torrent's file indices are the filesystem's readdir order — on ext4 a per-filesystem name hash, different on every machine. Never hardcode an index that is coupled to a file's name, length or path; look it up with `backend::librqbit::torrent_file_index` (enginefs) or `file_index` (`server/tests/embed.rs`). The same goes for anything the *server* derives from the order, notably torrent-wide `phase`, which describes the guessed stream file — ask `/{infoHash}/{fileIdx}/stats.json` about the file you mean. And size fixture files as whole pieces (multiples of the 16 KiB piece length) unless the test is about a boundary piece, or which files share one depends on the order.
  2. *Path spellings.* `prepare_downloads_dir` stores and reports the **resolved** `downloadsDir`. An expectation built from a `TempDir` path must go through `stream_server::resolved_path` (the same `plain_path(canonical_prefix(..))` the server uses, exported doc-hidden for exactly this) — on Windows `TempDir` yields the 8.3 short name (`C:\Users\RUNNER~1\…`) and the server the long one, and on macOS `/var` is a symlink to `/private/var`. Reproduce it on Linux by running with `TMPDIR` pointed at a symlink to the real temp dir.
  3. *Sleeping instead of synchronising.* Nothing that waits on a spawned task, the blocking pool or the network may be sequenced with a fixed `sleep`. Use `#[tokio::test(start_paused = true)]` where the clock can be virtual, otherwise a bounded poll on observable state (`wait_until`, a `TEST_WAIT_BOUND` deadline). A bound is only there so a regression fails instead of hanging — keep it generous; a tight one is a timing assertion nobody meant to write.
  4. *`{:?}` on a path in an assertion needle.* `Debug` escapes the separator, so a `must not contain` check built that way is vacuous on Windows. Match the formatting the value under test actually used (see `a_torrent_error_reaches_the_client_without_the_server_paths`), or assert against both spellings.

  Fixtures also get a scratch root of their own (`fake_engine_root` in the enginefs tests), never a fixed path under `std::env::temp_dir()`: the tests run in parallel and a pin rewrites `pinned-downloads.json` in whatever root it was given.
- **Versions**: all crates share one version (bump in lockstep across every Cargo.toml).
- **Commits**: conventional style — `feat(scope):`, `fix(scope):`, `build:`, `ci:`, `docs:`, `chore:`.

### Agent model economy

Use the cheapest model adequate for the task at hand. Small/fast models are fine for mechanical edits, docs updates, renames, and enumeration; reserve strong models for architecture decisions, concurrency-sensitive code, and adversarial review. This is a standing instruction from the repo owner to conserve tokens/quota.

## Gotchas & do-not-touch

- **Do not casually edit**: the `.github/workflows/release.yml` build matrix and artifact/asset names (`scripts/generate_release_notes.py` and the release-notes step depend on the `release/*` filenames it produces); `server/Cargo.toml`'s `[package.metadata.deb]` and `[package.metadata.wix]` blocks (release-critical, and the WiX GUIDs must never be regenerated).
- **Contract strings**: `stremio-runtime-stub` depends on the literal ready line `EngineFS server started at http://127.0.0.1:11470` and port 11470 — changing startup output or default ports breaks legacy clients.
- **Release profile** (`panic = "abort"`, lto, opt-level=z, in the root `Cargo.toml`) means no unwinding in release — don't rely on `catch_unwind`.
- **Single instance**: the server takes a lockfile in the temp dir (`stream-server.lock`); a second desktop instance exits silently.
- **Magnet adds block inside librqbit**: `Session::add_torrent` for a magnet resolves metadata before returning, with no timeout of its own, and no torrent exists until then. enginefs runs every such add detached and bounded by `METADATA_RESOLVE_TIMEOUT` (90 s, const-asserted below `INACTIVE_TORRENT_REMOVE_TIMEOUT`) in a registry keyed by info hash. Routes that must answer promptly (stats/status) go through `EngineFS::get_or_begin_add_magnet` (non-blocking: `EngineLookup::Ready`/`Adding`/`Failed`) and report `EngineStats::resolving_metadata` or `EngineStats::magnet_add_failed`; routes that need the file list use `get_or_add_magnet`/`routes::compat::get_or_create_engine` (waits, joins an existing add, and is the only path that retries a failed one) and map the typed `MagnetAddError` with `compat::engine_creation_failure` (timeout → 504). A supervisor task settles the registry entry however the add ends (success removes it; error/timeout/abort — and a panic in debug builds; under the release profile's `panic = "abort"` a panic kills the process instead — turn it into a `FailedMagnetAdd` record), and the engine eviction loop sweeps entries nobody has looked up for the inactivity window. Never call `EngineFS::add_torrent` for a bare info hash from a route — `/{infoHash}/create` included. Trackers can only be supplied by the request that creates the engine (`LibrqbitHandle::add_trackers` is a documented no-op), so every creation path must pass the request's `tr=` trackers. For a magnet librqbit ignores `AddTorrentOptions::trackers` and reads only the link's own `tr=` params, so `LibrqbitBackend::add_torrent` folds the merged list into the magnet URL (`magnet_with_trackers`) — keep that when touching the add path.
- **The pin set is not optional state.** Any new want-set logic (`plan_only_files`, a new `Reconcile` branch, a smarter eviction policy) must union the engine's `pinned_files` in, and anything that drops or pauses torrents must skip an engine with `is_pinned()` -- the idle sweeper and the seeding-disabled pause already do. A pinned file that stops being wanted is a download that silently stalls, and a swept pinned engine loses the cache cleaner's protection with it. Pins are persisted, so the mistake survives restarts. The delete path is where this bites hardest: `unpin_download(.., delete_files = true)` validates `file_idx` against the file list *before* anything is removed (an index the torrent does not have would clear no pin, look like the last pin going, and take the whole torrent), and it drops the file from the playback bookkeeping before it reconciles, because the plan unions the active file back in and librqbit would keep writing through the handle it holds on an unlinked inode.
- **`/proxy` caches, and the cache is bounded by being ordinary cache.** `server/src/proxy_cache.rs` keeps whole 256 KiB chunks of a proxied response under `<download_dir>/.proxy`, beside the piece store and inside the cache root on purpose: the cleaner already walks that directory, so every cached byte is counted, aged and evicted per volume with **no change to `cache_roots` and nothing of it in `EngineFS::protected_paths`** -- keep it that way. Two traps sit either side of it. The root may not be named `.cache` or `.metadata`: `cache_cleaner::is_session_artifact` exempts *any* path with either component anywhere in it, and a cache that exempts itself from the cleaner is unbounded disk nobody counts. And nothing here may become protected: `is_path_protected` is `starts_with`, so one protected ancestor would shield the whole subtree, and a proxied stream nobody is reading is the first thing that should go. Eviction is per file, oldest mtime first, so it punches holes into the middle of a cached response -- that is intended, and every chunk is therefore read as independently absent. **Presence has to mean complete here, and unlike the piece store nothing outside the module can make it so** (there is no hash to check a URL's bytes against), so a chunk is held in memory until it is whole, written to a temporary name and renamed into place, and one whose length disagrees with its entity is read as absent; do not "optimise" that into a direct write. **Identity is the other half of that, and has the same reason.** An entity is filed under `<length>_<content type>_<validator>` and the validator is not optional: length and type say nothing about a URL whose content was replaced by content of the same size, and without it chunks of two generations land in one directory and a cached head is joined to a stranger's tail -- a body the player was told a coherent `Content-Range` about and that nothing anywhere could find out was wrong. So a response the origin will identify by neither `ETag` nor `Last-Modified` is not kept, the narrowed fetch asks `If-Range` under the validator, and the join happens only when the `206` names it again. Do not weaken any of the three into "the lengths match". The launch-time sweep (`proxy_cache::sweep`, called from `run` before the router serves) takes those temporaries and **nothing else** -- unlike the piece store's sweep, nothing claims a cached URL, every committed chunk is cache and surviving a restart is the whole point. The key is the target URL plus `h=` plus the forwarded player headers that are not about a range, computed from `routes::proxy::FORWARDED_REQUEST_HEADERS` rather than from a second list; `r=` and `p=` are deliberately out of it (`r=` never reaches the origin, and `p=` in the key would defeat two players sharing one stream). A credential in `h=` is refused, not keyed -- `/proxy` takes no bearer token, so it reuses `CREDENTIAL_REQUEST_HEADERS` rather than restating the credential rule, which has already failed as a discipline four times. A full cache hit is put through the same playlist classification (`routes::proxy::is_a_playlist`) a fetch is, before it answers -- that is what keeping `r=` out of the key rests on, and while the hit answered first the same URL was rewritten on a miss and relayed raw on a hit. **The doc says what it does not do -- nothing revalidated, no `Vary`, no coalescing -- and that list must stay honest**; the README repeats it, and three documents in this repo have already overclaimed. The one conditional this cache sends is that `If-Range`, and it is not revalidation: it rides on a fetch the player had asked for regardless.
- **The cache cleaner counts occupancy, never `metadata().len()`** (`cache_cleaner::occupied_bytes`): librqbit pre-allocates every wanted file at its full length, so the cache root is full of sparse files whose apparent size is the whole film. Counting `len()` reported 17 GB on a phone holding 3.85 GB and had the cleaner evicting against a limit the disk had never crossed. Unix uses `st_blocks * 512` (a POSIX unit, not the filesystem's block size); Windows falls back to the apparent length, since `std` exposes no cheap equivalent. The same rule already applies in enginefs to progress. A run yields an `EvictionReport`, and one that ends over the limit warns with the protected byte count rather than reporting a cleanup that did nothing. That warning is driven by `EvictionReport::over_limit` and never by `total` against `limit`: one pass is one report folded from every volume's, and summing both sides lets a roomy volume's slack cancel a full one's shortfall -- the client is told the pass got under the limit while the drive it cannot write to is over its own cap by exactly as much as before. Anything folded across volumes that has to answer "is one of them still stuck?" needs its own per-volume figure carried through the fold, as that field is. The debounced clean is armed by the first filesystem event only — re-arming on every event meant a torrent that keeps writing deferred it for the whole of playback.
- **The DHT is a peer source, not a requirement, and a dead one must stay quiet.** librqbit retries DHT bootstrap and UPnP forwarding *forever*, at WARN on every attempt (`crates/dht/src/dht.rs`'s `bootstrap_hostname_with_backoff`, `crates/upnp/src/lib.rs`'s discovery/`manage_port` loops), so a network that drops the DHT's UDP produced hundreds of identical warnings and no conclusion in a real field log. Both targets are therefore pinned to `error` in `DEFAULT_LOG_FILTER` (`server/src/lib.rs`) and the state is reported once instead, by `diagnostics::dht_health`: INFO when it comes up, ONE WARN after a 90 s grace if it has not, INFO if it recovers, everything else at debug. Do not re-raise those directives, and do not add bootstrap hosts to `DEFAULT_DHT_BOOTSTRAP_NODES` to "fix" a bootstrap failure: an earlier commit did exactly that and made things worse -- three of the five names it shipped resolve but answer 0/3 DHT pings, which is retry noise, not resilience. The list is now exactly the two names measured to answer (which is also librqbit's own default); `router.bittorrent.com` was kept a while on reputation and dropped once a re-probe from two networks had it answering nothing there either. A test asserts the list exactly, and **a host may only be added with a measured `ping` behind it**. The real fix for the field log was DNS: `backend/dht_bootstrap.rs` resolves the names itself (system resolver, then DNS over HTTPS, then a `dht-bootstrap.json` cache next to `dht.json`) and hands librqbit address literals, since `lookup_host` accepts them; whatever it cannot resolve stays a name so librqbit can keep trying. Both DHT files -- `dht.json` and `dht-bootstrap.json` -- are `is_session_artifact`s in `cache_cleaner.rs`, so the cache cleaner cannot evict the very state that exists to avoid the network. Both resolvers are injected (`BootstrapResolvers`) -- `BootstrapResolvers::offline()` is the no-DNS set every hermetic caller must use, and no test may hit a real resolver. That fixes the DNS half only; a network that drops the DHT's UDP is unaffected, and the doc comments say so. The observable state is `enginefs::backend::DhtStatus` (`ever_bootstrapped` is sticky on purpose), served as the `dht` key of `/stats.json` and as `ServerHandle::dht_status`; a client shows "DHT unavailable, using trackers only", not an error. Also note the librqbit fork's misleading message: `bootstrap_hostname` returns `v4.or(v6)`, so a v4 failure's error is *discarded* and what gets logged is the v6 branch's `NoSuccessfulLookups { errors: 0 }` for bootstrap hosts that have no `AAAA` record -- "0 errors" is an empty v6 address set, not proof that nothing was attempted.
- **UPnP port forwarding is only for a fixed listen port** (`TorrentListenPort::wants_upnp_forwarding`). `Ephemeral` -- what `ServerConfig::embedded()`, the Android JNI cdylib and every test use -- binds a different port each launch, so a mapping is worthless next time, and on Android SSDP discovery is multicast the app sandbox cannot send at all. The forwarder retries on an interval for the life of the process either way.
- **The startup piece sweep claims what the *session records*, not what came up.** `BackendEngineFS::sweep_unadopted_pieces` deletes every directory under `<cacheRoot>/.pieces` that nothing claims, and the claim set is three things: the restored engines, the dormant pins, and whatever librqbit's own persistence still names -- `session.json` plus the per-torrent `<infoHash>.bitv`/`.torrent` files in the persistence folder, read by `piece_store::session_recorded_hashes`. The third is not redundant and must not be dropped: a restore is allowed to fail (an output volume that is not mounted, a `.torrent` that will not parse, an add that errored), the failure says nothing about the data, and a claim set of "engines ∪ dormant pins" deletes that torrent's whole piece directory while `session.json` and its fastresume bitfield still point at it. Both persistence records are read because either can be the only one left: an unparseable `session.json` takes every claim in it with it, and a torrent added seconds before the process died has a session entry and no bitfield yet. Anything unreadable is a warning and no claim -- and that is only safe because the two records back each other up.
- **The cache cleaner walks `downloadsDir` too, and protection is the only thing keeping a download** (`cache_cleaner::cache_roots` puts it in `download_dirs`). It used to be pruned out of the walk on the grounds that what is there is an offline download the user asked for; that stopped being right when downloads became piece files like everything else, because an old plain-file download under `downloadsDir` is neither migrated nor read and, unwalked, would be orphaned *and* immortal. Everything handed to `evict`/`scan_usage` is now walked to the bottom, and what may not go is decided by `protected_paths` alone: live engines' files, `<downloadsDir>/<infoHash>` for every **dormant** pin (which has no engine to speak for it), the piece-store directory `<cacheRoot>/.pieces/<infoHash>` of both, and both ends of every relocation in flight (`EngineFS::protected_paths`). That last one is not optional either: `begin_relocation` takes the engine out of the registry before the backend moves a byte and the successor is only published when the copy is done, so for the length of a cross-device move -- minutes -- nothing else names the tree being written into or the tree being read out of. That last one names nothing today -- no torrent is handed a `PieceStoreFactory` yet -- and it is there so that the commit which wires the store in cannot forget it: the store's root is inside the cache root on purpose, so every piece in it is walked. Do not "optimise" the pinned-engine exemption away, and do not add a walk root without checking what in it is protected. The roots are grouped by volume (`budgets_by_volume`, over `enginefs::volume_id`) and **only then** collapsed to the outermost within each group (`cache_cleaner::outermost`), so a `downloadsDir` inside a cache root is one walk and not two -- while they share a volume. That order is not cosmetic: `prepare_downloads_dir` permits a `downloadsDir` *below* a cache root and on a desktop that dir is an external drive mounted there, so collapsing first threw the drive away as a root before anything asked which volume it was on, and its bytes were then walked and capped by the cache root's free space -- a cap about a volume they are not on, which is the one reading per-volume budgets exist to stop. Since roots on different volumes therefore survive nested, every walk stops where another budget's root begins (`walk_within`, `CacheRoots::boundaries`): `WalkDir` crosses mount points by default and a walk that crossed would count and evict the other volume's files against this one's cap all over again. What survives the collapse is not a sufficient stop condition for `remove_empty_parents` either -- it prunes up to the directories the cleaner was *given* (`CacheRoots::keep_dirs`), or it would delete the configured `downloadsDir` the moment eviction emptied it. Each volume gets its own cap: a free-space cap is a statement about a volume, and one budget summing every root's occupancy against the tightest free-space reading of all of them evicts a healthy disk's cache to answer a shortage on a disk it can reclaim nothing from. Normally there is one volume and one budget, and nothing about the pass changes. `routes::system::prepare_downloads_dir` still refuses one *at or above* a cache root, now because the roots the cleaner walks are the roots it evicts from and one above the cache root would hand it a tree the engines do not own.
- The `server` crate is also a **cdylib consumed over JNI** by stremio-android — keep `src/jni.rs` symbol names (`Java_com_stremio_mobile_server_...`) and `ServerConfig::embedded()` semantics stable. (`embedded()` binds an ephemeral BitTorrent listen port — an embedder that needs a fixed, forwardable one sets `torrent_listen_port: TorrentListenPort::Fixed(..)` itself.)
