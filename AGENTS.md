# AGENTS.md

Guidance for AI coding agents working on this repository.

## What this repo is

Stream Server is a hard fork of an open-source Rust replacement for Stremio's closed-source `server.js`: a local HTTP torrent-streaming engine with archive streaming (RAR/ZIP/7Z/TAR) and a deliberately small control API — only what stremio-core's `StreamingServer` model calls (`/settings`, `/network-info`, `/device-info`, `/casting`, `/create`, `/{infoHash}/create`, the `stats.json` routes, `/get-https`) plus `/heartbeat` and `/stats.json`, and a **stub of the `/local-addon`** Stremio's default profile calls (`routes/local_addon.rs`: empty manifest, `{"streams": []}`, `{"metas": []}` for both catalog shapes core builds, `meta` → quiet 404, and its own fallback so anything else under the prefix is a debug-logged 404 rather than an ERROR-level unhandled request — kept so stock profiles show no error group, no failed catalog row and log no ERROR per details page; it serves nothing). Media routes and the local-addon stub are open; every control route requires a per-launch bearer token (`ServerAuth`, `server/src/auth.rs`), and everything a control route does is also a library method on `ServerHandle` so embedders need no HTTP client. The README's API section lists every surviving route with its OPEN/TOKEN status and the removed ones. Serves HTTP on **11470** and HTTPS on **12470** by default. **Source is MIT; default binaries are GPL-3.0-or-later** — see [Licensing](#licensing). Consumed by stremio-native (desktop) and stremio-android (JNI) today, and targeted at a new in-development Flutter + libmpv/media_kit client going forward.

This fork has deliberately dropped Stremio server.js API compatibility for transcoding: there is **no HLS transcoding and no FFmpeg/FFprobe integration** (no `hlsv2` route, no probe/hwaccel endpoints, no embedded-subtitle-track extraction) — that logic, and the `ffmpeg`/`ffprobe` runtime dependency it needed, has been removed. Clients are expected to direct-play and handle codecs/subtitles themselves.

**The entire build is pure Rust, with no opt-in native path at all**: `librqbit` is the sole, unconditional torrent backend, 7z is pure-Rust `sevenz-rust2`, and RAR is pure-Rust `unrar-rs` behind a default-on feature. `cargo build` / `cargo test` — with or without `--no-default-features` — always succeeds on a machine with **no** libclang, no fontconfig/gtk headers, no FFmpeg, and no libtorrent. The C++ `libtorrent` backend and its vcpkg build apparatus (the `libtorrent-sys` binding crate, `triplets/`, `vcpkg-overlays/`, `vcpkg.json`) have been removed entirely from this repo; there is nothing left here that pulls in a C or C++ toolchain for torrenting. The server is headless by design — no tray, no desktop GUI; graphical shells live in wrapper binaries in other repos.

## Licensing

The repo **source** is MIT (the `LICENSE` file is unchanged and must **stay MIT** — it contains no GPL code). But RAR support is **on by default** and uses the `unrar-rs` crate, which is **GPL-3.0-or-later**. That crate is only fetched at build time, yet linking it means a **default-built, distributed binary is GPL-3.0-or-later**. This is intentional: the owner wants RAR on by default and is releasing openly (iOS App Store is not a concern). MIT is GPL-compatible, so the MIT source shipping alongside GPL default binaries is fine. To build an **MIT binary without RAR**, use `--no-default-features` (RAR requests then return 501; the librqbit backend is not a feature, so it's not named here). Do **not** change the `LICENSE` file to GPL; document the situation instead.

The client's order is quit-then-close (a cancelled demuxer never reaches its reconnect), and it reaches only a wedge that is a blocked read. `src/routes/` has one file per API area (`routes/downloads.rs` holds the offline-download functions shared by `ServerHandle::{pin_download, unpin_download, downloads, download_path}` and the control routes `POST`/`DELETE /{infoHash}/{fileIdx}/download` and `GET /downloads.json`; a refused pin answers `PinDownloadError::client_message` only -- 404 bad index, 507 full disk, 504/502 failed magnet add; `settings.cacheRoot` is the one torrent-data root, validated by `routes::system::prepare_torrent_data_root` and prepared at startup *before* the session opens on it -- it replaced `downloadsDir`, which was a second location for pinned downloads; a client that still sends that key gets what it gets for any unknown key, nothing). The session map is an `archives::sessions::Sessions`, which sweeps a session `SESSION_IDLE_TIMEOUT` after its last lease — a route keeps the lease inside the response body — and dropping a session releases what it owned: the downloaded file and extracted members (`archives::source`, one `ProgressiveCache` per member, shared by every request on it, and its writers give up after `cache::ABANDONED_AFTER` with no reader). Everything the archive routes write goes under `<cache root>/.archives`, never the system temp dir, so it lands on the volume this server counts and caps; every file there is a `NamedTempFile` the session owns, so the idle sweep taking the session is what unlinks it), `diagnostics/` (logging setup, crash handler, memory sampler, `dht_health` — no HTTP routes), `ssdp.rs`, `state.rs` (`AppState`). |
| `enginefs/` | Torrent engine abstraction. `src/backend/mod.rs` defines async traits `TorrentBackend`/`TorrentHandle`, `BackendConfig` (whose `listen_port: TorrentListenPort` — `Fixed(range)` tried in order, or `Ephemeral` = port 0 — is the one field librqbit consumes at session start), with a single implementation: `backend/librqbit.rs` (pure Rust, unconditional — there is no other backend to select), with `backend/dht_bootstrap.rs` resolving its DHT bootstrap names to address literals first). Plus `engine.rs`, `retention.rs` (the retention policy's driver and the one have-set interlock -- see the bullet below), piece/disk/metadata caches, tracker management/probing, and `traffic.rs` (the window that turns the torrents' peer counters into the client's activity signal -- see the bullet below). Offline downloads: `BackendEngineFS::pin_download` (pin set on the `Engine`, unioned into every want-set plan; exempt from idle removal and the seeding pause; **a retention property and never a location** -- see the bullet below -- so a torrent that was streamed first is pinned where it already is, with the engine every open reader holds; a torrent the pin has to add is added like any other, with a `TorrentPlacement` that is now a want-set and nothing more; refused below `PIN_FREE_SPACE_MARGIN` of free space on the store's volume -- `PinDownloadError::client_message` is the only text of that error a route may put in a response body, like `MagnetAddError::client_message`; a refused pin drops the torrent *its own add* created (`started_here && joiners == 0 && !is_pinned && !torrent_activity_registers(..)` -- never one a stream request joined, whose reader is about to open, and never one anybody is on **now**: `joiners` counts who joined the *pending add* and the engine is published before the preconditions are checked, so a stream that opens across `file_count()`/`stats()`/the free-space probe joins nothing and is invisible to it; the live registers are the only thing that sees it) and takes no byte with it, since the refusal precedes any download and what the store holds was fetched by somebody else; not persisted here at all -- the embedder keeps the set and hands it back at the next startup (`ServerConfig::pins`, applied by `BackendEngineFS::apply_pins`); pins that found no torrent stay dormant for the run, are listed by `dormant_pinned_downloads`, and come back with the torrent. `unpin_download(hash, idx, delete_files)` forgets the pin and, with `delete_files`, deletes the data too -- the whole torrent through `remove_torrent_and_files` when it was the last pin, otherwise just that file, since librqbit has no per-file delete and the torrent must keep running for its other pins; for a dormant pin, its directory in the piece store, which nothing else would reclaim while the pin protects it -- but only after the session has been asked whether "dormant" is even true (see the placement bullet). It returns an `UnpinOutcome`, whose `deleted_files` is what actually left the disk -- never echo the request flag, and never read "already absent" as "freed".) The librqbit session runs with `fastresume` (per-torrent `.bitv` bitfields in the persistence folder). **The `bt*` settings reach librqbit through one place**: `LibrqbitBackend::new_with_settings` takes a `SessionTuning` (what `SessionTuning::from_settings` can express of the speed profile and privacy config -- DHT on/off, LSD, a SOCKS5 proxy URL, the download limit, the per-torrent peer limit, one bind device), `update_torrent_settings` applies the download limit live and returns a `BtSettingsReport` naming what applied, what waits for the next start and what is never honoured, and `bt_settings_support()` is the row-per-setting truth table a test keeps complete; a setting without a librqbit knob is listed there as `NotHonoured` with the reason, never wired to something that merely resembles it. |
| `stremio-runtime-stub/` | Zero-dep `stremio-runtime` shim binary: spawns the server with `--no-auth` (legacy clients speak plain HTTP and cannot send the bearer header; `REAL_SERVER_ARGS`), monitors it, waits for port 11470, prints the exact ready line legacy clients expect. |

There is no `bindings/` directory of any kind: the vendored 7-Zip and UnRAR C++ bindings were replaced long ago by the pure-Rust `sevenz-rust2` and `unrar-rs` crates (direct `server` dependencies), and the C++ `libtorrent-sys` FFI binding crate — the last native crate in the workspace — has since been removed too, along with the vcpkg overlays/triplets/baseline it needed. cargo fmt --all             # run before every commit; CI enforces --check

## Conventions

- **Errors**: `anyhow` (`Result` + `.context()`) in application crates; `thiserror` for typed errors in `enginefs`.
- **Logging**: `tracing` macros only (no `println!` for diagnostics). Subscriber setup lives in `server`; HTTP tracing via tower-http `TraceLayer`. The one deliberate `println!` besides the startup lines is the generated auth token: secrets never go through `tracing` (the log files would keep them).
- **Async**: tokio multithreaded; `async-trait` for the backend traits; keep hot-path methods cheap (see `TorrentHandle::is_finished` doc comment — no full stats walks on stream-start). Blocking work (e.g. 7z decompression) goes through `spawn_blocking`.
- **Feature gating**: the only cargo feature left in this workspace is `rar` on `server` (`#[cfg(feature = "rar")]`, default-on, returning 501 when disabled). New *native/C* deps must be optional behind a feature, never in the default set; pure-Rust deps like `unrar-rs` (`crypto-rust`) may ship by default, subject to their license (see [Licensing](#licensing)). There is no backend feature to gate — `librqbit` is a plain unconditional dependency of `enginefs`.
- **Routes**: one file per API area in `server/src/routes/`, registered centrally in `build_router()` in `server/src/lib.rs`, which merges two sub-routers. **A new route goes in `control_router()` — token-protected — unless it serves media bytes to a player** (then `media_router()`, open, because players cannot send headers). The `/local-addon` stub is the one deliberate non-media open route (default profiles, legacy clients included, call it as an addon and it exposes nothing) — do not grow it into a real addon. Never add a token-in-query-string path; the bearer header is the only credential. Preserve exact endpoint paths/response shapes for the surface that remains — it mirrors the subset of Stremio's server.js API (camelCase serde) that stremio-core's `StreamingServer` model calls; do not resurrect removed server.js routes without a consumer (see the README's "Removed routes"). A route landing in `media_router()` is **not** automatically on the LAN media listener: that listener serves `lan_media_routes()` (`server/src/lib.rs`), a separate, explicit allow-list of exactly what a cast receiver needs — the byte-serving halves only (`lan_stream_routes`, `archive_stream_routes`), over torrents and sessions the loopback side already created — so a new media route needs its group added to `lan_media_routes()` by name before the LAN can reach it, and the safe default for one that is not is exclusion. The test of belonging there is that a stranger on the network cannot make this device *do* anything through it: `/proxy` and `/ftp` fetch an arbitrary caller-supplied remote URL (an open proxy for whoever can reach it); the archive `/create` routes download a caller-named archive; and the loopback `stream_routes` create a torrent, with the caller's `tr=` trackers, on the first request for a hash — so the LAN mounts `routes::stream::{lan_stream_video, lan_head_stream_video}` (`EngineAccess::ExistingOnly`: an unknown hash is a `404`, `tr=` is ignored, no magnet add is started or joined). All of that is fine on loopback (only this host's own stremio-core can reach it), not fine handed to the whole LAN. See `server/src/lan_media.rs` and the README's "LAN media listener" section.
- **Library parity**: whatever a control route does must be reachable as a `ServerHandle` method sharing the same function (`routes::system::{engine_stats, file_stats, update_settings}` are the pattern); the embed test compares the two. Input normalisation belongs *inside* the shared function, not in the HTTP handler — the stats functions normalise their tracker list themselves (`compat::normalize_tracker_sources`) and the handlers hand them the raw `tr=` values, so a library caller cannot see different behaviour. Types crossing that boundary stay `serde`-serializable for FFI.
- **State**: `AppState` (Clone, Arc fields) in `server/src/state.rs`; DashMap for concurrent maps.
- **Platform code**: behind `cfg(target_os = ...)` with no-op stubs. Edition 2024 everywhere.
- **Tests**: inline `#[cfg(test)]` modules beside the code; integration test at `server/tests/embed.rs`, where requests to control routes go through `bearer_client(&handle)` (the default config generates a token). Every embedded server binds ephemeral ports for both HTTP (`http_addr` port 0) and librqbit (`ServerConfig::embedded()` sets `TorrentListenPort::Ephemeral`), so any number of server-spawning tests may run in parallel — still fold related assertions into one server where it reads naturally, but there is no port budget. Bare `cargo test` runs everything — there's no reduced default set to worry about.

  **Five ways a test passes here and fails on a CI runner** — four CI rounds went on these, so check every new test against all five:
  1. *Torrent file order.* `librqbit::create_torrent` walks a fixture directory with `walkdir` and never sorts, so a torrent's file indices are the filesystem's readdir order — on ext4 a per-filesystem name hash, different on every machine. Never hardcode an index that is coupled to a file's name, length or path; look it up with `backend::librqbit::torrent_file_index` (enginefs) or `file_index` (`server/tests/embed.rs`). The same goes for anything the *server* derives from the order, notably torrent-wide `phase`, which describes the guessed stream file — ask `/{infoHash}/{fileIdx}/stats.json` about the file you mean. And size fixture files as whole pieces (multiples of the 16 KiB piece length) unless the test is about a boundary piece, or which files share one depends on the order.
  2. *Path spellings.* `prepare_torrent_data_root` stores and reports the **resolved** `cacheRoot`. An expectation built from a `TempDir` path must go through `stream_server::resolved_path` (the same `plain_path(canonical_prefix(..))` the server uses, exported doc-hidden for exactly this) — on Windows `TempDir` yields the 8.3 short name (`C:\Users\RUNNER~1\…`) and the server the long one, and on macOS `/var` is a symlink to `/private/var`. Reproduce it on Linux by running with `TMPDIR` pointed at a symlink to the real temp dir.
  3. *Sleeping instead of synchronising.* Nothing that waits on a spawned task, the blocking pool or the network may be sequenced with a fixed `sleep`. Use `#[tokio::test(start_paused = true)]` where the clock can be virtual, otherwise a bounded poll on observable state (`wait_until`, a `TEST_WAIT_BOUND` deadline). A bound is only there so a regression fails instead of hanging — keep it generous; a tight one is a timing assertion nobody meant to write.
  4. *`{:?}` on a path in an assertion needle.* `Debug` escapes the separator, so a `must not contain` check built that way is vacuous on Windows. Match the formatting the value under test actually used (see `a_torrent_error_reaches_the_client_without_the_server_paths`), or assert against both spellings.
  5. *Waiting for a peer to actually connect.* A bounded wait on a real peer connection is a bet on the runner's network stack, and the Windows runner lost it: a dozen loopback seeder sessions dialling an embedded server's librqbit listener produced `peers=0` after 120 s, run after run, so the test's own precondition — a swarm bigger than the cap — could not be met there at all. Peer-dependent assertions belong in the enginefs tests, which dial *out* to addresses they were handed (`lean_parks_the_surplus_and_full_re_dials_it`); everything else — a footprint, a cap, bytes served from data already on disk — is provable with no peer, which is what the embed suite does (`set_background_caps_the_torrent_and_still_streams`). A test that cannot make its point without a swarm should be one of the enginefs ones, not a second copy in `embed.rs`.

  Fixtures also get a scratch root of their own (`fake_engine_root` in the enginefs tests), never a fixed path under `std::env::temp_dir()`: the tests run in parallel and every fixture's torrent is `TEST_HASH`, so a shared root is one test writing and unlinking the piece files another is asserting on.
- **Versions**: all crates share one version (bump in lockstep across every Cargo.toml).
- **Commits**: conventional style — `feat(scope):`, `fix(scope):`, `build:`, `ci:`, `docs:`, `chore:`.

### Agent model economy

Use the cheapest model adequate for the task at hand. Small/fast models are fine for mechanical edits, docs updates, renames, and enumeration; reserve strong models for architecture decisions, concurrency-sensitive code, and adversarial review. This is a standing instruction from the repo owner to conserve tokens/quota.

## Gotchas & do-not-touch

- **Do not casually edit**: the `.github/workflows/release.yml` build matrix and artifact/asset names (`scripts/generate_release_notes.py` and the release-notes step depend on the `release/*` filenames it produces); `server/Cargo.toml`'s `[package.metadata.deb]` and `[package.metadata.wix]` blocks (release-critical, and the WiX GUIDs must never be regenerated).
- **Contract strings**: `stremio-runtime-stub` depends on the literal ready line `EngineFS server started at http://127.0.0.1:11470` and port 11470 — changing startup output or default ports breaks legacy clients.
- **Release profile** (`panic = "abort"`, lto, opt-level=z, in the root `Cargo.toml`) means no unwinding in release — don't rely on `catch_unwind`.
- **Single instance**: the server takes a lockfile in the temp dir (`stream-server.lock`); a second desktop instance exits silently.
- **Magnet adds block inside librqbit**: `Session::add_torrent` for a magnet resolves metadata before returning, with no timeout of its own, and no torrent exists until then. enginefs runs every such add detached and bounded by `METADATA_RESOLVE_TIMEOUT` (90 s, const-asserted below `INACTIVE_TORRENT_REMOVE_TIMEOUT`) in a registry keyed by info hash. Routes that must answer promptly (stats/status) go through `EngineFS::get_or_begin_add_magnet` (non-blocking: `EngineLookup::Ready`/`Adding`/`Failed`) and report `EngineStats::resolving_metadata` or `EngineStats::magnet_add_failed`; routes that need the file list use `get_or_add_magnet`/`routes::compat::get_or_create_engine` (waits, joins an existing add, and is the only path that retries a failed one) and map the typed `MagnetAddError` with `compat::engine_creation_failure` (timeout → 504). A supervisor task settles the registry entry however the add ends (success removes it; error/timeout/abort — and a panic in debug builds; under the release profile's `panic = "abort"` a panic kills the process instead — turn it into a `FailedMagnetAdd` record), and the engine eviction loop sweeps entries nobody has looked up for the inactivity window. Never call `EngineFS::add_torrent` for a bare info hash or a magnet link from a route — `/{infoHash}/create` included, and `/create`'s `from`, which sorts a magnet out (`routes::engine::CreateSource`) before the torrent-file case reaches `add_torrent`. Trackers can only be supplied by the request that creates the engine (`LibrqbitHandle::add_trackers` is a documented no-op), so every creation path must pass the request's `tr=` trackers. For a magnet librqbit ignores `AddTorrentOptions::trackers` and reads only the link's own `tr=` params, so `LibrqbitBackend::add_torrent` folds the merged list into the magnet URL (`magnet_with_trackers`) — keep that when touching the add path.
- **The pin set is not optional state.** Any new want-set logic (`plan_only_files`, a new `Reconcile` branch, a smarter eviction policy) must union the engine's `pinned_files` in, and anything that drops or pauses torrents must skip an engine with `is_pinned()` -- the idle removal and the ladder's bottom arm already do, and the free-space arm is the one deliberate exception. A pinned file that stops being wanted is a download that silently stalls, and a swept pinned engine loses the cache cleaner's protection with it. The embedder hands the same pins back at the next boot, so the mistake survives restarts. The delete path is where this bites hardest: `unpin_download(.., delete_files = true)` validates `file_idx` against the file list *before* anything is removed (an index the torrent does not have would clear no pin, look like the last pin going, and take the whole torrent), and it drops the file from the playback bookkeeping before it reconciles, because the plan unions the active file back in and librqbit would keep writing through the handle it holds on an unlinked inode. **The bytes are one record of a file and librqbit's have-set is the other**, so the per-file delete asks `TorrentHandle::drop_file_pieces` (librqbit's `drop_pieces`) before it truncates, holds the returned claim until the unlink is done, and the claim's release re-selects the boundary piece the still-pinned neighbour shares. **`drop_pieces` frees no byte** -- it is have-set bookkeeping and hands the indices back precisely so the caller can delete them -- so the delete takes two things: those pieces out of the store (`piece_store::delete_pieces`), and the whole-file copy at the backend's path if an earlier version left one there. Miss the first and the client is told the disk came back while every piece of the file is still in a directory the pin protects, which nothing would ever reclaim. `deleted_files` is therefore "bytes actually left the disk" and **not** "the path is absent": under this storage the path is always absent, so the old "NotFound counts as deleted" would have made the flag a constant true. Without it librqbit kept reporting the deleted file complete, advertised its pieces, and a re-pin downloaded nothing. But `drop_pieces` needs `piece_reclaim`, and at the pinned librqbit rev `Session::add_torrent` refuses that option on a storage that cannot release a single piece -- so `LibrqbitBackend` sets it only when the session's storage can (`session_can_release_pieces`, decided once when the session opens, and asked of the factory rather than assumed from its type). **The shipped session's default storage is the piece store, one file per piece, and releasing a piece is deleting its file -- so `piece_reclaim` is on for every add**, `drop_file_pieces` works, and the per-file delete's claim really does re-select the boundary piece the still-pinned neighbour shares. It was off for as long as the session ran on librqbit's own whole-file filesystem storage, and the degradation it had then is still the code's fallback for a backend whose storage cannot release: `drop_file_pieces` is refused by name and logged, the bytes still go, and the next restart's fastresume validation -- one hash-checked piece per claimed file -- catches the empty file and re-checks the torrent from disk. `piece_reclaim` is persisted with the torrent, and the price of it being on is paid at every startup: **librqbit restores every torrent paused**, because the piece-level want-set is not in the record, and nothing but the reconciler starts one again -- after `apply_pins` has put the want-set back and marked each restored engine settled (`reconcile::Conditions::settled`). A change that skips or reorders that is a restart that comes up downloading and seeding nothing.
- **`/proxy` caches, and one retention policy bounds it.** `server/src/proxy_cache.rs` keeps whole 256 KiB chunks of a proxied response under `<download_dir>/.proxy`, beside the piece store and inside the cache root on purpose: it is the one torrent-data root, so every cached byte is counted in the one usage figure and capped by the one published budget -- keep it that way. Its own owner is the only thing that ever deletes from it; only `.pieces` is asked for rather than walked. Two traps sit either side of it. The root may not be named `.cache` or `.metadata`: those were the two components the old cache cleaner's walk exempted as session records, and a cache that exempts itself is unbounded disk nobody counts. And nothing here may become protected by *place*: protection is a question asked of the retention policy, and the two answers that keep a proxy chunk are that a player is inside its window right now and that an open body has been framed to deliver it and has not yet (`retention::ReclaimGate::releases_file`, fed by `proxy_retention::ProxyRetention::fill_gate`, which inserts both) -- a proxied stream nobody is reading is still the first thing that should go, and what it leaves behind is forgotten once no reader is open on it and `IDLE` has passed since its last delivered byte. (`is_path_protected`, the `starts_with` match that used to shield a whole subtree from one protected ancestor, is gone with the paths it matched.) Eviction is otherwise per file, oldest mtime first, so it punches holes into the middle of a cached response -- that is intended, and every chunk is therefore read as independently absent. **The bytes themselves are the one chunk store's** (`enginefs::chunk_store::ChunkDir`, the same store the torrent pieces are in): the directory shape, the bucketing, the two staging spellings, the rename that makes presence mean complete, the typed read, the listings and the occupancy are written down once and `proxy_cache` is an *adapter* over them -- the key, the entity, the refusals, and `offset / CHUNK` where a torrent has a file table with padding in it. Two things about the store differ between the two adapters and both are parameters of it: a `/proxy` chunk is staged **anonymously** (`ChunkDir::write_whole`, so two uncoalesced fillers of one chunk touch no name the other could hold, where librqbit's staged piece is addressable and resumable), and **completeness has to be established internally here, since there is no hash to check a URL's bytes against** -- a chunk is held in memory until it is whole, that expected byte count is handed to the store as the commit criterion (a torrent piece passes `None`, because librqbit never writes padding and a padded piece commits *short*), and one whose length disagrees with its entity is refused at the read and deleted, never served (`Cached::body` is the one place a chunk's length is checked; the lookup lists bucket directories and goes by name); do not "optimise" that into a direct write. **Identity is the other half of that, and has the same reason.** An entity is filed under `<length>_<content type>_<validator>` and the validator is not optional: length and type say nothing about a URL whose content was replaced by content of the same size, and without it chunks of two generations land in one directory and a cached head is joined to a stranger's tail -- a body the player was told a coherent `Content-Range` about and that nothing anywhere could find out was wrong. So a response the origin will identify by neither `ETag` nor `Last-Modified` is not kept, the narrowed fetch asks `If-Range` under the validator, and the join happens only when the `206` names it again. Do not weaken any of the three into "the lengths match". The launch-time sweep (`proxy_cache::sweep`, called from `run` before the router serves anything) **empties the root**: every entity directory, every committed chunk, every stray file under it. Nothing claims a cached URL across a restart -- a proxied entity is kept only while something is playing it, and a process that has served nothing is playing nothing -- so every byte here belongs to a playback that ended with the last process and no owner in this one would ever count it or reclaim it. That is also what makes `proxy_retention::ProxyRetention::occupancy`, a running count of what *this* process wrote, true from the first byte. The key is the target URL plus `h=` plus the forwarded player headers that are not about a range, computed from `routes::proxy::FORWARDED_REQUEST_HEADERS` rather than from a second list; `r=` and `p=` are deliberately out of it (`r=` never reaches the origin, and `p=` in the key would defeat two players sharing one stream). A credential in `h=` is refused, not keyed -- `/proxy` takes no bearer token, so it reuses `CREDENTIAL_REQUEST_HEADERS` rather than restating the credential rule, which has already failed as a discipline four times. **Every** cache hit is put through the same playlist classification (`routes::proxy::is_a_playlist`) a fetch is -- whole or partial, before it answers *and* before a fetch is narrowed against it -- and a hit whose verdict is "playlist" steps aside whole, leaving the player's own range to go to the origin unnarrowed. That is what keeping `r=` out of the key rests on, and it has been got wrong at both ends: while a full hit answered first the same URL was rewritten on a miss and relayed raw on a hit, and while a partial hit narrowed first it came back as a raw unrewritten `206` of the tail alone. Write "every hit" or write nothing here: the qualified form is what let four documents say two different things about one rule. **The doc says what it does not do -- nothing revalidated, no `Vary`, no coalescing -- and that list must stay honest**; the README repeats it, and three documents in this repo have already overclaimed. The one conditional this cache sends is that `If-Range`, and it is not revalidation: it rides on a fetch the player had asked for regardless.
- **Occupancy is counted, never `metadata().len()`** (`enginefs::chunk_store::occupied_bytes`, the one copy of that arithmetic): librqbit's *filesystem* storage pre-allocates every wanted file at its full length, so the cache root is full of sparse files whose apparent size is the whole film. The session runs on the piece store now and writes nothing sparse, but the rule stays: the roots are still full of what earlier versions pre-allocated (nothing migrates), and a figure that reads a length as a cost is one bad add away from the same reading. Counting `len()` reported 17 GB on a phone holding 3.85 GB and sized the cache against a limit the disk had never crossed. Unix uses `st_blocks * 512` (a POSIX unit, not the filesystem's block size); Windows falls back to the apparent length, since `std` exposes no cheap equivalent. The same rule already applies in enginefs to progress. `POST /cache/clean` yields an `EvictionReport`, and one that ends over the limit says so with the protected byte count (`shortfall_message`) rather than reporting a cleanup that did nothing. That line is driven by `EvictionReport::over_limit` and never by `total` against `limit`: when the two are computed by different readers, summing both sides lets one reader's slack cancel another's shortfall, and the client is told the cache got under the limit while the disk it cannot write to is over its own cap by exactly as much as before. **The floor is `enginefs::CACHE_FREE_SPACE_FLOOR`, one number with three readers** — the stream route's readiness check, the published cap (`cache_budget::cap_to_publish`), and the engine's reconciler (`EngineFS::start_reconciler`, started by `run()` per engine, every 2 s) — and the third is what makes the other two hold: librqbit writes the file it wants straight to `ENOSPC`, so without it a film larger than the free space ran a television to zero in 40 s. The reconciler's free-space arm pauses a writing torrent under the floor (`TorrentHandle::stop_torrent` → `Session::pause`, **pinned torrents included** — the one deliberate exception to "anything that pauses skips a pinned engine", because the alternative is the filesystem stopping it as a fatal error; nothing ever takes a pinned torrent's bytes), rings `retention::SlackBell` so the owners give back everything nobody is playing at once, and starts it again itself (`TorrentHandle::start_torrent`) only 64 MiB over the floor (hysteresis, whose memory is the torrent's own run state). Its readers stay parked while the pass decides — librqbit wakes a parked read only when its piece arrives, so `Engine` keeps its readers' wakers and `refuse_reads_for_space` fails them with `StorageFull`; that is done once the **volume** has been short for 20 s (`STOPPED_READ_STALL_BOUND`, per volume and not per torrent, and applied on the same pass as a later torrent's stop), the bound for a volume nothing here can free. **The refusal is recomputed too, and lifting it is not tied to the start call**: it stands while the free-space arm is the arm stopping that torrent, and the very next pass whose verdict is anything else lifts it (`let_reads_park_again`), because it is a claim about the device and no other arm makes one. Tied to `start_torrent` instead it could stand for ever with nothing able to clear it -- a stopped torrent gets no start when the slack goes and frees the volume, and the playback that follows resumes it in `activate_file` before the reconcile is asked, so the `Run` finds it already `Live`. The one verdict that does *not* lift it is `Leave`: `Error` is the ladder's own arm, whose `restart_from_error` lifts it itself, and a failed `statvfs` is evidence neither that the volume filled nor that it cleared. `restart_from_error` restarts only what the backend actually killed — a torrent that is merely stopped is started by the next reconcile, from a reading it takes itself. The stream route answers `507` for a request that would write to a volume under the floor and `get_statistics` reports `phase: error` with `STOPPED_FOR_SPACE_MESSAGE` for a torrent stopped on one (`Engine::is_stopped_for_space`, recomputed — see the bullet below). Do not move the floor back into the server crate.
- **The cache budget is published by `server/src/cache_budget.rs`, and every publication goes through `cache_budget::publish`.** That module owns `CacheLimit` (`min(cacheSize, occupied + available - CACHE_FREE_SPACE_FLOOR)`), the `statvfs` behind `available`, the `CachePasses` order and the one writer of `EngineFS::cache_budget`'s shared cell. It exists because everything downstream of the number hung off a walk whose only purpose was eviction, and that walk is gone: `CacheBudget::Unknown` installs no retention policy at all, so a process that has published nothing holds no window over a proxied stream and reclaims none of it. Three triggers state a budget today: a minute timer that states one *before* it is even spawned (`cache_budget::start` publishes and only then spawns its loop, and `run` **awaits** it, so the budget exists before the router is built rather than a moment after -- `server/tests/proxy.rs::a_stream_relayed_before_anything_has_walked_the_cache_is_still_bounded` is the pin, and it is the claim the whole module leads with), `routes::system::update_settings` (because `cacheSize` is half of what the cap is made of, and waiting for the next tick left everything already playing bounded by the number the client had just replaced), and `POST /cache/clean`, which restates the cap before it reports it so the number a client reads is the number the owners are sized against. It goes in through `cache_budget::publish_counted`, outside the claim the cap is published under, because the walk is the only thing in the process that counts and the timer overtakes any walk longer than a minute: one `statvfs` against sixteen thousand statx calls. Recorded under the cap's claim, as it first was, a device whose walk always loses kept no count at all, `occupancy_last_counted` answered 0 for the life of the process, and every publication after it sized the cap from free space alone. **`occupied` is the input with no cheap source**, and the trick that makes the other triggers possible is that `occupied + available` does not move when the *cache* does -- every byte written comes off one and goes onto the other -- so a stale occupancy against a fresh `statvfs` is wrong only by what the rest of the device did. `occupancy_last_counted` therefore takes `LastEviction`'s figure, and 0 before anything has counted -- which is not "stale but close": it is wrong by the whole of the cache, so a full 4 GB television with 600 MiB free states 88 MiB as the entire budget and `retention::policy_for` installs a real policy at that size. It is still the right absence, because the alternative (`Unknown`) bounds nothing at all, and because it now ends at the first walk rather than lasting for ever. When the eviction walk goes, something must still keep that figure honest (a per-entity owner that knows what it holds, or a running total in the chunk store) or the disk arm drifts by however much the cache has grown since the last count. **Do not add a second writer.** A publication that took its own reading and called `RetentionBudget::set` directly is exactly the bug `CachePasses` exists for: readings overlap, and one taken before `cacheSize` was lowered must not land on top of one taken after.
- **A zero-byte read from the archives' progressive cache is not the end of the stream, and the reader may not wait on the writer for the tail.** `archives/cache.rs` counts `written_bytes` the moment tokio *buffers* a write, so a reader is routinely promised bytes its own `File` handle cannot see yet -- measured at about once per iteration of `finish_right_after_buffered_write_reads_full_tail`. The read it issues for them can be answered with zero bytes by an operation spawned before those bytes landed: that zero describes a file that no longer exists, and treating it as EOF truncates the member (which is the bug that test was written for). Treating it as a reason to park on the writer's `Notify` is the *other* half of the same mistake, and it is a permanent hang: `CacheWriter::finish` flushes and then publishes completion, and the `notify_waiters` beside that completion is the last word the writer ever says, so a waiter armed after it is never woken again -- the read stops for the life of the process, which the workspace suite saw once in 250 runs as "reader timed out". So once `is_complete` is set the reader **retries the read** instead of waiting, and that is exactly safe because the flush precedes the completion: every counted byte is physically there and one fresh read finds it, with no spin. While the writer is still going, parking stays right -- its next write, its finish or its error is another notification -- and retrying there would spin against the disk until the buffered write lands. `ProgressiveReader::wait` must also keep its `Notified` future across `Poll::Pending` returns: dropping one deregisters the waker.
- **HTTPS here trusts Mozilla's compiled-in roots, not the device's store.** Every `reqwest` client in this workspace is built by `enginefs::http_client_builder` (`enginefs/src/http_client.rs`), which calls reqwest's `tls_certs_only` over `webpki-root-certs`; librqbit has its own copy of the same policy at the pinned rev, so a tracker announce is covered too. **Do not build a bare `reqwest::Client`**: reqwest 0.13 hands any client that brings no roots of its own to `rustls_platform_verifier::Verifier`, and `add_root_certificate` is not an escape (extra roots take `new_with_extra_roots`, still that verifier). On Android that verifier calls Java's `CertPathValidator` with revocation checking on, so a leaf with no OCSP URL makes Android download and parse the issuer's CRL in Java -- measured at ~400 MB of Java heap per announce on a Chromecast with Google TV, 91% of the app's Java allocation and the GC storm behind an ANR; on Linux it re-reads the system store from disk per client built, and this workspace builds several. The trade is stated in the module doc and is deliberate: a corporate TLS-inspecting proxy's CA no longer verifies our HTTPS, which for a server whose every HTTPS peer is on the open internet is the right way round. `enginefs/tests/tls_roots.rs` proves it by difference (a plain builder cannot `build()` with `SSL_CERT_FILE`/`SSL_CERT_DIR` pointed at nothing; ours can), and a unit test pins that the compiled-in set is a real root program -- with `tls_certs_only` an empty set trusts nothing. Two clients are deliberately outside it and neither reaches the platform verifier: `/proxy`'s unverified retry (`danger_accept_invalid_certs` takes reqwest's `NoVerifier` arm first) and one proxy unit test whose connection is refused before any TLS. `jni::init_android_tls_verifier` still arms the Java verifier, as a fallback for a client somebody forgets to route through the builder -- a handshake that reaches it is the bug, not the design.
- **librqbit's `paused` flag is not what the torrent is doing, and across an initial check it is wrong in both directions.** `ManagedTorrent` keeps a persisted `paused` bool *and* a `ManagedTorrentState`, writes them at different moments, and lets them disagree. `Session::unpause` sets `paused = false` (`torrent_state/mod.rs:649`) before `_start` discovers a check is already running and returns success having started nothing (`:548-551`); that check finishes with its own captured `start_paused` and parks the torrent in `Paused` -- stopped, flag says running. The other way, `TorrentStateInitializing::check` passes `pause_requested` to `FileOps::initial_check` and to nothing else (`initializing.rs:279`, read at `file_ops.rs:113`), so a pause landing during a *fastresume* check is dropped, the continuation applies the add-time `start_paused` and the torrent goes `Live` -- downloading, flag says paused. That second one is the measured 3 MiB -> 12 MiB overshoot past the free-space floor. A third shape has no divergence but no settled state either: a pause during a *full* check does bail it, and the `Err` arm returns `Ok` without touching the state (`mod.rs:590-593`), leaving the torrent `Initializing` with no check running, which `wait_until_initialized` (`mod.rs:759`) polls forever. So ask `TorrentHandle::run_state` (`enginefs/src/backend/mod.rs`), which reads the state machine, and never `is_paused()`; and keep `Initializing` a separate answer from `Paused`, because only the latter is a state anything can start again. Three tests in `backend/librqbit.rs` (`run_state_*`) drive a real persisted session into each shape; they need a storage that blocks in `pread_exact` (`gated_storage`) to be inside the window at all, which is why no earlier test in this area could see it. librqbit's own `is_pause_requested` is `pub(crate)` at the pinned rev, so the `pause_requested` these report is the persisted flag -- the same thing to a caller, but it cannot tell you whether the check is still running.
- **The reconciler makes every start and stop, and why a torrent is stopped is recomputed, never stored.** librqbit persists one pause bit and never records why it is set. Every earlier version of this code kept an in-memory note of which policy had paused what, and in a fresh process that note is empty while the pause it describes has survived the restart, so the resume paths that consulted it did nothing in exactly the case they were written for. `reconcile::desired()` is a pure function of conditions that can all be read now, so nothing has to survive a restart. Its doc comment lists the ladder and why each arm sits where it does. The rules that hold it up:
  - Decide from `TorrentHandle::run_state`, never `is_paused()` (see the bullet above). Tests assert on `run_state` too, never on a flag the code under test wrote. Four defects in a row got past tests that asserted the flag. `stats.json`'s `swarmPaused` answers from `run_state`, so `server/tests/embed.rs` can assert the same thing.
  - The hysteresis stores no bit. A running torrent is measured against the floor and a stopped one against floor + `FREE_SPACE_RESUME_MARGIN`, so the trigger's memory is its own output. A `PlaybackStart` is measured against the floor. `Engine::is_stopped_for_space` and the stream route's gate call `reconcile::volume_is_short` at the floor itself. At the resume line they would report a volume the rest of the server considers fine as out of disk.
  - "Playing" means the liveness cell (`enginefs::retention::live`): one entity, written when the server sees a stream open, with no clock attached. A viewer who pauses keeps their torrent running. When they open something else, every other unpinned torrent is stopped on the next tick (arm 6). There is no idle grace, no last-active stamp, and nothing outside the reconciler pauses or resumes a torrent.
  - Whatever needs a torrent running *now* (the stream route's `MetadataResolutionGuard`, `on_stream_start`, `focus_torrent`, `pin_download`) awaits `reconcile_hash(.., PlaybackStart)` after registering its activity. The start it may issue is what un-wedges a torrent the last process left stopped, and the reader opens on the very next line. `set_seeding_enabled` uses `Timer`, because nobody is waiting for a reader. A torrent stopped for space therefore keeps its resume margin when `server::run` applies the persisted setting at startup.
  - The reconciler holds one lock per info hash (`reconcile::HashLocks`), never a global one. It looks engines up with `peek_engine`, never `get_engine`, because `get_engine` resets the idle-removal clock. It leaves alone any handle whose backend manages its own playback lifecycle.
  - Only two process records survive, and both are correct when they start empty. `Conditions::settled` means this process has re-applied the want-set: it is false at start, and nothing may start a restored torrent before `apply_pins` runs. `Engine::last_transition_at` drives the anti-flap dwell (`RECONCILE_MIN_DWELL`), and `u64::MAX` means "never moved" rather than `0`, because the clock reads `0` for the whole first second. The `Error` arm answers `Leave` only for a settled torrent. An unsettled one gets `Stop`, which calls nothing and lets its reads park again.
  - **Every route that opens a reader on a torrent registers a stream first.** There are two such routes: `routes::stream` and the `torrent:` form of `routes::archive::stream_file`. The second one's guard (`TorrentMemberStream`) rides inside the response body, and its `Drop` spawns `on_stream_end`. `server/tests/embed.rs` holds both halves (`an_archive_body_keeps_its_torrent_running_while_it_is_open`, `an_archive_member_read_lets_the_torrent_be_stopped_again_when_it_is_done`). Grep for `get_file_reader` before adding a third route.
  - A stop is a real `Session::pause`: peers are dropped, writes stop, and the pieces are kept. `start_torrent` (`Session::unpause`) resumes it with no re-check. Afterwards the swarm has to be re-acquired, and that cost is accepted on purpose, because a torrent nobody is playing or pinning is fetching bytes that its next retention pass will delete. `the_reconcilers_stop_stops_fetching_and_its_start_keeps_the_pieces` pins this against a real two-session swarm. `TorrentHandle::set_upload_throttled` is still on the trait, but nothing calls it.
  - **`seedingEnabled` switches uploading, not running.** On, the session uploads all the time; off, it uploads only while a player is reading (`BackendEngineFS::apply_upload_switch`: `seeding_enabled || playback_is_live()`, the same predicate the activity light is drawn from, so the light can never show an upload the setting ruled out). It is the fork's session-wide choke (`Session::set_upload_enabled`): nothing is paused, no peer is dropped, downloading is the ladder's and the owner's as before, and while a player reads every torrent uploads, pinned ones included -- it does not choose between torrents, and the per-piece advertise mask that could is the retention owner's. Recomputed, never stored: applied on a stream start and a settings change (where it turns on) and on every reconciler tick (where it turns off), under one lock so a stale "off" cannot land after a fresh "on". The ladder does not read the setting: `Conditions::seeding_enabled` is still copied in but no arm uses it, and the reconcile pass `set_seeding_enabled` runs decides nothing new.
- **The DHT is a peer source, not a requirement, and a dead one must stay quiet.** librqbit retries DHT bootstrap and UPnP forwarding *forever*, at WARN on every attempt (`crates/dht/src/dht.rs`'s `bootstrap_hostname_with_backoff`, `crates/upnp/src/lib.rs`'s discovery/`manage_port` loops), so a network that drops the DHT's UDP produced hundreds of identical warnings and no conclusion in a real field log. Both targets are therefore pinned to `error` in `DEFAULT_LOG_FILTER` (`server/src/lib.rs`) and the state is reported once instead, by `diagnostics::dht_health`: INFO when it comes up, ONE WARN after a 90 s grace if it has not, INFO if it recovers, everything else at debug. Do not re-raise those directives, and do not add bootstrap hosts to `DEFAULT_DHT_BOOTSTRAP_NODES` to "fix" a bootstrap failure: an earlier commit did exactly that and made things worse -- three of the five names it shipped resolve but answer 0/3 DHT pings, which is retry noise, not resilience. The list is now exactly the two names measured to answer (which is also librqbit's own default); `router.bittorrent.com` was kept a while on reputation and dropped once a re-probe from two networks had it answering nothing there either. A test asserts the list exactly, and **a host may only be added with a measured `ping` behind it**. The real fix for the field log was DNS: `backend/dht_bootstrap.rs` resolves the names itself (system resolver, then DNS over HTTPS, then a `dht-bootstrap.json` cache next to `dht.json`) and hands librqbit address literals, since `lookup_host` accepts them; whatever it cannot resolve stays a name so librqbit can keep trying. Both DHT files -- `dht.json` and `dht-bootstrap.json` -- were the `is_session_artifact`s of `cache_cleaner.rs`'s walk, which is gone: nothing sweeps them now, and the state that exists to avoid the network is kept because no owner speaks for it. Both resolvers are injected (`BootstrapResolvers`) -- `BootstrapResolvers::offline()` is the no-DNS set every hermetic caller must use, and no test may hit a real resolver. That fixes the DNS half only; a network that drops the DHT's UDP is unaffected, and the doc comments say so. The observable state is `enginefs::backend::DhtStatus` (`ever_bootstrapped` is sticky on purpose), served as the `dht` key of `/stats.json` and as `ServerHandle::dht_status`; a client shows "DHT unavailable, using trackers only", not an error. Also note the librqbit fork's misleading message: `bootstrap_hostname` returns `v4.or(v6)`, so a v4 failure's error is *discarded* and what gets logged is the v6 branch's `NoSuccessfulLookups { errors: 0 }` for bootstrap hosts that have no `AAAA` record -- "0 errors" is an empty v6 address set, not proof that nothing was attempted.
- **UPnP port forwarding is only for a fixed listen port** (`TorrentListenPort::wants_upnp_forwarding`). `Ephemeral` -- what `ServerConfig::embedded()`, the Android JNI cdylib and every test use -- binds a different port each launch, so a mapping is worthless next time, and on Android SSDP discovery is multicast the app sandbox cannot send at all. The forwarder retries on an interval for the life of the process either way.
- **The piece store is the session's default storage, and that is the only place it can be.** `LibrqbitBackend::session_storage_factory` builds a `PieceStoreFactory` over `piece_store::StoreRoot::in_download_dir(download_dir)` -- `<cacheRoot>/rqbit-downloads/.pieces` -- and `open_session` installs it as `SessionOptions::default_storage_factory`, never on an individual add. The persisted record librqbit replays at startup names an output folder and a file selection and **no storage**, so the storage a restored torrent comes back on is whatever the next session's default is; that is why `StorageFactory::ensure_persistable` (a promise that a restart finds the data again) can only be made from here, and it is made. Two consequences you must not forget. **Torrent data is now one file per piece uniformly, downloads included**: librqbit still reports a file path per file, under an output folder it chooses itself, but no payload byte is ever written there -- the store takes one root and it is the cache root, so `DownloadInfo::path` is a name and not a file. Nothing above the backend reads that name for anything (see the placement bullet below). **Every free-space question is therefore asked of that root, and of nothing else**: `reconcile::Volumes` is built over it and has no per-folder API left to get wrong (`available()`, `short_for(now)`, `data_folder()`), which is what the reconciler's arm, `Engine::is_stopped_for_space`, `held_stopped_for_space` (so what `stats.json` reports), the stream route's per-torrent `507` and `check_pin_preconditions` all read. Asking `TorrentHandle::output_folder()` instead -- which every one of them did until the store went in -- reads a card nothing writes to, and for a pin that used to be the card a settings key of its own named: the ladder left a torrent running onto a full store, and refused a pin that had all the room it needed. `check_pin_preconditions` also asks only for the pinned file's **missing bytes**: the copy sizing it used to do (`same_volume`, `volume_id_probe`, `allocated_bytes`, all now deleted) was about a relocation rewriting whole files at the destination, and there is no relocation left at all. **There is no migration, by decision**: a whole-file download an earlier version wrote is neither converted nor read, the torrent re-downloads as pieces, and the old bytes belong to no owner at all: no store speaks for them, no usage figure counts them (`StoreRoot::unregistered_bytes` is one `read_dir` of `.pieces`, and they lie beside it), and the launch sweep (`sweep::sweep_legacy_downloads`, on the same hop as `sweep_unadopted`) removes them whole on the first start handed a pin set -- a start handed `None` sweeps nothing. One thing did not have to change: `PIECES_PER_DIRECTORY` was already applied in `piece_store::store::piece_path`, so a 27 GB torrent's ~6,750 piece files land in seven bucket directories and not one, with a test that says so. **That bucketing is the store's alone now** -- see the next bullet: `piece_store::StoreRoot` is the one type that turns an info hash and a piece index into a place, and `root_in`/`PIECE_STORE_DIR` are crate-private behind it, so a caller can name the store but never its shape.
- **The retention policy decides what may be reclaimed, and it is wired.** `enginefs/src/retention.rs` is the driver: one `piece_store::policy::RetentionPolicy` per torrent, for the file most recently streamed on it, sized once from the published cap and fed the playhead a reader actually reached. Three calls make its answer true, and the order is the point. **The window is held back from what we announce before the reader opens** (`Engine::begin_retention` -> `TorrentHandle::set_pieces_advertised(range, false)`), which is the only ordering under which no Have ever goes out for a window piece: there is no un-Have in BitTorrent, so a piece announced once is announced to every peer that was connected. **A piece the window releases is committed and only then advertised.** **Everything else of that file is reclaimed**, which is the backend forgetting it and the store unlinking it, under one claim. So the only pieces a peer is ever told about are the ones nothing will ever reclaim. The third state this needs -- have, readable, announced to nobody -- is the fork's `ManagedTorrent::set_pieces_advertised`, which is why the policy sat unwired until the librqbit pin was moved to it; `AfterRelease::LeaveDropped` is the other half, because a piece put back into the want-set the moment its claim is released is re-downloaded at once and the bound becomes a treadmill (241 MB came back off the swarm in one second of an idle test torrent when that was got wrong). **No policy is installed** for a pinned torrent (retention property, keep and share everything), for a budget that covers the file (`Shape::Whole` -- the phone with 379 GB free and every desktop), or before anything has published a budget at all: `CacheBudget::Unknown` is an absence and **not** a zero, or the first stream of every boot would reclaim everything the window passed before anything had measured the disk. The pass rides the reconciler's two-second tick (`BackendEngineFS::retain_engine`), because a torrent playing at 20 MB/s writes a gigabyte a minute and nothing else is measuring it. The budget is `cache_budget::cap_to_publish`'s answer, pushed in by `cache_budget::publish_now` -> `EngineFS::cache_budget` and **never recomputed here**: a second reading of the same volume would have the two halves of the cache sized against different numbers. Both halves are proved over real librqbit sessions on the wire in `backend::librqbit`'s tests -- `a_stream_past_the_cache_budget_stays_under_it_and_still_plays` measures the piece files on disk after every pass, and `a_peer_is_never_told_about_a_piece_we_later_reclaim` reads the leecher's own piece store to see what it was offered.
- **The same policy bounds `/proxy`, and the playhead it needed is the thing that was missing.** `server/src/proxy_retention.rs` is the second driver of the *one* `piece_store::policy::RetentionPolicy` -- same 90/10 window, same reclaim rule, and the same `RetentionBudget` **cell** (`EngineFS::cache_budget`, handed out rather than copied: two readings of "how much room is there" over one volume is how two layers come to evict against different numbers). What `/proxy` never had was anywhere recording *where playback is*: it serves ranges, so the reads and the offsets were always there, but nothing was a playhead, so the cache was bounded by the old cache cleaner's walk alone -- a minute after the last write at best, against a stream writing a gigabyte a minute. There are now exactly **two** places a proxied playhead is written, and both are a byte that really went out: `proxy_cache::Cached::body` for what came off the disk (which is the whole of a rewatch, where the origin is never asked anything) and `proxy_cache::Filler::take` for the origin's body on its way past. **Never a `Range` header** -- that is what a player asks for, and `bytes=0-` is every player's first request. **There is no playhead at process start and the map holding them is empty**, which is true rather than a placeholder: a cache directory says which bytes were fetched and nothing whatever about where anyone read to in them, and nothing here is persisted for the same reason. A `ProxyRetention::Reader` is opened per read (`Entry::look_up` for a hit, `Entry::fill` for the origin's body) and dropped with the body, so the map holds open reads and not a permanent entry per URL ever played. The pass runs on the playhead moving rather than on a tick -- a proxied entity grows only as its own body is relayed, so the byte that moves the window is the byte that grew the cache -- throttled to `PASSES_PER_WINDOW` per window of playback, which is what the overshoot above the budget is. Two things are the adapter's and not the policy's: nothing is held back or announced (there is no swarm), and the reclaim is the unlink with no have-set to interlock against. **What there is to interlock against is the read itself, and it is the thing the split was hiding.** A torrent's reader is refused by librqbit -- `drop_pieces` will not forget a piece a reader is waiting on -- and a proxied read has no backend to refuse for it, so it refuses for itself: `Reader::promises` records the chunks a response was framed around and has not delivered, `note` shrinks that from the front as they go out, and the pass skips them. It is not a second policy and decides nothing about what to keep; without it the pass a body's own playhead drives deletes that body's tail, because a window is 90% ahead of the playhead and the run the window itself kept is a whole window long -- measured, a 32-chunk `206` that died at 29 chunks. **A window is a statement about a playhead and there is one per live reader**, not one per entity: two players in one entity (`p=` is out of the key on purpose) each get one, or each pass reclaims the other's read-ahead in alternation. And **an entity with no policy still has a window** -- all of it -- for `Shape::Whole`, for no cap, and for `CacheBudget::Unknown`: no policy means nothing here reclaims, never that nothing here is being read, and the published cap is per volume, so the rest of the cache can push past it while a player is inside these bytes. That is the same answer the torrent half gives (`TorrentGate::Announced` for an engine with no policy). The proofs are in `server/tests/proxy.rs`: `a_proxied_stream_past_the_cache_budget_stays_under_it_and_still_plays` is the torrent bound's twin, `a_seek_back_inside_the_window_is_served_from_disk_and_one_outside_it_is_not` is what the split was costing us, `the_cleaner_leaves_the_chunks_a_proxied_player_is_inside` is what a clean may not take, and `the_run_the_window_kept_is_served_back_whole` and `a_second_player_fetching_does_not_truncate_the_first_ones_read` are the promise.
- **What a playback panel is told about a stream, and why it is an interface and not a layer.** `server/src/stream_numbers.rs` answers one question -- *what do you hold of the stream this URL names?* -- and `GET /stream-numbers.json?url=...` / `ServerHandle::stream_numbers` are the two doors to it. **The URL is what dispatches**: a torrent stream is `/{infoHash}/{fileIdx}` -- **`-1` included**, which is the documented auto-select the stream route, the archive route and `/{infoHash}/-1/stats.json` all resolve with `routes::compat::resolve_file_idx` and the `f=` filters, and which this dispatch therefore resolves the same way, over the file list of an engine it peeks at rather than creates; a client that lets the server pick the file holds that URL and no other -- or its `/stream/` alias; a proxied one is `/proxy/?d=...` or the Core path format; and both shapes are this crate's own routes -- so the `StreamStore` trait is implemented twice, once per store, each recognising its own shape and no other, and a URL **neither** recognises is `None`: a stream this server does not hold, not an error, and a `200 null` rather than a `404`. The proxy half reads the target through `routes::proxy::requested`, the same function the route itself reads it with, so the URL shape is defined once; keep it that way. **The trait carries no state and neither implementation may grow any**: both stores are already keyed by something this server maintains for other reasons (the piece store by info hash, the proxy cache by entity), each answers from a live listing of its own directories, and a route with bookkeeping of its own would be a third thing to keep true. Nothing new is persisted. The one field this added is `proxy_retention::LiveStream::target`, and it is there because it is the one thing that cannot be derived: a cache key is a hash of the target *and* the player headers, so an entity directory cannot be worked back to the URL a client holds. It is written when the entry is created, dies with it, and is absent at process start like every other field of that map. **The window is what is on the disk, split at the playhead** -- `behind` is what a scan back gets, `ahead` is read-ahead that has *arrived* -- and not the extent the policy intends to fill; time is the client's to compute, from a bitrate this server does not have. **Every absence is real and none of them is a zero**: no `window` where no policy is bounding the stream (what is on the disk is then whatever the stream has fetched, a different quantity) or where no reader has been inside it; no `sharing` at all for a proxied response, which is not seeded; no `committedBytes` for a torrent with no policy, which has promised nothing whatever it announces. **The transfer totals are this session's** -- librqbit's own per-torrent counters -- and the ratio with them: the conventional across-restarts ratio would mean persisting counters, which is a stored claim about a past this process never saw, and is exactly the bug this codebase keeps shipping. Do not persist it. They are also **`None` rather than zero for a torrent that is not live**: librqbit keeps those counters in the live state, so a torrent that is paused, still checking, stopped for space or in error has none to read -- all of them reachable with a panel up, from the fastresume check at stream start to the idle, background and free-space arms of `reconcile::verdict` -- and a torrent that has moved gigabytes and then paused has not moved nothing. `TorrentHandle::transfer_totals` therefore answers an `Option`, the three numbers travel as one `transfer` group that is present or absent together, and only a caller reading a *difference* may flatten the absence to zero (`traffic.rs`, where a sum that dropped reads as "not grown"). **What a panel is told about the retention policy is read from `Engine::bounds`, never from the policy slot**: `Engine::retain` takes the `FileRetention` out of that slot for the length of a pass -- a store listing and two awaited backend calls -- on the reconciler's two-second tick, so a reading off the slot would tell a panel "nothing is bounding this stream" for a second out of every two and blink both rows out; the bounds are written beside the policy under the same `announce` lock, exactly as the proxy keeps `LiveStream::bounded` and `LiveStream::windows` beside its own.
- **A pin is a retention property, and `output_folder` decides nothing.** There is one torrent-data root -- the piece store's, `<cacheRoot>/rqbit-downloads/.pieces` -- and data placement is that root plus the info hash and nothing else. `output_folder` is librqbit's concept and stays inside `backend/librqbit.rs` (the fork must remain upstreamable): it is where a torrent's *name* lives, it is reported to a client as `DownloadInfo::path`, and it is what the per-file delete sweeps a legacy whole-file copy from. Nothing in enginefs or server may key off it for placement, monitoring, protection or accounting, and there is no `TorrentHandle::output_folder` to read it with any more. What went with that rule, and must not come back: `TorrentPlacement::output_folder` (the struct is a want-set now), `TorrentBackend::relocate_torrent` and librqbit's file-moving implementation of it, `EngineFS::{relocate_engine, begin_relocation, end_relocation, replace_engine, download_folder, set_downloads_dir, downloads_dir, engine_paths}`, the `relocations` registry the cache cleaner consulted, `PendingMagnetAdd::settled_later` and its optional abort handle, and the owned pin guard a move carried. **A pinned torrent does not move**, so none of the machinery that made a move safe is owed: it was all there because a pin used to re-add the torrent under `<downloadsDir>/<infoHash>`. Where a location is genuinely needed, ask the store (`BackendEngineFS::piece_dir`): that is what protection, the dormant-pin delete and the free-space check all do. **The dormant-pin delete must prove it is dormant before it unlinks anything, and the registry is not the proof.** `unpin_download` reaches that path because `get_engine` found nothing, and `remove_engine` drops a registry entry while leaving the torrent running (the TUI's `d`, and the idle sweep between dropping the entry and telling the backend), while a magnet add parks a hash outside both the registry and the backend for as long as metadata takes. Unlinking `<cacheRoot>/rqbit-downloads/.pieces/<infoHash>` in either case is the have-set desync the whole interlock exists to prevent -- the torrent goes on advertising pieces that are gone. So three things gate it: the pin actually removed (`was_dormant` -- with no engine and no pin this layer has no record tying those bytes to a download, and they are the next launch sweep's), `pending_magnet_add` (a hash being added is left entirely alone), and `TorrentBackend::get_torrent` (a torrent the session holds is deleted *through the backend*, `remove_torrent_and_files`, which drops it before its storage releases the pieces -- the interlock stays in the one place). Only a hash the session has never heard of is deleted by hand. `settings.downloadsDir` did not survive: there is one torrent-data root, `settings.cacheRoot`, and every figure and every sweep is over that one root (read from the engine, not from the setting).
- **There is one chunk store, and two adapters over it.** `enginefs/src/chunk_store.rs` is "store chunks; read them back as chunks (to serve a peer) or as a random-access byte range (to play)", which is what a torrent's pieces need and what a cache for HTTP range requests needs, so it is written once: `ChunkDir` owns `<dir>/<index / 1000>/<index>` (`CHUNKS_PER_DIRECTORY`), the two staging spellings (`STAGING_SUFFIX`), the rename that makes presence mean **complete**, `remove` taking both copies, the name-only listings, `stat` with its strays, the one `occupied_bytes`, the typed read (`ChunkError::Missing` vs `Io`) and the `OpenChunks` handle LRU. The adapters are `piece_store::PieceStore` (a `TorrentStorage` over a `ChunkDir` and a `PieceLayout` -- the multi-file global byte space and BEP-47 padding sit **above** the store and none of it is in there) and `server::proxy_cache` (a byte-range reader and writer per cached entity). **Exactly two things are parameters and there is not a third**: *staging identity* (addressable `<index>.part`, reopened across many 16 KiB writes, read back by the hash check and recovered at `init` -- versus anonymous `<index>.<pid>-<n>.part` for uncoalesced concurrent fillers that can resume nothing; collapse them either way and either two fillers interleave into one file or librqbit loses its incremental write), and *the commit trigger* (`ChunkDir::commit(index, expected_len)`: librqbit renames after its own SHA-1 and passes `None`, a URL response has no hash and passes the byte count it buffered). **`expected_len` must stay optional.** librqbit never writes BEP-47 padding, so a piece whose tail is padding is committed *short* -- there is no length a legal padded piece would satisfy, and promoting the URL criterion into the store breaks every padded torrent (`each_piece_file_holds_exactly_its_own_slice_of_the_torrent` is the test). **Reads are typed and listings are lenient**, in both adapters: "not there" is an ordinary state a reclaim creates and a hash check must not be handed zeroes for it, while a caller counting the disk must not be stopped by one directory it may not enter. The chunk *size* is deliberately not shared -- 256 KiB is what a `/proxy` boundary costs a fetch and an uncompleted chunk costs in memory, a piece length is the swarm's -- so the store is always **told** an index and never computes one. The two roots stay where they are (`.pieces`, `.proxy`): each adapter answers for its own half of the root, and it is why there is no migration to write. **The delete stays behind each adapter, and the type system says so**: `ChunkDir::remove` is `pub(crate)` to `enginefs`, so the whole `server` crate -- routes and the `/proxy` adapter alike -- cannot name it and a call to it does not compile (`E0624`). A generic *public* `remove` on the shared store would be the second door into the unlink that `StoreRoot::delete_pieces` exists to refuse, and "nobody calls it" is a convention, not a guarantee. It takes both copies of a chunk and it is **lenient about anything wearing a chunk's name that is not a chunk**: a directory answers `EISDIR` and not `NotFound` to `remove_file`, the listing can only filter that at the complete name (a directory at the *staged* name spells no index, so no listing ever sees it), and this is the delete of a whole run whose have-bits the caller has already dropped -- so a failure that abandons the rest of the run leaves bytes nothing will read, offer or count as ours again on a disk the caller has been told it freed. `StoreRoot::delete_pieces` follows from the same fact and **cannot fail**: it attempts every piece it is given, logs what the volume would not give up, and returns how many really went.
- **In the piece store, a piece is ours at one instant, and presence means complete.** Bytes are written to `<piece>.part` and renamed into place (`chunk_store::ChunkDir::commit`) in `TorrentStorage::on_piece_completed`, which librqbit calls after the hash check, and `PieceStore::has_piece` answers from the final name alone. That is not tidiness: the rev we pin builds the startup have-set as the resume bitfield **intersected with `TorrentStorage::has_piece`**, the intersection only clears bits, and the fastresume hash check samples ~65 pieces of a torrent however large -- so a wrong "yes" is not a re-download, it is a have-bit standing over bytes nothing verified, advertised and served. A file created by a piece's first 16 KiB chunk is there for the whole of the download, which is why `is_file()` on the piece name is the wrong answer and had to stop being it. Three rules hang off the staging name and each has a test: **a read prefers the staged copy** (the two coexist only while a dropped piece is being downloaded again over one not yet deleted, and the read that decides whether to keep the new bytes is the hash check itself -- served the old copy it passes over bytes nothing wrote); **`init` deletes a staged copy that shadows a complete one, and only that one** (the pair is explained by chunk bookkeeping that does not survive the process, so what a kill leaves is a stale shadow over a verified piece, while a lone staged piece shadows nothing and a pause is allowed to keep its in-flight work); and **`delete_piece` takes both**. A piece no file owns -- entirely inside BEP-47 padding -- answers *yes* to the trait's `has_piece` and *no* to the store's: nothing will ever write it, and a piece nothing can write is a piece nothing can lose, which is the question the trait asks; answering no would clear a have-bit no download could ever set again. The store also keeps a few open handles (`chunk_store::OpenChunks`, `OPEN_HANDLES` of them, keyed by chunk and by copy) and an in-memory set of the pieces that have a staged copy, so a piece written or streamed end to end is one `open` instead of one per 16 KiB chunk (and two per read, the staging probe first). Neither changes what is on disk or what a read sees: a handle is forgotten before its file is renamed or deleted and a cached complete handle goes the moment a staged copy is begun, the staged set is advisory in one direction only (its "yes" is checked against the filesystem, its "no" is trusted because every staged file is either written by this process or seen at `init`), and a test pins the open counts.
- **The retention policy is arithmetic, and two things it must never grow.** `piece_store::policy` decides what we keep and what we share -- budget covers the file, keep and seed all of it; it does not, split it into a rolling window (90% ahead, 10% behind) and a committed set that is filled only from pieces we already hold and never churns once full. **Where that split falls is a number and not a kind of stream** (`Share`): a torrent gives half to the committed set because a peer may ask us for its pieces, a proxied URL response gives none because nothing will ever ask -- a committed half for one would be half the cache held permanently, by the committed set's own never-reclaimed rule, for a reader that does not exist. One formula, two numbers, and no branch on which store is calling. It takes its budget in bytes from `CacheLimit::effective` and does not recompute it, deliberately: two layers with two readings of "how much room is there" evict against different numbers. **Do not build an availability map** -- rarity-based retention was measured at <=0.15% over random across four live swarms and 0.00% on three of them, because seeder fractions of 94-100% cap the effect -- and **never fetch outside the playhead**: the committed set takes pieces the window is about to release and nothing else. What used to stand here, that the policy was wired to nothing, is settled and is the bullet above: `retention.rs` drives it against a running torrent, and the fork's `ManagedTorrent::set_pieces_advertised` is the have-readable-unannounced third state that made it expressible.
- **The activity light reads the connection, never the disk, and it is judged in one place.** `ServerHandle::background_traffic` answers "this server is using your connection while you are not watching", in two halves -- `downloading`, `uploading` -- with `active` their disjunction, because the client's light is one slot with three glyphs and offers a control per half, so each must be honest alone. There is deliberately no taxonomy of who is at the other end. **The conjunction with "nothing playing" is taken in Rust** (`routes::system::background_traffic`), never handed to the client as two signals: the halves are measured differently, and an app sampling them a moment apart across FFI gets a light that flickers on every disagreement. Four things around it are load-bearing. **One: the counters are librqbit's own per-torrent peer counters** (`TorrentHandle::transfer_totals` → `TransferTotals { fetched, uploaded }`, summed by `BackendEngineFS::transfer_totals` over the torrents that exist), compared against the last reading of the same sum. They are *not* the storage and *not* `EngineStats::downloaded`: the first version wrapped the session's default storage factory to count reads and writes, and lit up at every launch with saved torrents, in a session with no network -- librqbit's initial check reads every restored torrent back off the local disk to hash it. `downloaded` has the same trap in another form: it is `progress_bytes`, have-bytes, which mirrors the hash check's `checked_bytes` while a torrent initializes, so it too grows through a check no peer took part in. `fetched` is the peer-received counter and nothing else feeds it; a test (`the_initial_check_moves_nothing_over_the_connection`) adds a torrent whose data is already on disk to a hermetic session and reads the counters before the check and after it -- the reading before is trivially zero, since an initializing torrent has no live state to count, so what the test pins is that the check leaves both halves at zero while `downloaded` ends at the payload's length; the light staying dark *during* the check was observed in a live restart, not asserted. The counters live on the live state, so a torrent that pauses or is removed takes its bytes out of the sum; a sum that dropped reads as "not grown", which is right. **Two: there is one engine** (`AppState::engine`). There used to be two fields, `engine` and `download_engine`, holding the same `Arc` -- the pairing of a memory-only stream engine with a disk-backed download engine was designed and never built, no memory-only storage exists, and every reader read one instance twice behind an `Arc::ptr_eq` guard. The light sums that one engine's torrents (`BackendEngineFS::transfer_totals`), the same reading `/stats.json` takes; "nothing playing" is its `BackendEngineFS::playback_is_live`. If a genuinely distinct second engine is ever wanted it can be added back honestly -- a field that is a clone of another is not that. **Three: the reading is a peek, not a poll, and it creates nothing.** `Engine::get_statistics` touches `last_accessed`; `transfer_totals` must not, or a light polled every second or two holds every torrent out of the idle sweep for ever and is then lit by the seeding it caused (a test pins the idle clock while it asks). Nothing in the path looks a hash up or adds one -- `stats_target` falls through to `get_or_begin_add_magnet`, and a light that started a torrent in order to report on it would be reporting on itself. `stats()` is not the cheap path either: it builds the file list and takes a tracker-scrape snapshot that may schedule a scrape, so the light reads librqbit's `stats_snapshot()` under the torrent's state lock instead -- a handful of torrent-level counters plus the aggregate peer counters, since `TorrentStateLive::stats` is private at the pinned rev -- and takes `fetched_bytes` and `uploaded_bytes` from it. **Four: "moving" is judged over a window and playback has to be absent over that window too** (`TRAFFIC_WINDOW`, 5 s; `TRAFFIC_WINDOW_STALE_AFTER`, 20 s; `TrafficWindow`, on `AppState`, one per server, with its own clock rather than an engine's). A counter that has not grown since the last reading is the measurement -- a single sample of a total is not a rate -- so nothing can be said until one window has closed, and a window that stretched past the stale bound (a backgrounded app, a suspended phone) is a baseline again rather than a verdict about minutes nobody observed. The bytes a player's own stream pulled in are still in the counters after they stop, so a verdict that asked only "is anything playing *now*" would light the light for one window after every playback; the cost of getting that right is up to two windows of latency the other way, which is the right side to be wrong on. Playback seen inside a window puts both halves out at once, not at the window's close -- the verdict does *not* only change when a window closes, and a test says so. `StreamActivitySnapshot::playback_is_live` is the *definition* of "playing" -- the live fields only (`engine_active_streams`, `active_streams`), and it must never grow to include `active_file` or `active_multifile_selections`, which name the file last chosen, outlive the stream because the want-set is planned from them, and would make a light that comes on with the first playback of the session and never goes out. `BackendEngineFS::playback_is_live` is the same answer without building the snapshot (two read locks, nothing cloned), and a test holds the two together across every state one live field can produce; a change to the definition goes in both.
- **The startup sweep claims what the *embedder's pin set* names, and it runs before the session opens.** `piece_store::sweep_before_session` deletes every directory under `<cacheRoot>/rqbit-downloads/.pieces` that the set does not name, and `BackendEngineFS::boot` is the one place that order lives: take the set (`ServerConfig::pins`, a `piece_store::PinSet`), sweep, open the session, apply the same set (`BackendEngineFS::apply_pins`). Swept after the session instead, every deleted piece would already have been seeded into a store's held set (`init`) and stayed counted as held for the life of the process. A pin is the *only* claim on piece data that outlives a process: librqbit's own `session.json` and per-torrent `.bitv`/`.torrent` files are not a second claim set, and `piece_store::session_recorded_hashes` is gone with that reading -- they claim torrents the sweep must take, because everything that is not pinned is cache and a process that has served nothing is playing nothing. **This server keeps no pin record of its own.** The embedder is the authority, because the app that pins already keeps that list as the downloads the user asked for, and two records of one fact are two records that can disagree; `pinned-downloads.json` is gone, and the name survives only in `sweep::NOT_OURS`, so an install upgraded from a build that wrote one does not have it swept as a previous release's data. Which makes the handed-in set the only thing between a user's offline downloads and `remove_dir_all`, so **`None` is an answer of its own and never "no pins"**: it sweeps nothing, sets `piece_store::PinsUnknown` (every restored torrent reads as pinned to the retention owner, to the reconciler and on `GET /downloads.json`), and **never lifts** -- nothing in the process can learn a set nobody named, so there is no repair, no `clear()`, and the next boot is told or it is not. An embedder whose own record would not read passes `None` and warns its user; passing an empty map instead says "the user has pinned nothing", which deletes their downloads. Never read `pins_unknown()` twice inside one answer: a pin taken at any await fills the in-memory set, and the second read is a duplicate entry in a listing that already named the file.
- **There is no cache cleaner, and nothing walks the cache.** It was a filesystem watch, a debounce, a walk of the one torrent-data root, an age rule, a size rule and a tier order -- a second owner of every byte under that root, choosing victims from a reading of the disk that was minutes old by the time it acted on it. Every byte now has exactly **one** owner that knows whether anybody wants it, and the whole of `server/src/cache_cleaner.rs` that is left is the wire types (`CacheUsage`, `EvictionReport`) and the two functions behind `GET /cache.json` and `POST /cache/clean`. **Every byte under the root is in one of these categories, and adding a category without a deleter is how the disk becomes unbounded again**: pinned (kept until unpinned); inside a `Mode::Live` entity's window or its committed half (budget-sized, and it lasts as long as the response); slack (taken at the reconciler's next tick, at the next switch (`retention::live::Live` changing), on the running-low bell, on `POST /cache/clean`, and at boot by `piece_store::sweep_before_session` and `proxy_cache::sweep`); a chunk an open proxied body was framed to deliver; a `.archives` temp file the session that owns it unlinks; or a stray under `.pieces` the next launch's sweep takes. What is *not* in any of them, and is named rather than hidden: a whole-file download an earlier version of this server left (never counted, and deleted by the first launch sweep handed a pin set -- there is no migration, by decision) and whatever a kill leaves in `.archives` (never counted, and deleted by the next start's `archives::sweep_scratch`); both are bounded by a launch, not by an owner. **What the figures are made of**: `GET /cache.json` is `StoreRegistry::occupancy()` (a sum over the held bits each live store keeps, no syscall) plus `StoreRoot::unregistered_bytes` (one `read_dir` of the store root and a `stat` of each directory no live store speaks for -- a torrent in Error, a previous process's leftovers) plus the proxy owner's running count, against `CacheLimit::effective`; the protections are `Engine::protects` and `ProxyRetention::protected`, read off what the disk really holds and never off the window's own size. `POST /cache/clean` is `EngineFS::drop_slack()` plus `ProxyRetention::drop_slack()` and nothing else -- **"clean" is not a choice of victims any more**: a pin is kept and the window of the one entity being played is kept, so a clean that frees nothing is the ordinary answer and `EvictionReport::over_limit` is what says the cache is still over its cap. **Deleting a piece behind librqbit's back is still the one thing that must not happen, and no *piece* is unlinked any other way**: every piece unlink in the process is `StoreRegistry::delete` (through the live store, so the held bit and the cached descriptor go with the file) reached from `retention::take_claimed`, which holds the `DroppedFilePieces` claim from `TorrentHandle::drop_pieces` across the unlink and releases it last -- or the proxy owner's own `remove_file`. A hash with no registered store frees nothing and says so; its directory is the boot sweep's, and the claimless door refuses outright if a store *is* registered by the time the pool picks it up. Two by-path removals of a whole `<hash>` directory remain, and both are deliberate rather than overlooked: `EngineFS::delete_dormant_download_data` (a `remove_dir_all` for a pin the session does not hold -- guarded by asking the pending-add registry and the session first, which is a reading older than the unlink, so it is the one place left where a store registered in between would be deleted around) and the TUI's Files view, which removes whatever entry under `download_dir` an operator selects, `.pieces` included. Do not add a third. `StoreRoot::delete_pieces` is `#[cfg(test)]` for exactly that reason: its last production caller was the cleaner's, and a door left open for one to come back through is a door that will be used. Do not add a second door into it, and do not add a walk. The store's side of the bargain stands: **every level of a piece's address is checked for the spelling the store writes, not for the number it parses to** (`chunk_store::canonical_index`, taking neither a leading `+` nor leading zeroes; `StoreRoot::scan` applies the same rule to a torrent directory's name, since `torrent_dir` lowercases), so `<hash>/00/0`, `<hash>/0/00` and `<hash>/+0/0` are strays -- counted, because they occupy the volume, and never offered as pieces. **One root means one volume and one cap**: `cacheSize` against that volume's free space, keeping `CACHE_FREE_SPACE_FLOOR` back. What that replaced -- `budgets_by_volume`, `outermost`, `walk_within`, `EvictionReport::combined_with` -- existed because the removed `downloadsDir` could put a second root on a second disk, and a free-space cap is a statement about *one* volume.
- **The shipped `btMaxConnections` is 160, which is 40 peers per torrent, and it applies live.** `TorrentSpeedProfile::effective_connection_limits` derives the per-torrent live-peer cap as `btMaxConnections / 4` clamped to 40..=200; the default was 800, which landed on the ceiling of 200. On the device this server is aimed at that is the wrong end: a peer costs ~75 KiB once buffers, task, channel and table entry are counted, so 200 of them are ~15 MB per torrent on a 2 GB television whose low-memory killer fires around 300 MB -- the same measurement that produced `LEAN_PEER_LIMIT` and `Footprint`. Lean already takes the *background* to 8; 40 is what the **foreground** wants, and `DEFAULT_BT_MAX_CONNECTIONS = 160` lands exactly on the floor, deliberately. A user who wants more still has it, up to `MAX_EFFECTIVE_BT_CONNECTIONS`. **The setting is `Live` in `bt_settings_support`, not `NextStart`**: `LibrqbitBackend::set_configured_peer_limit` puts the new cap on every torrent at once through the same `ManagedTorrent::set_peer_limit` the footprint uses, so lowering it hangs up on the surplus now and raising it re-queues the parked peers, with no restart and no progress lost. The footprint and the configured limit are one `Mutex<PeerCaps>` because they are one decision (`PeerCaps::limit()`) and either can change under the other -- under `Lean` a settings change only *stores* the new value, which is then what the return to `Full` restores, and it never prunes the peer table (only a footprint change does). `SessionOptions::peer_limit` is still what the session *opens* with, so never read the live cap off it; `SessionTuning::pending_restart` deliberately omits `btMaxConnections` for the same reason. Note the reach: the first run writes the default into `settings.json`, so an install that has been up since the 800 default keeps 800 -- nothing can tell that from a user who typed it, and rewriting a persisted setting behind their back is worse.
- **Lean mode shrinks, it does not stop -- and it keeps seeding.** `ServerHandle::set_background(true)` puts the torrent session on `enginefs::backend::Footprint::Lean` (`set_background(false)` = `Full`); the app calls it from its hidden/paused and resumed hooks. It exists because a 2 GB TV's low-memory killer took the backgrounded app twice at 311-379 MB RSS, and the measured attribution put the largest *and still growing* share on librqbit's peers: `peer_limit` 200 per torrent, each ~48 KiB of protocol buffers plus a task, a channel and a table entry, and a peer table that had retained 4224 addresses after one download. "Share between films" is a feature, so **what lean keeps is deliberate: every torrent stays live -- seeding goes on, a pinned download goes on -- nothing is paused, nothing on disk is touched, and a stream request that arrives while lean is served like any other (the embed test streams the head of a file while lean), just from fewer peers.** What it drops: the per-torrent live-peer cap goes to `LEAN_PEER_LIMIT` (8 -- a client uploads to four or five unchoked peers at a time and a home uplink saturates before that, so eight is the unchoke set with headroom for churn; the number is argued on the constant) and the surplus is hung up, least useful first (peers still connecting, then peers that have nothing we need and want nothing from us, fewest bytes exchanged first); and the peer table is pruned of every `Dead` and `NotNeeded` entry. **Only the `NotNeeded` half of that pruning is free** -- those are peers we hung up on, and the table kept them to remember not to dial them again -- while a `Dead` entry is the opposite, a peer waiting out a backoff *to be re-dialled*, and forgetting one cancels the reconnect: it comes back only when a tracker, the DHT or PEX names it again, or when it dials us. Both go anyway, because the table is the thing lean is shrinking (4224 addresses after one download, each with counters and backoff state) and a reconnect on a timer is the last thing a backgrounded app wants; the fork offers no state-filtered variant and asking for one would trade the larger half of the saving for reconnects we are trying not to make. The lever is the fork's, at the pinned rev: `ManagedTorrent::set_peer_limit` (runtime cap on the live state's peer semaphore; a lowered cap forgets permits as the parked peers return them, so the cap holds without a second pass; a raised cap re-queues the parked `NotNeeded` peers) and `TorrentStateLive::forget_disconnected_peers`. **The return to `Full` is not instant and the parked peers are not first**: `reconnect_all_not_needed_peers` pushes them onto the *tail* of the same FIFO queue every tracker/DHT/PEX address joins, so in the field they are dialled behind whatever backlog is waiting (in the cap's own tests there is no tracker and no DHT, so the queue is empty and they do come back at once -- which is what made the claim look true). It also re-queues every *other* `NotNeeded` outgoing peer, not only the ones the cap parked. Three things about the order are load-bearing. **Prune before lowering, never after**: the peers the lower cap parks are `NotNeeded` too, and pruned they are gone for good -- `Full` would have nobody to re-dial. **A repeated `Lean` is a no-op at the backend** (`LibrqbitBackend::set_footprint` returns early on the footprint it already has) for the same reason: a second prune would take the parked peers. And **an add reads and applies the footprint under the same mutex a change holds** while it walks the session's torrents, so a torrent added during a change ends with the footprint that won; a torrent that is not yet live takes the cap for when it is (`ManagedTorrentShared::peer_limit`). `PeerDiscovery::known` (additive in `stats.json`'s `peerDiscovery`) is the table's length -- the figure that shows the pruning; `seen`/`unique` is cumulative and never goes down. The Flutter/JNI half (calling this from the lifecycle hooks, pausing mpv, dropping the image cache) is the app's; `src/jni.rs` is untouched by this.
