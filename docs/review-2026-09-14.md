## Details

### 0. A piece reserved whole while deep is never split or doubled once it drifts to the head

**[high] rq:tracker -- `crates/librqbit/src/piece_tracker.rs:619`**

**Claim.** Splitting happens only in the `None` (not yet in flight) branch of the priority walk, gated on `deep < DEADLINE_PIECES`. A piece that entered the in-flight map whole at depth >= 2 keeps its single whole claim forever; when the stream advances and it becomes depth 0 the `Some(inflight)` branch calls `claim()`, `unclaimed` is empty, and `lagging_claim` needs `proven?` -- a proof a non-holder can never have on a piece with no other claims to finish. The only remaining rescue is `steal_piece` at 10x. In the shipped configuration (32 MiB lookahead, 4 MiB pieces = 8 pieces; 17 seeders with 128-chunk windows) every piece is reserved whole the moment it enters the window at depth 7, so in steady-state playback the head pieces are always whole-held pieces that drifted in, and the field case (a read blocked on one slow peer's whole piece while sixteen others were turned away) is back for every piece except those that entered the window at the head (startup, seek, re-queue after a release). The doc argues the opposite.

**Failure.** Stream at piece 100, lookahead 100..108; peer S (slow, 200 kB/s) reserves piece 107 whole at depth 7. Twenty seconds later the reader is at 107, blocked; sixteen fast seeders call acquire_piece: `claim()` returns None (no unclaimed, no proof), `held_priority_piece = 107`, `steal_piece` requires 10x and per-piece lock; they all go fetch 108..115 instead. Read blocks until S finishes 4 MiB. Test `only_the_head_of_the_lookahead_is_split` uses a static window so nothing fails; no test advances a window over a whole-held piece.

**Fix.** In the `Some(inflight)` branch at `deep < DEADLINE_PIECES`, if the piece has one participant holding it whole (`unclaimed.is_empty() && participants.len()==1 && chunks == 0..n`), convert it to a split piece: shrink the holder's claim to the first ceil(window/CLAIM_CHUNKS) claims (what it can already have requested) and pool the rest, so the asker gets a share. Revert-proof: reserve piece 2 whole via a 3-piece window as peer 1, then acquire with window [2,3,4] as peer 2 and assert `Reserved { piece: 2, chunks }` with `chunks != 0..n`; today it reserves piece 3.

**Verifier's correction.** The finding is right in direction but understates the exposure and misattributes its origin. (1) It is not only pieces reserved whole at depth >= 2 inside the window: with 17 hungry seeders and an 8-piece window, once the window is spoken for every further peer reserves pieces beyond the window from the ordinary queue (step 2, always `split=false`), so nearly every piece the stream will ever reach is already whole-held by one peer before it enters the window -- at depth 0 as much as depth 7. Splitting effectively applies only at startup, after a seek, or after a release re-queues a piece. (2) Because `deep` counts only takeable non-have pieces, a piece that is NOT yet in flight when it enters the window in a fast swarm would be at depth 0 and split -- but with seeders reserving ahead from the queue that case rarely arises. (3) This is not a regression of bb6bad9b: the first splitting commit 3b387e11 also had `claim()` pop only `unclaimed` and never converted a whole-held piece, so the gap has existed for the whole delta; bb6bad9b merely widened it by also making depth >= 2 window pieces whole. (4) The 10x steal can fire sooner than the slow peer's full piece time (10 x a fast peer's ~0.3-0.5 s avg), but only from a peer with a recorded whole-piece average and a free per-piece lock, and it hands the piece to one peer whole again; it was already present when the field case was measured, so it is not a reliable rescue. The proposed fix (convert a single-participant, whole-claim piece to a split piece in the `Some` arm when `deep < DEADLINE_PIECES`, shrinking the holder's claim to what its request window can already cover) and the proposed revert-proof test are sound; the probe I ran shows today's outcome is `Reserved { piece: 3, chunks: 0..16 }`.

### 1. The floor is now two numbers: the reconciler still stops at 512 MB while the stream route and cap admit at total/32

**[high] ss:engine -- `enginefs/src/reconcile.rs:389`**

**Claim.** Commit 44796b7 makes `ensure_download_disk_ready` (server/src/routes/stream.rs:606) and the published cap (server/src/cache_budget.rs:306) use `free_space_floor(volume_total(root))`, but every reader in the engine that decides whether a torrent runs or is reported stopped still uses the constant: `reconcile::line` returns `CACHE_FREE_SPACE_FLOOR` for a Live torrent, `resume_line()` (reconcile.rs:508) and `Volumes::record` (reconcile.rs:472) add the margin to the constant, and `Engine::is_stopped_for_space` (engine.rs:1495) passes `crate::CACHE_FREE_SPACE_FLOOR` to `volume_is_short`. `server/src/proxy_cache.rs:347` and `server/src/routes/archive.rs:217` also still use the constant. The doc on the constant (lib.rs:43-47, "One number, three readers, and it is one number so they cannot drift") and the comment above the stream gate (stream.rs:600-602, "the same one the engine's reconciler stops a torrent at") both now assert something the code no longer does.

**Failure.** The exact device the commit is for: a 4 GB Chromecast with 422 MB free. The stream route now admits the request (required = 128 MB), cache_budget publishes a cap with ~294 MB of headroom, the entity's allowance grows into it -- and the reconciler's next tick (<= 2 s) evaluates `line(Timer, Live)` = 512 MB > 422 MB and stops the torrent for space; `Volumes::record` starts the stall clock because 422 MB < 576 MB; after STOPPED_READ_STALL_BOUND the reads fail with StorageFull and the player's next request meets `is_stopped_for_space()` = true and a 507. The device is exactly as unusable as before, now with a 2 s tease. More generally, on any volume under 16 GB the cap publisher and the reconciler are sized against different floors, so the owner is allowed bytes the reconciler will stop it for writing. No test exercises the two together: `the_floor_is_a_share_of_the_volume_it_holds_back` only tests the pure function, and every reconciler test still asserts against the constant.

**Fix.** Make the engine's floor volume-sized too, from the reading it belongs to: have `Volumes::record` take (available, total) -- one `fs4::statvfs(path)` gives both -- and store `floor = free_space_floor(total)` beside `available`; make `line`, `resume_line`, `volume_is_short`'s callers (`desired`, `is_stopped_for_space`, `held_stopped_for_space`, the `after_stopping_for_space` log, lib.rs:1882) read that floor rather than the constant; switch proxy_cache.rs:347 and archive.rs:217 to the same source; then update the constant's doc and the stream.rs comment. Revert-proof: a reconciler test with `set_free_space_probe` answering 422 MiB on a 4 GiB total that asserts a Live torrent is NOT stopped and `is_stopped_for_space()` is false, and a server test that `ensure_download_disk_ready` and `reconcile::desired` reach the same verdict for the same probe -- both fail today.

**Verifier's correction.** Right in direction; one detail is wrong in the reviewer's favour. The failure is not deferred to the reconciler's next 2 s tick: the stream route itself runs `focus_torrent` -> `reconcile_hash(Trigger::PlaybackStart)` (stream.rs:1235, lib.rs:3270) immediately after the disk gate, and `line(PlaybackStart, _)` is `CACHE_FREE_SPACE_FLOOR` (reconcile.rs:389), so on a 4 GiB volume with 422 MiB free the same request that passed the 128 MiB gate stops its own torrent for space before the first byte is served. And for a torrent the reconciler has already stopped, `is_stopped_for_space()` (engine.rs:1496, at 512 MiB) is checked first in `first_complaint` (stream.rs:753-762), so the route returns 507 without ever consulting the volume-sized `ensure_download_disk_ready` -- on that path the commit changed nothing at all.
