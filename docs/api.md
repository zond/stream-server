# API: the HTTP routes and the library

The reference for both of the server's surfaces: the HTTP routes, which exist for players and for stremio-core, and `ServerHandle`, which is how the app itself talks to the server. The [README](../README.md#the-http-surface) has the summary and the rule about adding routes; what the numbers in `stats.json` mean is [stats.md](stats.md).

## Who speaks HTTP to it

**Why this server speaks HTTP at all, and to whom.** This crate is a library the app links; the app calls it through `ServerHandle` ([Library API](#library-api)) and never opens an HTTP connection to it. HTTP exists for exactly two callers, and `build_router()` (`server/src/lib.rs`) is split along that line:

- **Players fetch media by URL** -- mpv, or a Chromecast receiver through the [LAN media listener](lan-media.md), which serves `/cast/{token}` for the ids the app published and nothing else. They cannot attach a header, so **media routes are OPEN**, and a route that hands a player bytes belongs there (`media_router()`).
- **stremio-core's `StreamingServer` model speaks Stremio's streaming-server protocol** over HTTP, through the app's `Env::fetch`, which attaches the bearer. Our fork of stremio-core is changed as little as possible -- by policy, so it keeps following upstream -- so the routes it calls stay exactly as it calls them. That is `control_router()`, and it is **all** of `control_router()`: `/settings`, `/create`, `/{infoHash}/create`, `/{infoHash}/{fileIdx}/stats.json`, `/network-info`, `/device-info`, `/get-https`, `/casting`, `/casting/{devID}/player`. (The archive `/create`s stremio-core builds are URLs it hands a player, so they are media routes.) Every one of these requires `Authorization: Bearer <token>`, header only -- a token in the query string is never accepted, so it does not end up in access logs or in URLs handed to third parties. A missing or wrong token gets `401` with the fixed body `unauthorized` and `WWW-Authenticate: Bearer`; the compare is constant-time.

**There is no third caller and none is planned.** **Do not add a control route**: a new capability is a `ServerHandle` method, a new byte-serving URL for a player is a media route, and a route appears in `control_router()` only when the core fork starts calling a path it did not call before -- which is a change to the core fork first. The control routes that once mirrored the embed API are gone; see [Removed routes](#removed-routes).

## Authentication

`ServerConfig.auth: ServerAuth` has one variant, `Generated`: 32 random bytes, hex-encoded, fresh per launch. The embedder reads it off `ServerHandle::auth_token()`; it is never passed to `tracing`, so it is in no log file, and it never reaches stdout.

**There is no way to start this server without a token**, and no way to choose one: an embedder reads the generated token off the handle, so a chosen secret would buy nothing, and an open control API on a machine that also runs a browser is a hole nothing here asked for.

## Archive members

The design is [design/translated-sources.md](design/translated-sources.md); this is what a caller sees. RAR routes return a `501` JSON error in a `--no-default-features` build, and `/tgz` answers `415` for every member: gzip has no way in at the middle.

A member is served with ranges, with the same framing a plain file gets from the stream route (`Content-Length`, `Content-Range`, `206`/`416`, `HEAD`): an unsatisfiable `Range` is `416` with `Content-Range: bytes */<len>`, and an empty member is an empty body.

**Every container is read as byte ranges and nothing is stored.** `/{zip|tar|rar|7zip|iso}/create` with `urls` reads the archive's index through the same ranged reads and the same cache `/proxy` uses -- the end record, the central directory, one local header per stored member for a ZIP; one 512-byte header per member for a TAR; each volume's headers for a RAR; the signature header and the packed index at the end for a 7z; the descriptors and the directory tree for an image -- and remembers *that*: an index in memory, no file. A member's bytes are then a range of the archive, so a range request for the film is one ranged request at the origin, a seek is one more, and **nothing is ever written under the cache root**. The `torrent:` form (`/{fmt}/stream/torrent:<infoHash>%2F<path>/{member}`) is the same thing over a torrent's own file: a seek in the member is a seek in the piece store. **The index is kept for as long as the bytes it indexes are** -- while nothing else has been opened -- and not for a fixed idle time: a player or a cast receiver that has paused still has its `{key}`, and what takes the session is the viewer starting something else, the same event that makes the cached bytes disposable. An origin that answers a ranged request with the whole file is **refused** with `501` and a sentence saying so -- serving it would mean downloading the archive to reach the member, which is the thing this design exists to stop.

**A member that cannot be pointed at is refused, not unpacked.** A compressed or encrypted member, a solid block, and a `.tar.gz` as a whole are `415` with `{"refused": "...", "message": "..."}` -- one sentence, for a player to show; an archive that contradicts itself is `422`. Reaching the end of a deflated film means inflating all of it, and this server does not download a file to seek in it.

**A RAR set is its volumes, in order.** A film in a RAR is a film across `film.part1.rar`, `film.part2.rar`, ... (or `film.rar`, `film.r00`, `film.r01`, ...) far more often than in one file, and a member of a set is a *part* of each volume. `/rar/create` takes the `urls` list as the volume list in the order it was given -- which is what stremio-core builds from an addon's `rarUrls` -- and the `torrent:` form finds the volumes among the sibling files of the one named, by those two naming rules and nothing else. The member is then one range of each volume, and a range request that crosses a volume boundary is answered from both. A set with a gap in its run is `422`, **naming the volume it wanted**, rather than a film with a silent hole in it; a file named under neither rule is one volume. Stored members only: a compressed, encrypted or solid RAR is refused like any other (above), and an encrypted stored member is refused too, whose bytes the layout could map -- there is no password UX, and a wrong guess is ciphertext to the player.

**A 7z is refused unless it is stored.** `/7zip/create` reads the archive's index the same way as the rest -- the 32-byte signature header at the front and the packed index at the back, which is where 7z keeps it -- and a file whose block is a single COPY coder with no encryption is byte ranges of the archive, like a stored ZIP member. Everything else is `415`: LZMA2 (what `7z a` writes by default, and what a 7z of a film off the internet nearly always is) as `compressed` naming the method, an AES coder as `encrypted`, and a block that is not COPY and holds several files as `solid` -- reaching the second file there means decoding the first, so no decoder could enter at it either. A multi-part set (`.7z.001`, `.7z.002`, ...) is `422` saying it is one file cut up: joining the parts is fetching all of them.

## Library API

**This is the control surface.** An embedder holds a `ServerHandle` (from `stream_server::start`) and does everything through it; there is no HTTP client in the app and, for most of these, no route at all. A method that needs the server's runtime runs on it and blocks the calling thread until done (a few -- `set_background`, `is_background`, `close_proxy_streams`, `dht_status`, `proxy_streams_live`, `proxy_download_key`, `torrent_listen_addr`, `lan_media_addr`, `lan_media_running`, `lan_media_requests_served`, `lan_media_bodies_served`, `release_player`, `publish`, `unpublish`, `install_producer`, `publish_rendition`, `prepare_rendition`, `rendition_state`, `rendition_readiness`, `rendition_restarts` -- answer synchronously without one, and the three `note_*` calls are `async`, awaited on the caller's runtime); all returned types are `serde`-serializable, so they can be passed as JSON over FFI. Where a method shares its function with one of the core-protocol routes, the "Same as" column says which, so the core and the app can never see two servers:

| `publish(&MediaId, Option<PlayToken>) -> Result<CastToken>` / `unpublish(&CastToken) -> bool` | no route of its own -- publish an id for a cast and get the token the receiver's URL ends in, `<lan_media_base_url>/cast/<token>`: 128 random bits, never derived from the id, memory only. Refused while the LAN listener is not running and for an id this server does not hold; the publication holds the id against eviction. With a `PlayToken` the receiver's reads are the viewer's playback, by `open_reader`'s rules. `unpublish` ends every body being served under the token at once; stopping the listener unpublishes every token. See [LAN media listener](lan-media.md#tokens) |
| `install_producer(Arc<dyn Producer>)` | no route -- install the embedder's rendition producer (`stream_server::rendition`: `Producer::start(Job)` with `Job {reader, spec, from, wants_index, sink}`, the blocking `SampleSink {format, index, sample, end, fail}` (`index` the source's `IndexEntry {pts_us, pos}` list when `wants_index`), `Sample {track, pts_us, key, data}`, `TrackFormat`), which `publish_rendition` needs. Once, after the server starts; a second call replaces it for renditions published afterwards. Rust API for the embedder's crate, not FRB's. See [design/renditions.md](design/renditions.md) §2.2 |
| `publish_rendition(&MediaId, RenditionSpec, Option<PlayToken>) -> Result<CastToken>` | no route of its own -- publish a rendition of an id for a cast -- one progressive fragmented MP4 with a length and ranges, which the receiver seeks in by bytes -- under a token by `publish`'s rules; the receiver is handed `<lan_media_base_url>/cast/<token>/stream.mp4`, and told to start at `startMs`, where the first run starts. `RenditionSpec {durationMs, segmentMs` (the slot grid of a source without an index; one with an index is cut at its sync samples)`, startMs, video: "copy" \| {h264: {width, height, bitrate}}, audio: "copy" \| {aacStereo: {bitrate}}, audioTrack}`. Refused while the LAN listener is down, for an id this server does not hold, and (`noProducer`) with no producer installed. No run starts until the receiver asks. See [LAN media listener](lan-media.md#renditions) |
| `rendition_state(&CastToken) -> RenditionState` | no route -- `{"state": "producing"}`, `"idle"`, `"failed"` with the `sentence` to show the viewer, or `"ended"` for a token not published (any more) or not a rendition. Cheap, no runtime hop, safe to poll from the cast watchdog |
| `prepare_rendition(&CastToken) -> bool` | no route -- make a published rendition's start with no receiver asking: the first run, the layout from the source's index, the header, slot 0, and the slot `startMs` falls in with those of the 6 s after it (a receiver asks for the file's start and then for exactly that slot; nothing before it is made). Returns at once; `rendition_readiness` says how far it has got, so the app loads the receiver at `ready`. Waits on a stalled source with no give-up timer; `unpublish` ends it. A second call is a no-op. Whether the token is a published rendition. See [LAN media listener](lan-media.md#renditions) |
| `rendition_readiness(&CastToken) -> RenditionReadiness` | no route -- how far a preparation has got: `{"phase": "index"}` (the source's index and formats), `"start"` (the receiver's first slots), `"ready"`, `"failed"` with the `sentence`, or `"ended"` for a token not published (any more) or not a rendition. Cheap, no runtime hop, safe to poll |
| `lan_media_base_url(for_peer: IpAddr) -> Option<Url>` | the base URL to hand a receiver at `for_peer` -- host = the local interface on its subnet, or the best-ranked one when nothing matches. `None` while the listener is off |
| `http_addr()` / `bound_http_addr()` / `torrent_listen_addr()` | the connectable and the bound HTTP address, and the address librqbit accepts peers on (`None` when it is not listening) |
| `shutdown()` / `join()` | stop the server / wait for it to stop |

Where a core-protocol route and a method answer the same question (`/settings`, the per-file stats), they call one function (`routes::system::{file_stats, update_settings}`), so they cannot drift; `server/tests/embed.rs` compares them. Everything else here has no HTTP twin to drift from.

## Removed routes

**2026-09-26: the control routes that mirrored the embed API.** `/heartbeat`, `/stats.json` (with its `?sys=1` probe), `/{infoHash}/stats.json`, `POST`/`DELETE /{infoHash}/{fileIdx}/download`, `GET /downloads.json`, `POST /downloads`, `DELETE /downloads/{key}`, `GET /cache.json`, `POST /cache/clean`, `GET /stream-numbers.json`, `POST /proxy-streams/{token}/close` and `POST /drive/create`. Each was a token-protected HTTP twin of a `ServerHandle` method, kept from the standalone daemon this fork started as. The app calls the methods over FFI and never had an HTTP client; stremio-core never called any of them; the only caller was this repository's own tests, which now call the handle. Keeping them meant a second front door to every capability -- one that took a credential in a body (`/drive/create`), one that could cut another device's playback (`/proxy-streams`), one that deleted files (`DELETE …/download`) -- for nobody. The methods are unchanged; see [Library API](#library-api). What remains of the control router is exactly the streaming-server protocol the core fork speaks, listed under [Routes](#routes), and [Who speaks HTTP to it](#who-speaks-http-to-it) says why nothing gets added to it.

Everything below existed for server.js compatibility and had no consumer in stremio-core, the Flutter client or the tests; it was removed to shrink the attack surface to what is actually used:

- `/` (redirect to web.stremio.com), `/favicon.ico`, `/thumb.jpg`, `/samples/{filename}` -- desktop/web-UI leftovers.
- `/list`, `/removeAll`, `/{infoHash}/remove`, `/{infoHash}/peers`, the `GET` variants of `/create` and `/{infoHash}/create` -- engine management nothing called (stremio-core POSTs).
- `/diagnostics/*` -- local debugging endpoints. The periodic memory sampler that logged alongside them is gone too; the process figures it read are now taken only by the panic hook, which puts them in the crash line.
- All subtitles routes (`/subtitles.vtt`, `/subtitles.{ext}`, `/{infoHash}/{fileIdx}/subtitles.vtt`, `/opensubHash`, `/opensubHash/{infoHash}/{fileIdx}`, `/subtitlesTracks`) and the engine code behind them -- the client fetches addon subtitles and selects tracks itself.
- `/update/*` and the self-update manager plus the `stream-server-updater` helper binary -- desktop baggage.
- `/{ipc_key}/downloader/*` -- stubs for an HTTP downloader that was never implemented.
- `/local-addon/*` -- the local-files Stremio addon (scanned `localFiles/` directory, catalogs, `bt:`/`local:` metas). **A stub remains** (the `/local-addon` rows of the table above), because stremio-core's default and account-synced profiles carry a protected descriptor for it and request its `stream` and `catalog` resources on every details page and board refresh; a `404` there shows up as an error group in the client and an ERROR-level log line each time. The stub answers an empty manifest, `{"streams": []}` and `{"metas": []}`, serves no local files, and logs its own intended 404s at debug.
- `/casting/transcode`, `/casting/convert`, `GET /casting/{devID}` and the `501` stubs for `/ftp/create*` and `/ftp/stream*`.

**Usenet (NZB)**: `/nzb/create*` and `/nzb/stream*` are gone, with the NNTP client and yEnc decoder behind them. stremio-core still builds `/nzb/create` for an addon's `nzbUrl` streams; no route here serves it, and as a two-segment path ending in `create` it matches the control route `POST /{infoHash}/create`, so it is refused and never serves media. The feature never worked end to end: article bodies were read as UTF-8 text, so binary data did not survive, and the connection pool was never refilled. Its routes were also open, fetching a caller-named URL and opening connections to caller-named news servers.

**YouTube**: stremio-core builds `/yt/{id}` URLs for `StreamSource::YouTube` when a streaming server is configured; this server has no `/yt` route, so YouTube-via-server is unsupported and a client has to open YouTube streams itself. `/yt/{id}` is two segments as well and lands in the `/{infoHash}/{fileIdx}` stream route, which tries to add `yt` as an info hash and answers with an error, never media.
