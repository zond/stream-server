# Storage: downloads and the cache

Where torrent and proxied bytes live, what keeps them and what takes them: offline downloads, the bound on the cache, and the two calls a storage screen uses. The design behind the retention owner is [design/read-pattern-retention.md](design/read-pattern-retention.md); downloads of non-torrent sources are [design/generic-downloads.md](design/generic-downloads.md).

## Offline downloads

A **pinned** file stays wanted no matter which file of the torrent is being played, and its torrent is exempt from idle removal and keeps running when nothing is playing, for as long as it has a pinned file -- and nothing ever reclaims a byte of it: a pin is kept until it is unpinned, whatever the cache is doing. A pin is per file: the torrent's other files are cached like any unpinned file, windowed while they play and given back after, except for the pieces they share with the pinned one. **Pinning is a retention property, not a location**: a pinned download is not written anywhere else, does not move, and is stored one file per piece under the store's single root exactly like a torrent that is only being streamed. `stats.json` reports `pinnedFiles` and, per file, `pinned` and `complete` (`downloaded == length`).

- **Pin by id**: `ServerHandle::pin(&MediaId)` pins whatever a media id names, through the pin paths below: a torrent file through `pin_download` (with the URL's `tr=` trackers, and `-1` chosen as the stream route chooses it), a link through `pin_proxy_download`'s link half keyed with its `h=` headers, a Drive file under a grant asked of the id's `GrantSupplier` (none is asked for a file already whole on the disk: no grant and not whole is `ProxyPinError::NoGrant`). A member of a container pins its container -- every volume of a set -- since a member is ranges of those files. A file on this device is `PinError::NothingToDownload`. It answers the rows `downloads()` lists for it, one per file pinned. `ServerHandle::unpin(&MediaId, delete_files)` drops the same pins (`unpin_download`/`unpin_proxy_download` per file, outcomes joined: `unpinned` if any pin went, `deletedFiles` if any bytes did); a torrent URL with an explicit index is unpinned without resolving, so a dormant pin's torrent is never added to learn it. The info-hash and key methods below stay; these dispatch to them.
- **Pin**: `ServerHandle::pin_download(info_hash, file_idx, trackers)`. `trackers` may be empty; a stream's own `sources`/`announce` array can be passed as is, and, as everywhere else, it only matters when this call is the one that creates the engine. Idempotent. The answer is one `DownloadInfo`: `{infoHash, fileIdx, path, name, length, downloaded, complete, phase, error}` (and, for a non-torrent download, `source` and `playUrl`). A file the torrent does not have is `PinDownloadError::FileNotFound`, a disk without room `InsufficientSpace`, a magnet that never resolved `MagnetAdd` -- `PinDownloadError::client_message` is the sentence to show, and it names no local path.
- **List**: `ServerHandle::downloads()` -- the same `DownloadInfo` shape, one entry per pinned file, ordered by info hash then file index, torrent rows first and non-torrent rows after them. A dormant pin (see *Restarts* below) is listed last, and answered by the disk: **with no `.pieces/<infoHash>` directory** this server holds nothing of it and knows so, and the row says held-nothing -- `complete: false`, `downloaded: 0`, `phase: "buffering"`, no `error` -- which a client reads as "not whole" (xtremio marks a finished row gone); **with one**, what it holds is unknown until the torrent comes back, and the row is `phase: "error"` with an `error` explaining that its torrent is not managed right now. `path`/`length`/`downloaded` are unknown (`null`/`0`) either way. Every pin the embedder hands in after the boot that deleted the previous build's cache directory (*Where*, below) is the first kind. `ServerHandle::download_path(info_hash, file_idx)` returns just the `path` without creating anything. It is a name and not a file: torrent data is stored one file per piece, so nothing is ever written at that path and a client plays a completed download through the media routes like any other.
- **Unpin**: `ServerHandle::unpin_download(info_hash, file_idx, delete_files)` answers an `UnpinOutcome {unpinned, deleted_files}`; `unpinned: false` means nothing was pinned, and `deleted_files` reports what actually left the disk rather than echoing the flag -- a delete that found nothing to take says `false`, and a failed delete is logged, not raised. Without `delete_files` only the pin goes: the bytes stay and the torrent is ordinary evictable cache again -- the download stops being shared, which ends with its torrent leaving the swarm before its bytes go (see [Sharing](#sharing)). With it the data goes too, **and now**: a delete is an explicit request, so it happens whatever `seedingEnabled` says and whoever's play session is on the torrent -- the whole torrent (pieces, session record, folder) when this was its last pin **and nothing else is on the torrent** (the activity registers and the viewer's session are asked first, so a season pack whose pinned episode 1 is deleted while episode 2 plays keeps running and loses only episode 1), otherwise only the one file, with the torrent out of the swarm first: it stops, the file's bytes go, what a play session drew of the file goes with them, and it starts again only for what still needs it (another pin, a session or a read on another file). A piece the file shares with a still-pinned neighbour stays, announced for the neighbour, and the rest of the file goes. The answer waits for every unlink the delete set going -- the slack drop its end of shares makes included, which would otherwise race the delete's own drop for the same pieces and leave it measuring a disk not yet freed -- so `deleted_files` is never `false` for bytes that leave a moment later. The one thing a delete waits for is a read of that very file -- in practice a cast in progress: the pin and the download's entry go at once, and the bytes the moment that read ends. Deleting the last pin therefore also drops files that were only ever streamed beside it. `delete_files` does not need the file to have been pinned, but it does need the file to exist: an unknown `file_idx` is `FileNotFound`, never a request to delete the whole torrent.
  - **A per-file delete is two deletions**: the pieces the backend agrees to give up (`drop_pieces` forgets them and hands the indices back for the caller to unlink), and any whole-file copy already at the path the backend reports. That copy is truncated before it is unlinked, because librqbit holds an open handle on every file of a running torrent, and it stops being the torrent's active file first so the re-planned want-set cannot start refilling the unlinked inode.
  - **A dormant pin's directory** (see *Restarts*) is removed by `delete_files` once no file of that torrent is pinned any more. **"The backend does not have it" is checked, not inferred from the engine registry**: the registry can lose an engine while the session keeps the torrent (the idle sweep mid-step), and a magnet add parks a hash outside both. So the piece directory is deleted by hand only for a hash the session has never heard of; a torrent the session holds is deleted through the session, which drops it before its storage releases the pieces; a hash being added right now is left alone and answers `deletedFiles: false`.
- **Where**: nowhere in particular. A torrent's data is one file per piece under the store's single root (`<cacheRoot>/media-cache/.pieces/<infoHash>`, the directory being `enginefs::CACHE_DIR_NAME`), for the streaming cache and offline downloads alike; **a pin changes what is kept, not where**. A torrent streamed first and pinned later does not move, the engine every open reader holds stays the engine, and `path` is the name the backend gave the file. The one torrent-data root is `settings.cacheRoot`: set to an absolute path it is checked, created if missing (a refused setting leaves no directory behind) and stored resolved; the update fails if it is not a string, is relative, or cannot be created or written. **A running librqbit session cannot move to a new root**, so a change takes effect at the next start, where the value is prepared before anything opens on it and one that can no longer be used falls back to the configured cache directory -- persisted, so `settings()`, the file and the next boot agree.
  - **The directory was `rqbit-downloads` before**, and there is **no migration**: the first boot that finds `<cacheRoot>/rqbit-downloads` deletes it -- the torrent pieces, the proxy cache, librqbit's `session.json` and DHT state, and every pinned download's bytes with them. Before the session opens it is renamed to `<cacheRoot>/.rqbit-downloads.deleting` (cheap, at the cache root, outside anything the launch sweep walks), and after it the rename is deleted on the blocking pool, so the boot does not wait for a store of one file per piece to be unlinked. A boot that finds a `.rqbit-downloads.deleting` -- a process killed mid-delete -- deletes it too. The pins the embedder hands in then name torrents the session never restored: dormant, with no piece directory, so held-nothing (*List*, above).
- **Free space**: a pin is refused (`PinDownloadError::InsufficientSpace`) when the piece store's volume has less than the pinned file's missing bytes plus a **500 MiB margin** (`PIN_FREE_SPACE_MARGIN`). Only the missing bytes are asked for, because that is all a pin writes: re-pinning a complete file needs nothing, and a torrent still `checking` is not measured at all (its `downloaded` reads 0 until the check ends). A whole-file download already at the path is not data in place and is measured for the whole file. A refused pin **drops the torrent it added and leaves every byte where it is** -- the refusal comes before anything is downloaded, and what the store already held stays slack. A torrent the pin merely joined (a stream's in-flight add) is not dropped, nor is one a reader took hold of *while the pin was checking* -- the engine is published before the check, so the live activity registers are consulted as well as the join count.
- **Restarts**: librqbit persists each torrent's place and want-set and, with fastresume, its verified pieces (`<cacheRoot>/media-cache/<infoHash>.bitv`), so a pinned download resumes where it was without a full re-hash; the pin set itself is the embedder's, handed in at startup (`ServerConfig::pins`, one `PinKey` per download: `{"kind": "torrent", "infoHash", "fileIdx"}`, `{"kind": "url", "target", "headers"}` or `{"kind": "drive", "fileId"}`) and applied to the torrents the session brought back -- its torrent keys to the piece store, its link and Drive keys to the proxy cache. A pin whose torrent the session did not bring back (a record librqbit could not restore -- an unparseable `.torrent`, an add that errored) is held dormant for the run, until the torrent returns -- on a later boot, or with the next pin of the same torrent, which applies the dormant pins alongside its own -- or until it is unpinned.
- **Non-torrent downloads**: an addon URL or a Drive file is pinned with `ServerHandle::pin_proxy_download` (or `pin` by id) and kept in the proxy cache under a pin the embedder hands in at boot (the `url` and `drive` keys of `ServerConfig::pins`: `None` sweeps nothing and exempts nothing, a list with none of them sweeps the proxy cache clean at launch). A filler fetches it whole; its `downloads()` row carries `source` and a `playUrl`, `/downloads/{key}/stream`, which serves the pinned entry by range. The design is [design/generic-downloads.md](design/generic-downloads.md).
- **No pin set**: a server handed none (`ServerConfig::pins: None`, the default, so an embedder that keeps no pin record gets this) cannot tell a pin from cache, so for the life of the process it treats **every torrent as pinned** (`PinsUnknown`): the launch sweep deletes no torrent data, the retention owner reclaims none, the reconciler keeps every torrent running (the free-space arm aside) and the idle sweep removes none, and `downloads()` lists every file of every torrent the server holds; the proxy cache's launch sweep takes nothing either. Only the free-space floor bounds torrent data then; the proxy cache is bounded as always. **There is one set for both stores**: an embedder that cannot say what one store's pins are says `None` for the whole, since a set that names the torrents and not the links would have the sweep delete every link download. An embedder that passes an empty list is saying the opposite -- nothing is pinned -- and both sweeps take everything unclaimed. xtremio passes the downloads the user asked for.

## What bounds the cache

**Every entity under the one root -- a file of a torrent, or one proxied body -- has exactly one retention owner that knows whether anybody wants it** (the piece store's for torrents, the proxy cache's for proxied bodies), and nothing walks the disk looking for victims. The root is `settings.cacheRoot`, taken from the running engine rather than from the setting, since a root set for the next start is not where the bytes are now.

**The cap is the smaller of `cacheSize` and what the filesystem can give**: `cacheSize` unset is `u64::MAX`, which on a 4 GB television meant nothing bounded the cache and librqbit wrote until the filesystem refused -- an ENOSPC that arrives as a fatal torrent error, mid-film. So the server reads the volume's free space (`fs4::available_space` → `statvfs`: the raw `statfs` syscall on Linux, bionic's `statvfs` on Android, both `f_frsize * f_bavail`, i.e. `df`'s "Available") and caps the cache at `occupancy + available − floor`, keeping the **free-space floor** free: a thirty-second of the volume, clamped between 128 MiB and 512 MiB (`enginefs::free_space_floor`), so a phone keeps 512 MiB and a 4 GB television keeps 128 MiB and can still play; a volume that will not say its size keeps 512 MiB. The floor is the same number `routes::stream::ensure_download_disk_ready` demands before it will stream to disk at all -- below it that check asks both owners for their slack and, if the disk is still short, answers the stream `507 Insufficient Storage`. A volume that cannot be probed is not read as "full": the configured `cacheSize` then stands alone.

**A cap is a statement about one volume, and there is one root, so there is one cap.** `overLimit` stays as a field of its own -- how far over the cap the cache still is -- because it is what a client should read before telling a user that cleaning helped.

**What keeps a byte, and what takes it**: a **pin** is kept until it is unpinned, whatever else is happening; the **one stream being played** keeps the window round its playhead and the pieces of its shared set it holds (and any file an open reader is still delivering); **everything else is slack** -- the moment a viewer opens something else, what they left is disposable, and it goes at the switch itself, at the reconciler's next two-second tick, when the volume runs low, on `clean_cache_now`, at shutdown, or at the next boot. What the left play session announced to peers goes only once its torrent has left the swarm (see *Sharing* below). So stopping playback changes nothing on disk and resuming inside the window plays from the cache, while starting something else really does throw the previous stream away. At boot, before the session opens, the launch sweep deletes every piece directory the embedder's pin set does not name, and a previous release's data beside the store (below); the proxy cache is swept of every entity no proxy pin names, and any leftover `.archives` extraction directory is removed, before the router serves a request; a previous build's whole cache directory, `rqbit-downloads`, is renamed aside before the session opens and deleted after (see *Where* under [Offline downloads](#offline-downloads)). A boot handed no pin set sweeps no torrent data at all (see *Restarts* under [Offline downloads](#offline-downloads)).

**A stream that would not fit is refused rather than served by evicting something**: the `507` path drops every disposable byte, re-reads the volume and tries again, and if pins plus the live window still do not fit, the answer is `507` -- never a pin or a playing stream taken to make room.

What is nobody's is not kept: anything directly under `<cacheRoot>/media-cache` that is neither one of the owners' directories (`.pieces`, `.proxy`) nor a session record is not this store's own data -- a plain-file download (there is no migration: the torrent that owns it re-downloads as pieces), or a `.cache`/`.metadata` directory nothing here reads -- and is never counted; the launch sweep (`piece_store::sweep::sweep_legacy_downloads`) removes it whole on every start that is handed a pin set -- a start handed none keeps everything on the disk, that included. The session's records (`session.json`, `<infoHash>.torrent`, the `.bitv` bitfields, `dht.json`, `dht-bootstrap.json` and their temp files) are not cache and are never swept, and neither is a stray `pinned-downloads.json`. What `/proxy` cached is (`.proxy` under the cache root, see [Proxied remote streams](proxy.md#proxied-remote-streams)): counted in the same figure, capped by the same number, and kept by the same question -- is somebody inside these bytes right now?

**Sizes are what a file occupies, not its apparent length**: a storage that pre-allocates a file at its full length before any of it is downloaded turns a part-streamed film into a multi-gigabyte `length` over a handful of written blocks -- once measured as 17 GB of reported cache on a phone holding 3.85 GB. This server's piece-per-file store pre-allocates nothing, but a root can still hold a file pre-allocated before it did, and nothing migrates one away, so the rule stands regardless: Unix uses `st_blocks`; Windows has no cheap equivalent through `std`, so the apparent length still stands in there.

**Who keeps a torrent running is declared, not guessed** (`enginefs/src/retention/holds.rs`). The reconciler runs a torrent that is **held**, pinned, or the last one a stream opened on (the liveness cell, as before -- a stream without a player token declares nothing else); otherwise it stops it. The cell is no longer what keeps a torrent a player or a television is using: any other open moves it. A hold has an owner and a lifetime: **a player screen** holds the torrent its own `p=` requests named from the first one until the app says the screen is gone (`ServerHandle::release_player`), paused, stalled or with nothing open -- one per viewer, so a newer screen's hold replaces an older one's and a screen that never said goodbye holds nothing once the viewer plays anything else, and a request carrying a released screen's token holds nothing again; **a cast** holds its id's torrent from `publish`/`publish_rendition` to `unpublish` (or the listener's stop), taken while the screen still holds it so a hand-over to a television has no gap; and **a body being delivered** holds its torrent for exactly as long as it lasts. A held torrent's files keep their retention windows whatever the liveness cell names. Holds live in this process's memory: an app that is killed takes them with it, and a restart starts with none. This replaced reading "playing" off the liveness cell and the reads open at the tick, which stopped the torrent a television was waiting on the moment anything else opened (measured on a phone: `torrent_stopped_by_reconciler playing=false` just after a cast began).

**A full disk is a signal to give slack back, not to stop**: librqbit treats a write that hits `ENOSPC` as fatal and leaves the torrent in an error state, which is how a film died ninety minutes in.

**The engine stops a torrent before the filesystem has to**: the engine's free-space arm (the reconciler's, every 2 s, one `statvfs` of the volume every torrent's pieces land on) pauses a torrent that is writing (`Session::pause`: peers dropped, writes stopped, files and piece map kept -- pinned torrents included, since a pin is a reason to keep the bytes, not a licence to run the disk out) the moment the volume falls under the floor, and rings the running-low bell so both owners drop their slack at once -- so the torrent's readers see a buffering pause of a few seconds, not a dead stream. The reconciler restarts a torrent librqbit killed with ENOSPC once the volume is 64 MiB over the floor and something holds or pins it, at most once per 15 s.

**A proxied stream stops writing at the floor too**: before each chunk a `/proxy` fill asks the volume (one `statvfs`, re-read at most every 2 s, less what it has written since), and a chunk that would take the volume under the floor is not written; the player keeps getting the body from the origin, and a later seek back into it fetches again.

A torrent the free-space arm stopped says `phase: "error"` in its `stats.json`, with a fixed "stopped for want of disk space" message, for as long as it is stopped, and a `GET` for it drops both owners' slack and, if the volume is still short, is a `507`.

**A film larger than the free space plays anyway**, which is what the rolling piece window is for. Torrent data is one file per piece (the piece store is the session's default storage), so reclaiming a single piece is a `remove_file`, and `enginefs/src/retention.rs` drives it from what the reads are doing, on the reconciler's two-second tick: every consumer the read-pattern detector finds on the file -- a viewer, a second audio track, a player's index crawler -- is kept and fetched a lookahead ahead of where it has reached, the film's own bitrate times the seconds the buffer profile asks for, shared out between them when the disk cannot cover them all; up to half the budget is a set committed for sharing; and what puts the file over its allowance is given back, coldest first -- the backend told to forget it first, then the bytes, under one claim. The shared set is never given back while the torrent is in the swarm. Bytes behind a consumer are not given back on a schedule: they are simply the first to go when the room is needed, which is what makes a scrub back cheap without anyone having to decide how far back a viewer might go.

**What a resumed film fetches ahead of its resume point is ordinary cache, held by nothing.** A torrent film resumed halfway asks the swarm for the resume point while the player is still reading the file's head ([media-pipeline.md §2.11](design/media-pipeline.md)). Those pieces are not pinned, not promised and not counted as protected: once on the disk they are kept while there is room and given back in the same order as everything else when there is not -- by when a piece was last any use, which for one nothing has read yet is when it arrived -- and they are protected only when the player's own reads reach them. The only thing held for it is the 16 MiB step being asked for at that moment, as a playing stream's read-ahead is. It asks for no piece that could not be kept beside what the readers hold, measured at each pass from the budget and what is held, so it never takes a reader's piece and never puts the cache over its cap; there is no share of the cache set aside for it.

**The budget is published on its own timer**: `server/src/cache_budget.rs` states it from one `statvfs` and what the owners of the cache say they hold (a sum over the bits each piece store keeps, plus the proxy cache's running count -- no walk, no syscall), on a minute timer, at startup before the router serves a request, and whenever a client changes `cacheSize`. `ServerHandle::cache_usage` and `clean_cache_now` are how a client reads the cache's state and asks for its slack back on demand. See [Cache usage and cleaning](#cache-usage-and-cleaning).

## Sharing

A torrent announces nothing that nothing chose: the session runs under the fork's `explicit_piece_advertising`, so a torrent -- added, restored at start-up, restarted out of an error -- announces no piece until told, and serves a request only for a piece it announced. Two things choose:

- **A play session shares a set drawn once, and only the app's player has one.** A play session belongs to a viewer, and only a stream request carrying the player token (`p=<viewer>.<screen>`: a viewer id per install, a number per player screen) starts or moves it: to the file it names, the moment it names a different one (the next episode on its new screen, another title), or off every torrent for a `p=` request to `/proxy`. A request from an older screen of the viewer than the newest one heard from -- the last screen's player still reconnecting as the next takes over -- moves nothing. The same film opened on a new screen is no move at all; back to the board is none either, and the session's draw goes on being shared while the torrent runs. A request without `p=` -- a subtitle or side file, another client on the HTTP routes, everything a translated source reads for itself (its index, and a member read without a play) -- draws nothing, announces nothing and moves no session, and its bytes go like any unshared bytes. **A member played through an id shares its own extent, in one file or across every volume of a set; a container played by URL shares nothing.** A reader the app opens with a play over a media id naming a member of a single-file container inside a torrent -- a film in a stored RAR or ZIP, by the `torrent:` form -- puts the viewer's session on the container file together with the member's byte extent in it: the draw is sized from the member's length (and the film's rate is the member's length over its duration, told to the container for the draw alone -- the container's own read-ahead takes no rate from it, which for a season in one ZIP would be the season's) and made only among the pieces the member lies in, so a season in one ZIP shares the episode being watched and not the ZIP, and the container is not sniffed, since the member path already knows what it is. The draw is the member's: the next episode in the same ZIP is a move like any other, which ends the first episode's draw and draws the second's. The player's `p=` request for an archive's own file on the HTTP route still puts its session there sharing nothing, with the member read out of it without one; an archive is told there by its name at the request and by its first bytes before anything is drawn (RAR, ZIP, 7-Zip, ISO 9660, UDF, TAR -- whatever it is called), and the draw waits until they are held. A member of a multi-volume set (`film.part1.rar`, `film.part2.rar`, ...) played by id shares the same way across the set: the session is on the set -- every volume the member crosses, each with the member's bytes in it -- which is one thing played, so the reader crossing from one volume into the next moves nothing and ends nothing, and leaving the set (another film, another torrent) ends what it shared as leaving a film does. The set draws once, over the member's bytes in all of its volumes (sized from the member's whole length, and its rate that length over the film's duration, which is told to the volumes for the draw alone -- a volume's own read-ahead takes no rate from it): the first volume opened draws and announces the set, and every later volume keeps its own pieces of that draw and announces nothing new. A container behind links is a proxied entity and announces nothing. The draw is a uniformly random set of the file's pieces, sized by the budget left beside the stream's **real** read-ahead -- the film's bitrate times the seconds the viewer asked for -- and **nothing, when the budget cannot hold both**: playing wins. The bitrate is the film's size over the length the player states, which it does once it has opened the media, so the draw waits for it: nothing is announced before it anyway. A player that never states a length gets its draw after ten seconds of playback, sized beside what its opens asked for. Once drawn the set is advertised, each piece of it is announced the moment it has downloaded (or at once, if it is here already), and nothing else of the file ever is. Under a budget that covers the file the set is the whole file, read-ahead included: all of it is kept and shared for the session, and a panel's `committedBytes` counts it. Nothing the viewer does redraws it or grows it: a seek, a budget that rises or falls, a length stated later. The set is never fetched for -- a viewer who stops halfway shares about half of it.
- **A download is shared whole**, finished or not, and keeps being shared after it finishes, for as long as it is pinned.

**An announcement is never taken back** -- there is no un-Have in BitTorrent -- and it ends only with the torrent leaving the swarm. So when a player's session moves to anything else -- another torrent, or the next file of the same one -- the torrent it left is **stopped first** (peers disconnected), its advertised set is made again from what is still shared, it starts again at once if it is still wanted (the next episode waits on that rebuild and nothing else), and **then** the left session's files are deleted, on the side -- no longer advertised, so no longer anybody's; the next episode's reader never waits on an unlink. A torrent that stopped for any other reason has its advertised set made again before it starts, so it never comes back announcing a draw that went while it was stopped. **Nothing else stops a torrent that is being played but an explicit delete, and one viewer never stops it under another**: two viewers on two files of one torrent each keep what they left shared until neither is on the torrent. (With xtremio there is only ever one: the server is embedded in the app and dies with it, stremio-core is pinned to it, and the one outside client, a cast receiver, carries the app's own token; the rule is what keeps a second token -- another client on the HTTP routes -- from stopping the torrent under the first.) An unpin without a delete, a cache clean or the disk gate in front of a refused stream ends what a torrent announces the same way, but not while a player is on it or a stream reads it: the download's pieces stay announced, and on the disk, until playback leaves the torrent, and go then. A delete ends it at once instead (see *Unpin* under [Offline downloads](#offline-downloads)). A torrent restarted out of an error has its advertised set made again first, so it does not come back announcing the draw of a session that ended while it was dead. At shutdown every torrent is stopped and then the play sessions' files are deleted, best effort; whatever is left is the next start's -- the launch sweep takes every torrent nobody pinned, and a restored torrent announces nothing until told. The upload switch (`seedingEnabled`) is a separate question: it decides whether peers are served at all, not what is announced.

## Cache usage and cleaning

The cache bounds itself (see [What bounds the cache](#what-bounds-the-cache) above); these two calls let a client show its usage and ask for its slack back without a restart:

- **Usage**: `ServerHandle::cache_usage()` reports a `CacheUsage` without deleting anything: `{totalBytes, limitBytes, protectedBytes, protectedFiles}`. `totalBytes` is occupancy (`st_blocks * 512` on Unix, not apparent length), and it comes from the owners that hold the bytes rather than from a walk: a sum over the bits each live piece store keeps, plus the proxy cache's running count, plus one `read_dir` of the store root for what no live store speaks for (a torrent held in Error, a previous process's leftovers), plus the staged copies of the pieces a live store is still writing, one `stat` each. `limitBytes` is the limit actually enforced in the same accounting -- the smaller of `settings.cacheSize` and what the volume holding the cache can give while keeping the free-space floor free, so on a small device it is a number even when `cacheSize` is `null` (`null` only when neither caps anything: `cacheSize` unlimited *and* the volume's free space unreadable). `protectedBytes`/`protectedFiles` are what a pin keeps or the stream being played is inside -- the part nothing can take. When `protectedBytes` equals `totalBytes` and the cache is still over `limitBytes`, cleaning cannot help: there is nothing disposable left until playback moves on or something is unpinned, and that is the line to give a user, not "clean failed". It costs no walk, one `read_dir` and a `stat` per piece in flight, so calling it when a "Storage" screen opens or is refreshed is cheap; it is not cached server-side, so avoid polling it on a sub-second timer.
- **Clean now**: `ServerHandle::clean_cache_now()` gives back everything nobody is playing and nobody is reading, now -- the same passes the reconciler's tick and a viewer opening something else run, so it can never be less careful -- and answers an `EvictionReport`: `{total, protected, protectedFiles, freed, deleted, limit, overLimit}`, occupancy throughout. **It is not a choice of victims**: a pin is kept until it is unpinned and the window of the one entity being played is kept until something else is played, so on a device with one film playing and one pinned the honest answer is that nothing was freed. `freed`/`deleted` are what this call really took; `total` is what the cache occupies once it finished, which can still be over `limit`. The cap is restated before the report is built (`cache_budget::publish_now`), so the owners are sized against the volume as the clean left it. `limit` is the number `cache_usage()` answers, which is the same rule applied to a different figure: that total also counts what no owner's count prices -- a torrent held in Error, a directory a previous run left, the pieces in flight -- and the published cap does not, so with any of those on the disk the reported `limit` is larger than the cap the owners are sized against, and `overLimit` is the excess of the whole root rather than of what the owners hold. A client offering "clean now" should read the response the same way as `cache_usage()`'s shortfall case: if `total` is still over `limit` afterwards, say that the reachable cache is as small as it gets right now, because a pin or the stream being played is holding the rest -- not that the clean failed.

Both are `cache_cleaner::{usage, drop_slack}`, the same passes the reconciler's tick runs; neither has a route.
