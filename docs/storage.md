# Storage: downloads and the cache

Where torrent and proxied bytes live, what keeps them and what takes them: offline downloads, the bound on the cache, and the two calls a storage screen uses. The design behind the retention owner is [design/read-pattern-retention.md](design/read-pattern-retention.md). Downloads of non-torrent sources are [design/generic-downloads.md](design/generic-downloads.md).

## Offline downloads

A **pinned** file stays wanted no matter which file of the torrent is being played. Its torrent is exempt from idle removal and keeps running when nothing is playing, for as long as it has a pinned file. Nothing ever reclaims a byte of it: a pin is kept until it is unpinned, whatever the cache is doing. A pin is per file. The torrent's other files are cached like any unpinned file, windowed while they play and given back after, except for the pieces they share with the pinned one. **Pinning is a retention property, not a location**: a pinned download is not written anywhere else, does not move, and is stored one file per piece under the store's single root exactly like a torrent that is only being streamed. `stats.json` reports `pinnedFiles` and, per file, `pinned` and `complete` (`downloaded == length`).

- **Pin by id**: `ServerHandle::pin(&MediaId)` pins whatever a media id names, through the pin paths below: a torrent file through `pin_download` (with the URL's `tr=` trackers, and `-1` chosen as the stream route chooses it), a link through `pin_proxy_download`'s link half keyed with its `h=` headers, a Drive file under a grant asked of the id's `GrantSupplier` (none is asked for a file already whole on the disk: no grant and not whole is `ProxyPinError::NoGrant`). A member of a container pins its container (every volume of a set), since a member is ranges of those files. A file on this device is `PinError::NothingToDownload`. It answers the rows `downloads()` lists for it, one per file pinned. `ServerHandle::unpin(&MediaId, delete_files)` drops the same pins (`unpin_download`/`unpin_proxy_download` per file, outcomes joined: `unpinned` if any pin went, `deletedFiles` if any bytes did). A torrent URL with an explicit index is unpinned without resolving, so a dormant pin's torrent is never added to learn it. The info-hash and key methods below stay, and these dispatch to them.
- **Pin**: `ServerHandle::pin_download(info_hash, file_idx, trackers)`. `trackers` may be empty. A stream's own `sources`/`announce` array can be passed as is. As everywhere else, it only matters when this call is the one that creates the engine. Idempotent. The answer is one `DownloadInfo`: `{infoHash, fileIdx, path, name, length, downloaded, complete, phase, error}` (and, for a non-torrent download, `source` and `playUrl`). A file the torrent does not have is `PinDownloadError::FileNotFound`, a disk without room `InsufficientSpace`, a magnet that never resolved `MagnetAdd`. `PinDownloadError::client_message` is the sentence to show, and it names no local path.
- **List**: `ServerHandle::downloads()` -- the same `DownloadInfo` shape, one entry per pinned file, ordered by info hash then file index: live torrent rows first, then dormant pins (see *Restarts* below), then non-torrent rows. A dormant pin is answered by the disk. **With no `.pieces/<infoHash>` directory**, this server holds nothing of it and knows so. The row says held-nothing (`complete: false`, `downloaded: 0`, `phase: "buffering"`, no `error`), which a client reads as "not whole" (xtremio marks a finished row gone). **With one**, what it holds is unknown until the torrent comes back. The row is then `phase: "error"` with an `error` explaining that its torrent is not managed right now. `path`/`length`/`downloaded` are unknown (`null`/`0`) either way. Every pin the embedder hands in after the boot that deleted the previous build's cache directory (*Where*, below) is the first kind. `ServerHandle::download_path(info_hash, file_idx)` returns just the `path` without creating anything. It is a name and not a file: torrent data is stored one file per piece, so nothing is ever written at that path and a client plays a completed download through the media routes like any other.
- **Unpin**: `ServerHandle::unpin_download(info_hash, file_idx, delete_files)` answers an `UnpinOutcome {unpinned, deleted_files}`. `unpinned: false` means nothing was pinned. `deleted_files` reports what actually left the disk rather than echoing the flag: a delete that found nothing to take says `false`, and a failed delete is logged, not raised. Without `delete_files` only the pin goes: the bytes stay and the torrent is ordinary evictable cache again. The download stops being shared, which ends with its torrent leaving the swarm before its bytes go (see [Sharing](#sharing)). With it the data goes too, **and now**. A delete is an explicit request, so it happens whatever `seedingEnabled` says and whoever's play session is on the torrent. The whole torrent goes (pieces, session record, folder) when this was its last pin **and nothing else is on the torrent**. The activity registers and the viewer's session are asked first, so a season pack whose pinned episode 1 is deleted while episode 2 plays keeps running and loses only episode 1. Otherwise only the one file goes, with the torrent out of the swarm first. The torrent stops and the file's bytes go. What a play session drew of the file goes with them, and so do a player screen's hold and a viewer's idle share on the file. A cast's hold stays until it is unpublished. The torrent starts again only for what still needs it (another pin, a session or a read on another file). A piece the file shares with a still-pinned neighbour stays, announced for the neighbour, and the rest of the file goes. The answer waits for every unlink the delete set going, so `deleted_files` is never `false` for bytes this call takes. That includes the slack drop its end of shares makes, which would otherwise race the delete's own drop for the same pieces and leave it measuring a disk not yet freed. The one thing a delete waits for is a read of that very file, in practice a cast in progress. The pin and the download's entry go at once, the answer says `deletedFiles: false`, and the bytes go the moment that read ends. An unpin of a file whose own pin is still resolving its magnet, with nothing else joined to that add, aborts the add at once, and the pin answers `MagnetAddError::Cancelled`. Deleting the last pin therefore also drops files that were only ever streamed beside it. `delete_files` does not need the file to have been pinned, but it does need the file to exist: an unknown `file_idx` is `FileNotFound`, never a request to delete the whole torrent.
  - **A per-file delete is two deletions**: the pieces the backend agrees to give up (`drop_pieces` forgets them and hands the indices back for the caller to unlink), and any whole-file copy already at the path the backend reports. That copy is truncated before it is unlinked, because librqbit holds an open handle on every file of a running torrent. It also stops being the torrent's active file first, so the re-planned want-set cannot start refilling the unlinked inode.
  - **A dormant pin's directory** (see *Restarts*) is removed by `delete_files` once no file of that torrent is pinned any more. **"The backend does not have it" is checked, not inferred from the engine registry**: the registry can lose an engine while the session keeps the torrent (the idle sweep mid-step), and a magnet add parks a hash outside both. So the piece directory is deleted by hand only for a hash the session has never heard of. A torrent the session holds is deleted through the session, which drops it before its storage releases the pieces. A hash being added right now is left alone and answers `deletedFiles: false`.
- **Where**: nowhere in particular. A torrent's data is one file per piece under the store's single root (`<cacheRoot>/media-cache/.pieces/<infoHash>`, the directory being `enginefs::CACHE_DIR_NAME`), for the streaming cache and offline downloads alike. **A pin changes what is kept, not where**. A torrent streamed first and pinned later does not move, the engine every open reader holds stays the engine, and `path` is the name the backend gave the file. The one torrent-data root is `settings.cacheRoot`. An absolute path set there is checked, created if missing (a refused setting leaves no directory behind) and stored resolved. The update fails if it is not a string, is empty or relative, or cannot be created, written or listed. **A running librqbit session cannot move to a new root**, so a change takes effect at the next start. There the value is prepared before anything opens on it. One that can no longer be used falls back to the configured cache directory, and the fallback is persisted, so `settings()`, the file and the next boot agree.
  - **The directory was `rqbit-downloads` before**, and there is **no migration**: the first boot that finds `<cacheRoot>/rqbit-downloads` deletes it: the torrent pieces, the proxy cache, librqbit's `session.json` and DHT state, and every pinned download's bytes with them. It is renamed to `<cacheRoot>/.rqbit-downloads.deleting` before the session opens (cheap, at the cache root, outside anything the launch sweep walks). After the session opens, the renamed directory is deleted on the blocking pool, so the boot does not wait for a store of one file per piece to be unlinked. A boot that finds a `.rqbit-downloads.deleting` (left by a process killed mid-delete) deletes it too. The pins the embedder hands in then name torrents the session never restored: dormant, with no piece directory, so held-nothing (*List*, above).
- **Free space**: a pin is refused (`PinDownloadError::InsufficientSpace`) when the piece store's volume has less than the pinned file's missing bytes plus a **500 MiB margin** (`PIN_FREE_SPACE_MARGIN`). Only the missing bytes are asked for, because that is all a pin writes: re-pinning a complete file needs nothing, and a torrent still `checking` that the pin did not add is not measured at all (its `downloaded` reads 0 until the check ends). A whole-file download already at the path is not data in place and is measured for the whole file. A refused pin **drops the torrent it added and leaves every byte where it is**. The refusal comes before anything is downloaded, and what the store already held stays slack. A torrent the pin merely joined (a stream's in-flight add) is not dropped, nor is one a reader took hold of *while the pin was checking*. The engine is published before the check, so the live activity registers are consulted as well as the join count.
- **Restarts**: librqbit persists each torrent's place and want-set and, with fastresume, its verified pieces (`<cacheRoot>/media-cache/<infoHash>.bitv`), so a pinned download resumes where it was without a full re-hash. The pin set itself is the embedder's, handed in at startup (`ServerConfig::pins`, one `PinKey` per download: `{"kind": "torrent", "infoHash", "fileIdx"}`, `{"kind": "url", "target", "headers"}` or `{"kind": "drive", "fileId"}`). It is applied to the torrents the session brought back: its torrent keys to the piece store, its link and Drive keys to the proxy cache. A pin can name a torrent the session did not bring back, from a record librqbit could not restore (an unparseable `.torrent`, an add that errored). Such a pin is held dormant for the run, until the torrent returns or until it is unpinned. The torrent returns on a later boot, or with the next pin of the same torrent, which applies the dormant pins alongside its own.
- **Non-torrent downloads**: an addon URL or a Drive file is pinned with `ServerHandle::pin_proxy_download` (or `pin` by id) and kept in the proxy cache under a pin the embedder hands in at boot (the `url` and `drive` keys of `ServerConfig::pins`). `None` sweeps nothing and exempts nothing, and a list with none of them sweeps the proxy cache clean at launch. A filler fetches it whole. Its `downloads()` row carries `source` and a `playUrl`, `/downloads/{key}/stream`, which serves the pinned entry by range. Its `phase` is `ready` once whole, `buffering` while its filler runs, and `checking` while nothing fetches it (a Drive pin not pinned again with a pairing since boot, or a link whose filler stopped). A file that changes at the origin mid-download is a new download: the filler opens it again, the old generation's bytes go, and it fills the new file from its first byte. One that changed into a file the origin will not range stops the filler, and the row's `error` says why. The design is [design/generic-downloads.md](design/generic-downloads.md).
- **No pin set**: a server handed none (`ServerConfig::pins: None`, the default, so an embedder that keeps no pin record gets this) cannot tell a pin from cache, so it treats **every torrent as pinned** (`PinsUnknown`) for the life of the process. The launch sweep deletes no torrent data, the retention owner reclaims none, the reconciler keeps every torrent running (the free-space arm aside) and the idle sweep removes none. `downloads()` lists every file of every torrent the server holds. The proxy cache's launch sweep takes nothing either. Only the free-space floor bounds torrent data then. The proxy cache is bounded as always. **There is one set for both stores**: an embedder that cannot say what one store's pins are says `None` for the whole, since a set that names the torrents and not the links would have the sweep delete every link download. An embedder that passes an empty list is saying the opposite, that nothing is pinned, and both sweeps take everything unclaimed. xtremio passes the downloads the user asked for.

## What bounds the cache

**Every entity under the one root -- a file of a torrent, or one proxied body -- has exactly one retention owner that knows whether anybody wants it** (the piece store's for torrents, the proxy cache's for proxied bodies), and nothing walks the disk looking for victims. The root is `settings.cacheRoot`, taken from the running engine rather than from the setting, since a root set for the next start is not where the bytes are now.

**The cap is the smaller of `cacheSize` and what the filesystem can give**: `cacheSize` unset is `u64::MAX`. On a 4 GB television that meant nothing bounded the cache, and librqbit wrote until the filesystem refused. That ENOSPC arrives as a fatal torrent error, mid-film. So the server reads the volume's free space (`fs4::available_space` → `statvfs`: the raw `statfs` syscall on Linux, bionic's `statvfs` on Android, both `f_frsize * f_bavail`, i.e. `df`'s "Available") and caps the cache at `occupancy + available − floor`. That keeps the **free-space floor** free: a thirty-second of the volume, clamped between 128 MiB and 512 MiB (`enginefs::free_space_floor`). A phone keeps 512 MiB, and a 4 GB television keeps 128 MiB and can still play. A volume that will not say its size keeps 512 MiB. The floor is the same number `routes::stream::ensure_download_disk_ready` demands before it will stream to disk at all. Below it, that check asks both owners for their slack. It answers the stream `507 Insufficient Storage` if the disk is still short. A volume that cannot be probed is not read as "full": the configured `cacheSize` then stands alone. The stream gate reads the same failure the other way, as a `507`, on purpose. For the cap, "full" would evict a healthy cache, while the gate only declines to start writing until the volume answers again.

**A cap is a statement about one volume, and there is one root, so there is one cap.** `overLimit` stays as a field of its own (how far over the cap the cache still is), because it is what a client should read before telling a user that cleaning helped.

**What keeps a byte, and what takes it**: a **pin** is kept until it is unpinned, whatever else is happening. The **files in use** keep the window round their readers and the pieces of their shared set they hold. A file is in use while it is played, read, held by a player screen or a cast, or is a viewer's idle share (*Who keeps a torrent running*, below). **Everything else is slack.** The moment a viewer opens something else, what they left is disposable. It goes at the switch itself, at the reconciler's next two-second tick, when the volume runs low, on `clean_cache_now`, at shutdown, or at the next boot. A full clear (`clear_cache`, [below](#cache-usage-and-cleaning)) takes the files in use as well: everything but a pin. What the left play session announced to peers goes only once its torrent has left the swarm (see *Sharing* below). So stopping playback changes nothing on disk and resuming inside the window plays from the cache, while starting something else really does throw the previous stream away. The launch sweep runs at boot, before the session opens. It deletes every piece directory the embedder's pin set does not name, and a previous release's data beside the store (below). The proxy cache is swept of every entity no proxy pin names before the router serves a request, and any leftover `.archives` extraction directory is removed then too. A previous build's whole cache directory, `rqbit-downloads`, is renamed aside before the session opens and deleted after (see *Where* under [Offline downloads](#offline-downloads)). A boot handed no pin set sweeps no torrent data at all (see *Restarts* under [Offline downloads](#offline-downloads)).

**A stream that would not fit is refused rather than served by evicting something**: the `507` path drops every disposable byte, re-reads the volume and tries again. The answer is `507` if pins plus the live window still do not fit. A pin or a playing stream is never taken to make room. A torrent that already has everything it wants writes nothing and is never refused: a finished film plays on a full disk.

What is nobody's is not kept. Anything directly under `<cacheRoot>/media-cache` that is neither one of the owners' directories (`.pieces`, `.proxy`) nor a session record is not this store's own data, and it is never counted. It is a plain-file download (there is no migration: the torrent that owns it re-downloads as pieces), or a `.cache`/`.metadata` directory nothing here reads. The launch sweep (`piece_store::sweep::sweep_legacy_downloads`) removes it whole on every start that is handed a pin set. A start handed none keeps everything on the disk, that included. The session's records (`session.json`, `<infoHash>.torrent`, the `.bitv` bitfields, `dht.json`, `dht-bootstrap.json` and their temp files) are not cache and are never swept, and neither is a stray `pinned-downloads.json`. What `/proxy` cached is cache (`.proxy` under the cache root, see [Proxied remote streams](proxy.md#proxied-remote-streams)). It is counted in the same figure, capped by the same number, and kept by the same question: is somebody inside these bytes right now?

**Sizes are what a file occupies, not its apparent length**: a storage that pre-allocates a file at its full length before any of it is downloaded turns a part-streamed film into a multi-gigabyte `length` over a handful of written blocks. That was once measured as 17 GB of reported cache on a phone holding 3.85 GB. This server's piece-per-file store pre-allocates nothing. A root can still hold a file pre-allocated before it did, though, and nothing migrates one away, so the rule stands regardless. Unix uses `st_blocks`. Windows has no cheap equivalent through `std`, so the apparent length still stands in there.

**Who keeps a torrent running is declared, not guessed** (`enginefs/src/retention/holds.rs`). The reconciler runs a torrent that is **held** or pinned, and stops every other one at its next tick (every 2 s; a stop waits out no dwell). Nothing is inferred: not the last thing a stream opened (the liveness cell, which any open moves and which decides only what the retention windows keep), and no clock. A hold has an owner and a lifetime. **A player screen** holds the torrent its own `p=` requests named, from the first one until the app says the screen is gone (`ServerHandle::release_player`), paused, stalled or with nothing open. There is one per viewer. A newer screen's hold replaces an older one's, and a screen that never said goodbye holds nothing once the viewer plays anything else. A request carrying a released screen's token holds nothing again. **A cast** holds its id's torrent from `publish`/`publish_rendition` to `unpublish` (or the listener's stop). It is taken while the screen still holds the torrent, so a hand-over to a television has no gap. **A body being delivered** holds its torrent for exactly as long as it lasts. That is a stream response, from its registration before the reader opens to its end, with or without a player token. So another client on the HTTP routes starts the torrent it asks for and keeps it through the gaps between its reads. A held torrent's files keep their retention windows whatever the liveness cell names. **What a viewer watched last goes on sharing after they leave it**: the screen's goodbye (`release_player`), or the unpublish of a cast published with the viewer's play token, turns the play's hold into the viewer's **idle share** on the same torrent, in one step. It is released when the viewer starts watching something else: a request of a current screen of theirs naming another torrent or something that is not a torrent, or a cast of theirs published. Starting the same film again turns it back into the screen's hold with no stop between. One per viewer: two viewers leave two. It runs its torrent only while idle sharing is allowed (`seedingEnabled` on and `set_idle_sharing_held` not holding it back), asked at each reconcile. The torrent stops at the next tick when sharing is switched off or the app goes to the background on a handheld. It runs again when that changes, and the share stands throughout. Nothing is announced or withdrawn for it: the viewer's play session is still on the torrent, so its draw is what it shares, and the viewer starting something else ends it as a move does. So while nothing plays, what stays in the swarm is the pinned downloads and each viewer's idle share, and nothing else. An app that is turned off takes its idle shares with it. Holds live in this process's memory: an app that is killed takes them with it, and a restart starts with none. A cache clear overrides every one of them, and the bodies being delivered when it ran, until the next ask (`clear_cache`, [Cache usage and cleaning](#cache-usage-and-cleaning)). This replaced reading "playing" off the liveness cell and the reads open at the tick. That stopped the torrent a television was waiting on the moment anything else opened (measured on a phone: `torrent_stopped_by_reconciler playing=false` just after a cast began). The cell also kept the last-played torrent running, and sharing, after its screen was gone, until any other open moved it (a subtitle, a link through `/proxy`). The idle share now does that explicitly, and the cell no longer runs anything.

**A full disk is a signal to give slack back, not to stop**: librqbit treats a write that hits `ENOSPC` as fatal and leaves the torrent in an error state, which is how a film died ninety minutes in.

**The engine stops a torrent before the filesystem has to**: the engine's free-space arm pauses a torrent that is writing the moment the volume falls under the floor. The arm is the reconciler's: every 2 s, one `statvfs` of the volume every torrent's pieces land on. The pause is `Session::pause`: peers dropped, writes stopped, files and piece map kept. Pinned torrents are included, since a pin is a reason to keep the bytes, not a licence to run the disk out. The arm also rings the running-low bell, so both owners drop their slack at once. The torrent's readers see a buffering pause of a few seconds, not a dead stream. The reconciler restarts a torrent librqbit killed with ENOSPC once the volume is 64 MiB over the floor and something holds or pins it, at most once per 15 s.

**A proxied stream stops writing at the floor too**: a `/proxy` fill asks the volume before each chunk (one `statvfs`, re-read at most every 2 s, less what it has written since). A chunk that would take the volume under the floor is not written. The player keeps getting the body from the origin, and a later seek back into it fetches again.

A torrent the free-space arm stopped says `phase: "error"` in its `stats.json`, with a fixed "stopped for want of disk space" message, for as long as it is stopped. A `GET` for it drops both owners' slack, and it is a `507` if the volume is still short.

**A film larger than the free space plays anyway**, which is what the rolling piece window is for. Torrent data is one file per piece (the piece store is the session's default storage), so reclaiming a single piece is a `remove_file`. `enginefs/src/retention.rs` drives it from what the reads are doing, on the reconciler's two-second tick. The read-pattern detector finds every consumer on the file: a viewer, a second audio track, a player's index crawler. Each is kept and fetched a lookahead ahead of where it has reached. The lookahead is the film's own bitrate times the seconds the buffer profile asks for, shared out between the consumers when the disk cannot cover them all. Up to half the budget is a set committed for sharing. What puts the file over its allowance is given back, coldest first: the backend is told to forget it first, then the bytes go, under one claim. The shared set is never given back while the torrent is in the swarm. Bytes behind a consumer are not given back on a schedule: they are simply the first to go when the room is needed. That makes a scrub back cheap without anyone having to decide how far back a viewer might go.

**What a resumed film fetches ahead of its resume point is ordinary cache, held by nothing.** A torrent film resumed halfway asks the swarm for the resume point while the player is still reading the file's head ([media-pipeline.md §2.11](design/media-pipeline.md)). Those pieces are not pinned, not promised and not counted as protected. Once on the disk, they are kept while there is room. When there is not, they are given back in the same order as everything else: by when a piece was last any use, which for one nothing has read yet is when it arrived. They are protected only when the player's own reads reach them. The only thing held for it is the 16 MiB step being asked for at that moment, as a playing stream's read-ahead is. It is fetched through one background stream at a time (the rqbit fork's `FileStreamOptions::background`): its pieces come whole, one peer a piece, never at the head of the picker, so it never slows the player's own reads. Where the last session on the file ended is kept in `read-positions.json` beside `settings.json` (`note_media_position`). It asks for no piece that could not be kept beside what the readers hold, measured at each pass from the budget and what is held, so it never takes a reader's piece and never puts the cache over its cap. There is no share of the cache set aside for it.

**The budget is published on its own timer**: `server/src/cache_budget.rs` states it on a minute timer, at startup before the router serves a request, on every settings update, on `clean_cache_now` and on `clear_cache`. It states it from one `statvfs` and what the owners of the cache say they hold: a sum over the bits each piece store keeps, plus the proxy cache's running count, with no walk and no syscall. `ServerHandle::cache_usage`, `clean_cache_now` and `clear_cache` are how a client reads the cache's state, asks for its slack back on demand, and clears it. See [Cache usage and cleaning](#cache-usage-and-cleaning).

## Sharing

A torrent announces nothing that nothing chose: the session runs under the fork's `explicit_piece_advertising`, so a torrent announces no piece until told, whether it was added, restored at start-up or restarted out of an error. It serves a request only for a piece it announced. Two things choose:

- **A play session shares a set drawn once, and only the app's player has one.** A play session belongs to a viewer. Only a stream request carrying the player token (`p=<viewer>.<screen>`: a viewer id per install, a number per player screen) starts or moves it. It moves to the file the request names, the moment it names a different one (the next episode on its new screen, another title). It moves off every torrent for a `p=` request to `/proxy`, or for a reader opened with a play on anything that is not a torrent file (a link, a Drive file, a file on this device). A request from an older screen of the viewer than the newest one heard from (the last screen's player still reconnecting as the next takes over) moves nothing. The same film opened on a new screen is no move at all. Going back to the board is none either, and the session's draw goes on being shared while the torrent runs. A request without `p=` draws nothing, announces nothing and moves no session, and its bytes go like any unshared bytes. Such a request is a subtitle or side file, another client on the HTTP routes, or anything a translated source reads for itself (its index, and a member read without a play). **A member played through an id shares its own extent, in one file or across every volume of a set; a container played by URL shares nothing.** The app can open a reader with a play over a media id naming a member of a single-file container inside a torrent (a film in a stored RAR or ZIP, by the `torrent:` form). That puts the viewer's session on the container file, together with the member's byte extent in it. The draw is sized from the member's length and made only among the pieces the member lies in, so a season in one ZIP shares the episode being watched and not the ZIP. The film's rate is the member's length over its duration, told to the container for the draw alone. The container's own read-ahead takes no rate from it: for a season in one ZIP, that rate would be the season's. The container is not sniffed, since the member path already knows what it is. The draw is the member's: the next episode in the same ZIP is a move like any other, which ends the first episode's draw and draws the second's. The player's `p=` request for an archive's own file on the HTTP route still puts its session there sharing nothing, with the member read out of it without one. On that route an archive is told by its name at the request, and by its first bytes before anything is drawn (RAR, ZIP or a self-extracting ZIP, 7-Zip, ISO 9660, UDF, TAR, whatever it is called). The draw waits until those bytes are held. A member of a multi-volume set (`film.part1.rar`, `film.part2.rar`, ...) played by id shares the same way across the set. The session is on the set: every volume the member crosses, each with the member's bytes in it. The set is one thing played, so the reader crossing from one volume into the next moves nothing and ends nothing. Leaving the set (another film, another torrent) ends what it shared, as leaving a film does. The set draws once, over the member's bytes in all of its volumes. The draw is sized from the member's whole length. Its rate is that length over the film's duration, told to the volumes for the draw alone, and a volume's own read-ahead takes no rate from it. The first volume opened draws and announces the set. Every later volume keeps its own pieces of that draw and announces nothing new. A container behind links is a proxied entity and announces nothing. The draw is a uniformly random set of the file's pieces, at most half the budget and at most 90 seconds of film (`COMMITTED_SECONDS`). It is sized by the budget left beside the stream's **real** read-ahead, which is the film's bitrate times the seconds the viewer asked for. It is **nothing, when the budget cannot hold both**: playing wins. The bitrate is the film's size over the length the player states. The player states it once it has opened the media, so the draw waits for it, and nothing is announced before it anyway. A player that never states a length gets its draw after ten seconds of playback, sized beside what its opens asked for. Once drawn, the set is advertised. Each piece of it is announced the moment it has downloaded (or at once, if it is here already), and nothing else of the file ever is. Under a budget that covers the file the set is the whole file, read-ahead included: all of it is kept and shared for the session, and a panel's `committedBytes` counts it. Nothing the viewer does redraws it or grows it: a seek, a budget that rises or falls, a length stated later. The set is never fetched for: a viewer who stops halfway shares about half of it.
- **A download is shared whole**, finished or not, and keeps being shared after it finishes, for as long as it is pinned.

**An announcement is never taken back** (there is no un-Have in BitTorrent), and it ends only with the torrent leaving the swarm. So a player's session can move to anything else: another torrent, or the next file of the same one. The torrent it left is then **stopped first** (peers disconnected). Its advertised set is made again from what is still shared. It starts again at once if it is still wanted, and the next episode waits on that rebuild and nothing else. **Then** the left session's files are deleted, on the side. They are no longer advertised, so they are no longer anybody's. The next episode's reader never waits on an unlink. A torrent that stopped for any other reason has its advertised set made again before it starts, so it never comes back announcing a draw that went while it was stopped. **Nothing else stops a torrent that is being played but an explicit delete, and one viewer never stops it under another**: two viewers on two files of one torrent each keep what they left shared until neither is on the torrent. (With xtremio there is only ever one: the server is embedded in the app and dies with it, stremio-core is pinned to it, and the one outside client, a cast receiver, carries the app's own token. The rule is what keeps a second token (another client on the HTTP routes) from stopping the torrent under the first.) An unpin without a delete, a cache clean or the disk gate in front of a refused stream ends what a torrent announces the same way, but not while a player is on it or a stream reads it: the download's pieces stay announced, and on the disk, until playback leaves the torrent, and go then. A delete ends it at once instead (see *Unpin* under [Offline downloads](#offline-downloads)). A torrent restarted out of an error has its advertised set made again first, so it does not come back announcing the draw of a session that ended while it was dead. At shutdown every torrent is stopped and then the play sessions' files are deleted, best effort. Whatever is left is the next start's: the launch sweep takes every torrent nobody pinned, and a restored torrent announces nothing until told. The upload switch (`seedingEnabled`) is a separate question: it decides whether peers are served at all, not what is announced.

## Cache usage and cleaning

The cache bounds itself (see [What bounds the cache](#what-bounds-the-cache) above). These three calls let a client show its usage, ask for its slack back without a restart, and clear it when the user wants the space whatever is playing:

- **Usage**: `ServerHandle::cache_usage()` reports a `CacheUsage` without deleting anything: `{totalBytes, limitBytes, protectedBytes, protectedFiles}`. `totalBytes` is occupancy (`st_blocks * 512` on Unix, not apparent length), and it comes from the owners that hold the bytes rather than from a walk: a sum over the bits each live piece store keeps, plus the proxy cache's running count, plus one `read_dir` of the store root for what no live store speaks for (a torrent held in Error, a previous process's leftovers), plus the staged copies of the pieces a live store is still writing, one `stat` each. `limitBytes` is the limit actually enforced in the same accounting. It is the smaller of `settings.cacheSize` and what the volume holding the cache can give while keeping the free-space floor free. So on a small device it is a number even when `cacheSize` is `null`. It is `null` only when neither caps anything: `cacheSize` unlimited *and* the volume's free space unreadable. `protectedBytes`/`protectedFiles` are what a pin keeps or a file in use is inside: the part nothing can take. Cleaning cannot help when `protectedBytes` equals `totalBytes` and the cache is still over `limitBytes`. There is nothing disposable left until playback moves on or something is unpinned. That is the line to give a user, not "clean failed". It costs no walk, only one `read_dir` and a `stat` per piece in flight, so calling it when a "Storage" screen opens or is refreshed is cheap. It is not cached server-side, so avoid polling it on a sub-second timer.
- **Clean now**: `ServerHandle::clean_cache_now()` gives back everything nobody is playing and nobody is reading, now. It runs the same passes the reconciler's tick and a viewer opening something else run, so it can never be less careful. It answers an `EvictionReport`: `{total, protected, protectedFiles, freed, deleted, limit, overLimit}`, occupancy throughout. **It is not a choice of victims**: a pin is kept until it is unpinned, and the windows of the files in use are kept until nothing uses them. So on a device with one film playing and one pinned, the honest answer is that nothing was freed. `freed`/`deleted` are what this call really took. `total` is what the cache occupies once it finished, which can still be over `limit`. The cap is restated before the report is built (`cache_budget::publish_now`), so the owners are sized against the volume as the clean left it. `limit` is the number `cache_usage()` answers, which is the same rule applied to a different figure. That total also counts what no owner's count prices (a torrent held in Error, a directory a previous run left, the pieces in flight), and the published cap does not. So with any of those on the disk, the reported `limit` is larger than the cap the owners are sized against. `overLimit` is then the excess of the whole root rather than of what the owners hold. A client offering "clean now" should read the response the same way as `cache_usage()`'s shortfall case. If `total` is still over `limit` afterwards, say that the reachable cache is as small as it gets right now, because a pin or the stream being played is holding the rest. Do not say that the clean failed.

- **Clear**: `ServerHandle::clear_cache()` is the one call that takes what somebody is using: it **stops everything that streams a torrent and deletes every byte no download keeps**, and answers a `CacheClearReport`: `{freed, stopped, deleted, total}`. `freed` is how far the cache's occupancy fell across the call, `stopped` how many torrents were running before it and are stopped after it, `deleted` how many piece files and chunks left the disk, `total` what the cache holds afterwards (the kept downloads, and a link a player is still reading). In order (`cache_cleaner::clear`, `BackendEngineFS::clear_cache`):
  1. **Every hold is overridden** (`Holds::clear`): each player screen's hold goes, but the screen is not retired, so its next request holds again. Every idle share goes. Every cast's hold is set aside: still owned by its publication, it holds nothing, and its unpublish leaves no idle share. Every viewer's play session is put on nothing (`PlaySessions::clear`), so no draw is shared any more. The liveness cell names nothing (`Live::forget_all`), so no window is kept, the last-played title's included. The bodies being delivered off every torrent count for nothing in the reconciler's `held` until a stream starts on it again.
  2. **Every read open on a torrent is stopped** (`Engine::cut_reads`). Its backend stream and its head on the file's entity are taken out of the handle, so its lookahead no longer keeps a piece from being dropped, and a parked read is woken. Every read or seek of it from then on fails with `ConnectionAborted` ("the cache was cleared: this stream was stopped"). A source opened before the clear opens nothing after it (`TorrentSource`'s `cleared_at`, against `EngineFS::clear_generation`). The pre-wants walking end with them. **What the player sees**: its read fails. The app's player shows the error it shows for any failed read, and nothing fetches again behind it.
  3. **Every torrent is reconciled as an explicit delete is** (`reconcile_hash_ending_shares`): nothing holds it any more, so it stops. A download pinned on it keeps it running and downloading instead, because a kept download is not cache. What it announced that nothing shares any more ends with it out of the swarm (stop, the advertised set made again, a pinned one started again at once). The want-set is re-planned without the file that was playing.
  4. **Every piece no pin covers goes** through the retention layer's own slack pass (`Engine::drop_slack`): every entity is slack now, no read keeps a window and nothing announced keeps a piece. Then the proxy cache's slack pass runs with the cell naming nothing, which takes every entity but a pinned download and one a body is being read off now, whose chunks are promised to that body. A link a player is still streaming goes on (only torrents are stopped), and its window goes once its read has closed.

  Untouched: kept downloads, finished or not; the settings; where each file was last played (`read-positions.json`); and anything that is not this server's (an app's image cache). While the pin set is unknown every torrent counts as pinned, so nothing is stopped or taken for want of a hold. Afterwards whoever asks is served as a first ask is: a player's request holds its torrent again and it starts, a cast published holds, a stream started counts. It is what a user's "Clear the cache" calls, and what an app making room for an update escalates to when `clean_cache_now` did not free enough.

All three are `cache_cleaner::{usage, drop_slack, clear}`. None has a route.
